    第18章 代码应当一目了然

    晦涩性是2.3节介绍的复杂性的两个主要成因之一。当系统的重要信息对新开发者不够清楚时，就出现了晦涩性。解决办法是让代码一目了然。本章讨论哪些因素会让代码更清楚，哪些会让它更难懂。

    代码一目了然，意味着读者能快速阅读，几乎不用费力思考，对代码行为或含义的第一判断就是正确的。读者无需花很多时间和精力，就能获得使用和修改代码所需的全部信息。如果代码难懂，就必须花大量时间和精力理解。这既降低效率，也增加误解和 bug 的可能性。一目了然的代码需要的注释也更少。

    “清楚”取决于读者的感受：发现别人的代码难懂，比发现自己代码的问题容易。判断代码是否清楚，最好的办法就是代码审查。如果读者说代码难懂，那么它就是难懂，无论作者自己觉得多么清楚。试着理解读者困惑的原因，就能学会在今后写出更好的代码。

    18.1 让代码更清楚的做法

    前面已经讨论过两个最重要的方法。第一，选择好名称（第14章）。精确且有意义的名称能让代码行为清楚，减少文档需求。如果名称模糊、有歧义，读者就必须通读代码来推断所指实体的含义，既费时又容易出错。第二，保持一致性（第17章）。相似事情始终采用相似做法，读者就能识别见过的模式，无需详细分析代码，立即得出可靠结论。

    以下是另外几种通用方法。

    合理使用空白。 代码排版会影响理解难度。下面的参数文档挤掉了空白：

    /**
 *  ...
 *  @param numThreads The number of threads that this manager should
 *  spin up in order to manage ongoing connections. The MessageManager
 *  spins up at least one thread for every open connection, so this
 *  should be at least equal to the number of connections you expect
 *  to be open at once. This should be a multiple of that number if
 *  you expect to send a lot of messages in a short amount of time.
 *  @param handler Used as a callback in order to handle incoming
 *  messages on this MessageManager's open connections. See
 *  {@code MessageHandler} and {@code handleMessage} for details.
 */

    注释译文：numThreads 是管理器为管理当前连接应启动的线程数。MessageManager 对每个打开的连接至少启动一个线程，所以这个值至少等于预计同时打开的连接数。如果预计短时间内发送大量消息，应取该连接数的某个倍数。handler 用作回调，处理此 MessageManager 打开的连接上收到的消息。详情参见 MessageHandler 和 handleMessage。

    很难看出一个参数的说明在哪里结束、下一个在哪里开始，连参数数量和名称都不够醒目。加一点空白，结构就清楚了，文档也更容易扫读：

    /**
 *  @param numThreads
 *           The number of threads that this manager should spin up in
 *           order to manage ongoing connections. The MessageManager spins
 *           up at least one thread for every open connection, so this
 *           should be at least equal to the number of connections you
 *           expect to be open at once. This should be a multiple of that
 *           number if you expect to send a lot of messages in a short
 *           amount of time.
 *  @param handler
 *           Used as a callback in order to handle incoming messages on
 *           this MessageManager's open connections. See
 *           {@code MessageHandler} and {@code handleMessage} for details.
 */

    注释译文：内容与上例相同；参数名称单独成行，参数说明统一缩进。

    空行也适合分隔方法中的主要代码块，例如：

    void* Buffer::allocAux(size_t numBytes)
{
    //  Round up the length to a multiple of 8 bytes, to ensure alignment.
    uint32_t numBytes32 = (downCast<uint32_t>(numBytes) + 7) & ~0x7;
    assert(numBytes32 != 0);

    //  If there is enough memory at firstAvailable, use that. Work down
    //  from the top, because this memory is guaranteed to be aligned
    //  (memory at the bottom may have been used for variable-size chunks).
    if (availableLength >= numBytes32) {
        availableLength -= numBytes32;
        return firstAvailable + availableLength;
    }

    //  Next, see if there is extra space at the end of the last chunk.
    if (extraAppendBytes >= numBytes32) {
        extraAppendBytes -= numBytes32;
        return lastChunk->data + lastChunk->length + extraAppendBytes;
    }

    //  Must create a new space allocation; allocate space within it.
    uint32_t allocatedLength;
    firstAvailable = getNewAllocation(numBytes32, &allocatedLength);
    availableLength = allocatedLength - numBytes32;
    return firstAvailable + availableLength;
}

    译注：原书此处写作 availableLength = allocatedLength numBytes32;，缺少运算符。上面的转录根据上下文补入减号，写作 allocatedLength - numBytes32。

    注释译文：将长度向上取整为8字节的倍数，以保证对齐。如果 firstAvailable 处有足够内存，就使用它；从高地址向低地址分配，因为高地址处保证对齐，底部内存可能已经用于可变大小的块。接下来，检查最后一个块的末尾是否还有额外空间。若仍不够，就必须申请一片新的内存，并从中分配空间。

    如果每个空行后的第一行都是描述下一块代码的注释，这种方式就很有效：空行会让注释更醒目。

    语句内部的空白有助于显示结构。比较下面两个语句，一个没有空白，一个有：

    for(int pass=1;pass>=0&&!empty;pass--) {

    for (int pass = 1; pass >= 0 && !empty; pass--) {

    注释。 有时，难以理解的代码无法避免。这时必须用注释补充缺失信息。要做好这一点，就得站在读者角度，找出哪里容易产生困惑，以及哪些信息可以消除困惑。下一节会给出几个例子。

    18.2 让代码变得难懂的因素

    许多因素会让代码难懂，本节列出几个例子。其中一些方式，例如事件驱动编程，在特定场景中有用，最终可能仍会采用。这时，额外的文档可以尽量减少读者的困惑。

    事件驱动编程。 在事件驱动编程中，应用响应外部事件，例如网络数据包到达或鼠标按钮按下。一个模块负责报告到来的事件。应用其他部分注册自己关心的事件，要求事件模块在这些事件发生时调用指定函数或方法。

    事件驱动编程让控制流难以追踪。事件处理函数从不被直接调用，而由事件模块间接调用，通常通过函数指针或接口进行。即使找到了事件模块中的调用位置，也无法确定具体调用哪个函数，因为这取决于运行时注册了哪些处理函数。这样，就很难推理事件驱动代码的行为，也很难确信它能正确工作。

    为弥补这种晦涩性，应在每个处理函数的接口注释中说明调用时机，例如：

    /**
 * This method is invoked in the dispatch thread by a transport if a
 * transport-level error prevents an RPC from completing.
 */
void
Transport::RpcNotifier::failed() {
    ...
}

    注释译文：如果传输层错误导致 RPC 无法完成，传输组件会在分派线程中调用此方法。

    危险信号：代码不够清楚

    如果快速阅读后仍无法理解代码的含义和行为，这就是危险信号，通常说明有些重要信息未能让读者立即看明白。

    通用容器。 许多语言提供通用类，将两个或更多项组合成一个对象，例如 Java 的 Pair、C++ 的 std::pair。这类工具很有吸引力，因为一个变量就能方便地传递多个对象。常见用途之一是从方法返回多个值，例如下面的 Java 代码：

    return new Pair<Integer, Boolean>(currentTerm, false);

    遗憾的是，通用容器会让代码难懂，因为元素的通用名称掩盖了含义。上例中，调用者必须通过 result.getKey() 和 result.getValue() 访问两个返回值，这两个名称丝毫没有提示它们的实际含义。

    最好避免使用通用容器。需要容器时，为具体用途定义专门的类或结构体，就能给元素起有意义的名称，并在声明中提供额外文档；通用容器做不到这一点。

    这个例子体现了一条普遍原则：软件设计应以便于阅读为目标，不能只图编写方便。 通用容器让作者省事，却给后来的所有读者造成困惑。作者多花几分钟定义专门的容器结构，就能让代码更清楚。

    声明与分配使用不同类型。 看下面的 Java 示例：

    private List<Message> incomingMessageList;
...
incomingMessageList = new ArrayList<Message>();

    变量声明为 List，实际值却是 ArrayList。这段代码合法，因为 List 是 ArrayList 的父类型，但只看到声明、没看到实际分配的读者可能被误导。具体类型可能影响变量的用法：ArrayList 的性能和线程安全性质与其他 List 子类型不同。因此，声明最好与实际分配相匹配。

    违反读者预期的代码。 下面是一个 Java 应用的主程序：

    public static void main(String[] args) {
    ...
    new RaftClient(myAddress, serverAddresses);
}

    多数应用在主程序返回时退出，读者很可能以为这里也是如此，但实际并非如此。RaftClient 的构造函数创建了额外线程，应用主线程结束后，这些线程仍继续运行。应在构造函数的接口注释中记录这个行为；由于它很不直观，也值得在 main 末尾加一句简短注释，说明应用会继续在其他线程中执行。代码符合读者预期的约定时最容易理解；如果不符合，就必须用文档说明行为，以免读者困惑。

    18.3 小结

    也可以从信息的角度理解“一目了然”。代码难懂，通常意味着读者缺少重要信息：在 RaftClient 示例中，读者可能不知道构造函数创建了新线程；在 Pair 示例中，读者可能不知道 result.getKey() 返回的是当前任期编号。

    要让代码清楚，必须确保读者始终掌握理解它所需的信息。有三种方法。最好的方法是使用抽象、消除特殊情况等设计手段，减少需要掌握的信息。第二，利用读者在其他场合已经学到的知识，例如遵循约定、符合预期，让读者无需为当前代码另学一套。第三，通过恰当命名、有针对性的注释等方式，在代码中直接呈现重要信息。
