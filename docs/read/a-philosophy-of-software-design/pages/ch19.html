    第19章 软件开发趋势

    为了说明本书的原则，本章考察过去几十年软件开发中流行起来的几种趋势和模式。我会分别说明它们与本书原则的关系，并据此评估它们是否有助于应对软件复杂性。

    19.1 面向对象编程与继承

    面向对象编程是过去三四十年软件开发中最重要的新思想之一。它引入了类、继承、私有方法、实例变量等概念。恰当使用这些机制，有助于改善软件设计。例如，私有方法和变量可以确保信息隐藏：类外部的代码无法调用私有方法或访问私有变量，也就不可能对它们产生外部依赖。

    继承是面向对象编程的重要组成部分。它有两种形式，对软件复杂性的影响不同。第一种是接口继承：父类定义一个或多个方法的签名，却不实现它们。每个子类都必须实现这些签名对应的方法，但可以采用不同方式。例如，接口可以定义执行 I/O 的方法，一个子类实现磁盘文件的 I/O，另一个子类实现网络套接字上的同类操作。

    接口继承通过在多种用途间复用同一接口来降低复杂性。解决一个问题时学到的知识，例如怎样使用 I/O 接口读写磁盘文件，可以用于解决其他问题，例如通过网络套接字通信。也可以从深度的角度理解：一个接口的不同实现越多，接口就越深。要让接口拥有多种实现，就必须抓住所有实现的共同要素，避开实现之间不同的细节；这正是抽象的要义。

    第二种是实现继承。父类不仅定义方法签名，还提供默认实现。子类可以继承父类实现，也可以定义同签名的新方法来覆盖它。如果没有实现继承，多个子类可能需要重复同一方法的实现，从而在子类之间产生依赖：修改时必须同步修改每个副本。实现继承减少了系统演化时需要修改的代码量，也就是减轻了第2章介绍的变更放大问题。

    但实现继承会在父类与各个子类之间建立依赖。父类的实例变量经常由父类和子类共同访问，导致继承层次内的信息泄漏，使人很难在不查看其他类的情况下修改其中一个类。例如，修改父类时，开发者可能需要检查所有子类，确保没有破坏任何功能。同样，子类覆盖父类方法时，开发者可能需要查看父类实现。最坏情况下，修改任何一个类，都要完整了解这个父类之下的整个类层次。大量使用实现继承的类层次，往往复杂性很高。

    实现继承应谨慎使用。使用之前，考虑组合能否提供相同好处。例如，可以用小型辅助类实现公共功能，让原来的各个类分别使用辅助类的能力，无需从父类继承这些功能。

    如果没有可行的替代方案，就尽量把父类管理的状态与子类管理的状态分开。一种方法是让某些实例变量完全由父类方法管理，子类只能只读访问，或通过父类的其他方法使用它们。这是在继承层次内部应用信息隐藏，以减少依赖。

    面向对象编程的机制有助于实现清晰设计，但机制本身并不保证好设计。例如，类很浅、接口复杂，或者允许外部访问内部状态，仍然会带来很高的复杂性。

    19.2 敏捷开发

    敏捷开发是一种软件开发方式，源于20世纪90年代末关于让开发更轻量、灵活、渐进的一系列思想，并在2001年的一次从业者会议上得到正式定义。敏捷开发主要关注开发过程，例如团队组织、进度管理、单元测试的角色、客户沟通等，对软件设计本身关注较少。不过，它与本书的一些设计原则有关。

    敏捷开发最重要的思想之一，是开发应当渐进且迭代。软件系统通过一系列迭代逐步形成，每次增加并评估少量新功能，包含设计、测试和客户反馈。总体上，这与本书倡导的渐进方式相近。第1章提到，项目开始时无法把复杂系统想得足够透彻，因而无法一次确定最佳设计。获得好设计的最佳办法，是逐步开发系统，每一步增加少量新抽象，并根据经验重构已有抽象。这与敏捷开发相似。

    敏捷开发的一个风险是可能导致战术式编程。它容易让开发者把注意力放在功能上，忽略抽象，还鼓励推迟设计决策，以尽快交付能运行的软件。例如，有些敏捷实践者主张不要马上实现通用机制，先实现最小的专用机制，等确认有需求，再重构为更通用的形式。这些观点有一定道理，但与投资式做法相背，鼓励了更偏战术的编程方式，可能导致复杂性迅速积累。

    渐进开发通常是好主意，但每一步应围绕抽象组织，不能只围绕功能。 某个功能尚未需要一项抽象之前，完全可以暂不考虑它。一旦需要，就投入时间把它设计清楚，并按第6章建议，让它具有一定通用性。

    19.3 单元测试

    过去，开发者很少编写测试；即使有测试，通常也由独立的质量保证团队编写。敏捷开发的一项原则是让测试与开发紧密结合，程序员应为自己的代码写测试。这种实践如今已经普及。测试通常分成单元测试和系统测试。开发者最常编写的是单元测试：规模小、目标集中，每项通常验证单个方法内的一小段代码。它可以独立运行，无需搭建系统的生产环境。单元测试经常与覆盖率工具配合，确保应用的每一行代码都得到测试。开发者每次编写新代码或修改已有代码，都有责任更新单元测试，保持适当覆盖率。

    另一类是系统测试，有时也称集成测试，用于确保应用各部分能够正确协作。它通常需要在生产环境中运行整个应用，更可能由独立的质量保证或测试团队编写。

    测试，特别是单元测试，在软件设计中很重要，因为它让重构更容易。没有测试集，对系统结构作重大调整就很危险。没有便捷的方法发现 bug，问题很可能直到新代码部署后才暴露，那时定位和修复成本更高。开发者因而会避免重构测试不完善的系统，为每个新功能或 bug 修复尽量减少代码改动。结果是复杂性不断积累，设计错误也得不到纠正。

    有了完善的测试，开发者重构时就更有信心，因为测试集能够发现大多数新引入的 bug。这鼓励开发者改善系统结构，得到更好的设计。单元测试尤其有价值：它的代码覆盖程度高于系统测试，更可能发现 bug。

    例如，在开发 Tcl 脚本语言时，我们决定用字节码编译器替换 Tcl 解释器来提高性能。这项重大改动影响了 Tcl 引擎几乎所有核心部分。幸好 Tcl 有一套出色的单元测试，我们把它用于新的字节码引擎。已有测试发现新引擎 bug 的效果很好，以至于字节码编译器发布 alpha 版后，只出现了一个 bug。

    19.4 测试驱动开发

    测试驱动开发要求程序员先写单元测试，再写代码。创建新类时，先根据预期行为为类编写测试。由于类的代码还不存在，测试全都无法通过。接着逐个处理测试，编写刚好足以让当前测试通过的代码。所有测试通过，类就完成了。

    我大力支持单元测试，但不喜欢测试驱动开发。它的问题在于，把注意力放在让具体功能工作上，对寻找最佳设计关注不足。这完全是战术式编程，也带有它的全部缺点。测试驱动开发的步子太碎：任何时刻，都容易为了通过下一个测试而匆忙补入下一个功能。没有明确的设计时机，最终就容易一团糟。

    正如19.2节所述，开发应以抽象为单位，避免仅以功能为单位。一旦发现需要某项抽象，就应一次性设计它，至少设计出一套相对完整的基本功能，避免随着时间一点点拼凑。这样更可能得到清晰的设计，让各部分良好配合。

    修复 bug 时，先写测试就很合理。修复之前，先编写一个会因该 bug 失败的单元测试；然后修复 bug，确认测试现在能够通过。这是确保问题确实修复的最好办法。如果先修复再写测试，新测试可能根本没有触发原来的 bug，也就无法证明是否真的解决了问题。

    19.5 设计模式

    设计模式是解决某类特定问题的常用方式，例如迭代器、观察者。Gamma、Helm、Johnson 和 Vlissides 合著的《设计模式：可复用面向对象软件的基础》推广了这一概念。如今，设计模式已广泛用于面向对象软件开发。

    设计模式为从零设计提供了一种替代选择：直接采用广为人知的模式。多数情况下，这是好事。设计模式之所以出现，是因为它们能解决常见问题，而且被普遍认为提供了清晰的方案。如果某个模式适合当前情况，通常很难再想出比它更好的其他方式。

    设计模式最大的风险是过度使用。已有模式无法清楚地解决所有问题；定制方案更清楚时，就不要硬套模式。采用模式不会自动改善系统，只有适合时才会带来改善。像软件设计中的许多思想一样，设计模式好，并不意味着模式越多越好。

    19.6 Getter 和 setter

    在 Java 社区，getter 和 setter 是流行的设计模式。它们与类的某个实例变量关联，名称通常为 getFoo 和 setFoo，其中 Foo 是变量名。getter 返回变量当前值，setter 修改变量值。

    严格来说，它们并非必需，因为实例变量可以声明为公有。支持 getter 和 setter 的理由是，在获取或设置变量时可以执行附加功能，例如变量变化时更新相关值、通知监听者，或者限制取值。即使起初不需要这些功能，后来也可以在不改变接口的情况下添加。

    如果必须暴露实例变量，使用 getter 和 setter 可能合理；但更好的选择是从一开始就避免暴露实例变量。暴露变量意味着类的部分实现对外可见，违背信息隐藏，也增加接口复杂性。getter 和 setter 是浅方法，通常只有一行；它们给接口增添杂乱，却没有提供多少功能。应尽量避免 getter、setter，以及其他任何暴露实现数据的做法。

    确立一种设计模式的风险之一，是开发者认定它是好东西，便尽量多用。Java 中 getter 和 setter 的滥用就是这样出现的。

    19.7 小结

    每当遇到新的软件开发范式，都应从复杂性的角度质疑：它真的有助于尽量降低大型软件系统的复杂性吗？许多提议乍看很好，深入考察后会发现，其中一些会加剧复杂性。
