    第14章 选择名称

    为变量、方法及其他实体选择名称，是软件设计中最被低估的工作之一。好的名称本身就是文档：它让代码更容易理解，减少对其他文档的需求，也让错误更容易暴露。糟糕的名称则会增加代码复杂性，造成歧义和误解，进而引发 bug。命名体现了复杂性逐步积累的特点。某个变量用了平庸的名称，没有采用最好的名称，大概不会明显影响系统整体的复杂性。但软件系统有成千上万个变量；为它们都选好名称，就会显著影响复杂性以及系统是否易于管理。

    14.1 示例：糟糕的名称导致 bug

    有时，仅仅一个变量命名不当，就会造成严重后果。我修复过的最棘手的 bug 就源于一次糟糕的命名。20世纪80年代末到90年代初，我和研究生们开发了一个名为 Sprite 的分布式操作系统。后来我们发现，文件偶尔会丢失数据：用户并未修改文件，其中一个数据块却突然全变成了零。这个问题很少发生，追查起来异常困难。几名研究生尝试过定位，却始终没有进展，最终放弃了。但对我来说，任何悬而未决的 bug 都是无法容忍的个人侮辱，我决定查个水落石出。

    花了六个月，我终于找出并修复了这个 bug。问题其实很简单——大多数 bug 在弄清楚后都是如此。文件系统代码把变量名 block 用于两个不同目的。有时，它表示磁盘上的物理块号；有时，它表示文件内部的逻辑块号。不巧，代码中的某个 block 变量存放的是逻辑块号，却误用于需要物理块号的地方，结果把磁盘上一个无关的数据块覆盖成了零。

    追查期间，包括我在内的几个人都读过出错的代码，却没有发现问题。看到 block 被当作物理块号使用，我们就下意识地认定它存放的确实是物理块号。我花了很长时间加入诊断代码、追踪执行过程，最终确定数据破坏必然发生在某条语句中。这时，我才突破名称造成的思维障碍，检查这个值究竟来自哪里。如果给两种块分别命名，例如 fileBlock 和 diskBlock，这个错误大概就不会发生：程序员会知道，那个场合不能使用 fileBlock。

    遗憾的是，大多数开发者很少花时间琢磨名称。只要与对象大致相符，他们通常就采用最先想到的名字。例如，block 与磁盘物理块、文件逻辑块都相当接近，当然算不上糟糕透顶。但它还是让我们为追查一个隐蔽的 bug 耗费了大量时间。不要满足于“大致相符”。多花一点时间，选出精确、无歧义、直观的好名称。这份投入很快就能收回，而且随着经验积累，选好名称也会越来越快。

    14.2 让读者形成清晰印象

    选择名称的目标，是让读者在脑海中形成对命名对象性质的印象。好名称能传达实体是什么，也能传达同样重要的信息：它不是什么。考虑一个名称时，问问自己：“假如有人只看到这个名称，看不到声明、文档或使用它的代码，能在多大程度上猜出它指什么？有没有其他名称能让印象更清晰？”当然，一个名称能承载的信息有限；超过两三个词，就会变得笨重。挑战在于，用寥寥几个词抓住实体最重要的方面。

    名称是一种抽象：它为理解背后更复杂的实体提供了简化的思考方式。与其他抽象一样，最好的名称把注意力集中于实体最重要的方面，省去不那么重要的细节。

    14.3 名称应当精确

    好的名称具有两个特征：精确和一致。先谈精确。名称最常见的问题是过于宽泛或含糊，使读者难以判断它指什么；读者可能误以为它指的是另一回事，上面的 block bug 就是如此。看看下面的方法声明：

    /**
 * Returns the total number of indexlets this object is managing.
 */
int IndexletManager::getCount() {...}

    注释译文：返回此对象当前管理的 indexlet 总数。

    “count”太宽泛了：到底数什么？看到方法调用的人，如果不阅读文档，很难知道它做什么。getActiveIndexlets 或 numIndexlets 这样更精确的名称会更好：读者很可能无需查阅文档，就能猜出返回值的含义。

    下面这些命名不够精确的例子来自不同的学生项目：

    一个图形文本编辑器项目使用 x 和 y 表示字符在文件中的位置。这两个名称太宽泛，可能指很多东西，例如字符在屏幕上的像素坐标。单独看到 x，人们很难想到它表示字符在一行文本中的位置。使用 charIndex 和 lineIndex 会更清楚，这些名称反映了代码实现的具体抽象。

    另一个编辑器项目包含以下代码：

    // Blink state: true when cursor visible.
private boolean blinkStatus = true;

    注释译文：闪烁状态；光标可见时为 true。

    blinkStatus 传达的信息不足。对于布尔值，“status”太含糊，无法让人知道 true 或 false 分别意味着什么。“blink”也含糊，因为没有说明什么在闪烁。下面的写法更好：

    // Controls cursor blinking: true means the cursor is visible,
// false means the cursor is not displayed.
private boolean cursorVisible = true;

    注释译文：控制光标闪烁；true 表示光标可见，false 表示不显示光标。

    cursorVisible 传达了更多信息，例如读者可以猜出 true 的含义。一般而言，布尔变量名应当是一个判断条件。名称不再包含“blink”，读者若想知道光标为什么没有一直显示，就需要查阅文档；这项信息的优先级较低。

    一个实现共识协议的项目包含以下代码：

    // Value representing that the server has not voted (yet) for
// anyone for the current election term.
private static final String VOTED_FOR_SENTINEL_VALUE = "null";

    注释译文：此值表示服务器在当前选举任期内尚未投票给任何人。

    这个名称说明它是特殊值，却没有说明特殊含义。使用 NOT_YET_VOTED 这样更明确的名称会更好。

    一个没有返回值的方法中使用了名为 result 的变量。它存在多个问题。首先，它会让人误以为这个变量将作为方法返回值。其次，除了表明这是计算所得的值，它几乎没有提供任何实际内容信息。名称应说明结果究竟是什么，例如 mergedLine 或 totalChars。对于确实有返回值的方法，使用 result 是合理的。这个名称依旧有些宽泛，但读者可以从方法文档了解它的含义，而且知道这个值最终会被返回也很有帮助。

    危险信号：名称含糊

    如果变量名或方法名宽泛到可以指许多不同的东西，它就无法向开发者传达多少信息，背后的实体也更容易被误用。

    像所有规则一样，精确命名也有例外。例如，只要循环仅有几行代码，就可以用 i 和 j 这样的通用名称作为循环变量。如果能一眼看全变量的使用范围，通常就能从代码看出它的含义，无需长名称。例如：

    for (i = 0; i < numLines; i++) {
    ...
}

    代码清楚地表明，i 用于遍历某个实体中的每一行。如果循环长到无法一次看全，或者难以从代码推断迭代变量的含义，就应采用更具描述性的名称。

    名称也可能过于具体。下面是删除某段文本的方法声明：

    void delete(Range selection) {...}

    参数名 selection 过于具体，暗示被删除的文本始终是用户界面中选中的文本。但这个方法可用于任意文本范围，无论是否选中。参数名应更通用，例如 range。

    如果很难给某个变量想出精确、直观又不太长的名称，这就是危险信号：该变量可能没有清晰的定义或目的。此时可以考虑其他划分方式。例如，是否试图用单个变量表示多个事物？如果是，将它们分别表示为多个变量，可能让各自的定义更简单。选择好名称的过程能暴露设计弱点，从而改善设计。

    危险信号：名称难选

    如果很难为变量或方法找到一个简单的名称，让人对背后的对象形成清晰印象，就意味着该对象的设计可能不够清晰。

    14.4 一致地使用名称

    好名称的第二个重要特征是一致性。任何程序都有反复使用的某些变量。例如，文件系统不断操作块号。为每一种常见用途选定一个名称，并在各处一致使用。例如，文件系统可以始终用 fileBlock 表示文件内部块的索引。一致命名和复用公共类一样，可以降低认知负担：读者在某个上下文中见过这个名称，再在其他上下文看到时，就能复用已有知识，立即作出判断。

    一致性有三个要求：第一，对于特定用途始终使用约定名称；第二，绝不用这个名称表示其他用途；第三，用途必须足够明确，让所有同名变量的行为都一致。本章开头的文件系统 bug 违反了第三点。文件系统用 block 表示行为不同的两种变量：文件块和磁盘块。这使人误判变量含义，继而造成 bug。

    有时，需要多个变量表示同一大类事物。例如，复制文件数据的方法需要源块号和目标块号。此时，分别沿用约定名称，再加上区分前缀，例如 srcFileBlock 和 dstFileBlock。

    循环也是一致命名能发挥作用的地方。若用 i 和 j 作为循环变量，始终让 i 用于最外层循环、j 用于内层循环。读者看到名称，就能立即对代码行为作出可靠判断。

    14.5 不同意见：Go 风格指南

    并非所有人都认同我的命名观点。一些 Go 语言开发者主张名称应当很短，往往只有一个字符。Andrew Gerrand 在关于 Go 命名的演讲中说：“长名称会掩盖代码的作用。”1 他展示了下面这个使用单字母变量名的示例：

    func RuneCount(b []byte) int {
    i, n := 0, 0
    for i < len(b) {
        if b[i] < RuneSelf {
            i++
        } else {
            _, size := DecodeRune(b[i:])
            i += size
        }
        n++
    }
    return n
}

    他认为它比下面这个使用较长名称的版本更易读：

    func RuneCount(buffer []byte) int {
    index, count := 0, 0
    for index < len(buffer) {
        if buffer[index] < RuneSelf {
            index++
        } else {
            _, size := DecodeRune(buffer[index:])
            index += size
        }
        count++
    }
    return count
}

    我个人并不觉得第二个版本更难读。若要比较，count 对变量行为的提示还比 n 稍好一点。阅读第一个版本时，我不得不通读代码来弄清 n 的含义；第二个版本就没有这种需要。但如果整个系统始终只用 n 表示数量，那么对其他开发者来说，这个短名称大概也会很清楚。

    Go 的文化鼓励用同一个短名称表示多个不同事物：ch 可以表示字符或通道，d 可以表示数据、差值或距离，等等。在我看来，这些有歧义的名称容易造成困惑和错误，就像 block 的例子一样。

    总体而言，我主张由读者判断代码是否易读，作者自己的判断不能代替读者。如果使用短变量名写代码，读者也觉得容易理解，那就没有问题。如果开始有人抱怨代码晦涩，就该考虑采用长一些的名称；在网上搜索“go language short names”，就能看到若干这样的抱怨。同样，如果有人抱怨长变量名使我的代码难读，我也会考虑缩短名称。

    Gerrand 有一句话我很赞同：“名称的声明与使用位置相距越远，名称就应当越长。”前面讨论的 i、j 循环变量就是这个规则的例子。

    14.6 小结

    恰当的名称让代码更一目了然：读者第一次遇到变量，几乎不用思考，就能正确猜出它的行为。选择好名称体现了第3章讨论的投资心态：一开始多花一点时间，今后修改代码就会更容易，也更不容易引入 bug。培养命名能力本身也是投资。刚开始决定不再满足于平庸名称时，想出好名称可能费时且令人沮丧。但经验越多，这件事就越容易；最终，选好名称几乎不再需要额外时间，也就几乎不付成本便能获得收益。
