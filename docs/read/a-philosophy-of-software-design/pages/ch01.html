    第1章 引言

    一切都围绕复杂性

    编写计算机软件是人类历史上最纯粹的创造活动之一。程序员不受物理定律等现实条件的限制；我们可以创造令人兴奋的虚拟世界，让它遵循现实世界绝不可能有的行为规则。编程也不像芭蕾舞或篮球，需要高超的身体技巧或协调能力。它只需要创造性的头脑，以及组织思路的能力。只要能在脑中构想出一个系统，大概就能通过计算机程序实现它。

    这意味着，编写软件最大的限制在于我们理解所建系统的能力。程序不断演化、增添功能，便会越来越复杂，各组成部分之间也会形成微妙的依赖。复杂性日积月累，程序员修改系统时，越来越难以在头脑中同时顾及所有相关因素。这会拖慢开发、引入 bug，而 bug 又会进一步拖慢开发并增加成本。任何程序在其生命周期中，复杂性都会不可避免地增长。程序越大，参与开发的人越多，管理复杂性就越困难。

    好的开发工具有助于应对复杂性，过去几十年也确实诞生了许多出色的工具。但单靠工具所能做到的事情有其限度。要让软件更容易编写，以更低的成本构建更强大的系统，就必须找到让软件更简单的方法。即使竭尽全力，复杂性仍会随时间增长；不过，简单的设计能让我们在复杂性变得难以承受之前，构建出更大、更强的系统。

    对抗复杂性大体有两种途径，本书都会讨论。第一种是把代码写得更简单、更清楚，从而消除复杂性。例如，消除特殊情况，或以一致的方式使用标识符，都能降低复杂性。

    第二种途径是封装复杂性，让程序员处理系统时，无须同时面对它的全部复杂性。这种方法称为模块化设计。模块化设计把软件系统划分为多个模块，例如面向对象语言中的类。各模块在设计上相对独立，让程序员可以处理一个模块，而无须理解其他模块的细节。

    软件具有很强的可塑性，软件设计也就成为贯穿系统整个生命周期的持续过程；这使它有别于建筑、船舶、桥梁等实体系统的设计。不过，人们并非一直这样看待软件设计。在编程历史上的很长一段时间里，设计和其他工程领域一样，集中在项目初期进行。这种做法的极端形式称为瀑布模型：项目划分为需求定义、设计、编码、测试和维护等彼此分立的阶段。瀑布模型要求一个阶段完成后，下一个阶段才能开始；很多情况下，各阶段由不同的人负责。整个系统在设计阶段一次性设计完毕，阶段结束时设计便被冻结，后续阶段负责充实并实现这一设计。

    遗憾的是，瀑布模型很少能在软件开发中取得良好效果。软件系统天生就比实体系统复杂；在尚未动手构建时，不可能仅凭设想就充分理解一个大型软件系统的设计及其全部影响。初始设计难免存在许多问题，而且往往要到实现工作已经深入开展时，问题才会显现。瀑布模型却没有为此时的大幅设计调整做好安排，例如设计人员可能已经转去参与其他项目。开发人员于是尽量在整体设计不变的前提下打补丁，绕过问题，最终导致复杂性急剧膨胀。

    由于这些问题，如今多数软件开发项目都采用敏捷开发等增量式方法，初始设计只关注整体功能的一小部分。先设计、实现并评估这一部分，发现并修正原有设计的问题，再设计、实现和评估少量新增功能。每次迭代都会暴露现有设计中的问题，在设计下一批功能之前先把它们修好。这样分散设计工作，就能趁系统规模还小时解决初始设计的问题；后续功能也能借鉴实现前期功能时积累的经验，减少问题。

    增量式方法适用于软件，是因为软件足够灵活，允许在实现过程中大幅修改设计。实体系统的大幅设计调整困难得多。例如，桥梁建到一半时再改变支撑桥梁的桥塔数量，就不现实。

    增量开发意味着软件设计永远不会结束。在系统的整个生命周期中，设计始终持续：开发人员应当一直思考设计问题。增量开发也意味着持续重新设计。系统或组件的初始设计几乎总有更优方案；经验必然会揭示更好的做法。作为软件开发者，应当随时留意改进当前系统设计的机会，并计划拿出一部分时间改进设计。

    如果软件开发者应当始终思考设计问题，而降低复杂性又是软件设计最重要的内容，那么开发者就应当始终思考复杂性。本书讨论的，就是如何在软件的整个生命周期中，用复杂性指导设计。

    本书有两个总体目标。第一个是描述软件复杂性的性质：“复杂性”究竟是什么，为什么重要，以及如何识别程序中不必要的复杂性。第二个目标更具挑战：介绍在软件开发过程中尽量降低复杂性的方法。遗憾的是，没有一套简单的步骤能够保证产生优秀的软件设计。我会介绍一些接近哲学层面的高层概念，例如“类应该具有深度”或“通过设计消除错误”。这些概念未必能立刻指出最佳设计，但可以帮助比较候选方案，指导我们探索可能的设计。

    1.1 如何使用本书

    这里介绍的许多设计原则较为抽象，不结合实际代码可能难以体会。寻找合适的例子一直很有挑战：它既要足够小，能放进书中，又要足够大，能够体现真实系统的问题。如果遇到好例子，欢迎发给我。因此，仅靠本书，可能不足以学会如何运用这些原则。

    使用本书最好的方式是结合代码审查。阅读别人的代码时，思考它是否符合本书讨论的概念，以及这些概念与代码复杂性有什么关系。别人代码中的设计问题，比自己代码中的更容易看出来。可以借助书中的危险信号发现问题并提出改进建议。审查代码也能让你接触新的设计方法和编程技巧。

    提高设计能力最好的办法之一，是学会识别危险信号：它们表明一段代码可能比实际需要的更复杂。在全书中，我会针对各项主要设计问题指出相应的危险信号；其中最重要的汇总在书末。编程时就可以利用这些信号：一旦发现，先停下来，寻找能消除问题的其他设计。刚开始采用这种方法时，可能要尝试好几个方案，才能消除一个危险信号。不要轻易放弃：解决问题前尝试的方案越多，学到的也越多。渐渐地，你会发现代码中的危险信号越来越少，设计越来越清晰。实践也会帮助你发现其他可用于识别设计问题的危险信号，我很愿意听到这些发现。

    应用本书观点时，需要适度，并根据情况判断。每条规则都有例外，每项原则都有适用限度。任何设计理念走到极端，都可能产生糟糕结果。优美的设计体现着不同理念和方法之间的平衡。若干章节设有“做过头了”一节，介绍如何判断一种好做法是否已经过度使用。

    本书的例子几乎全部使用 Java 或 C++，讨论也大多以面向对象语言中的类设计为背景。但这些观点同样适用于其他领域。与方法有关的观点，几乎都可以用于 C 等没有面向对象特性的语言中的函数。设计理念也适用于类之外的模块，例如子系统或网络服务。
