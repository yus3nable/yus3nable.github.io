    第16章 修改现有代码

    第1章介绍了软件开发的迭代性和渐进性。大型软件系统经历一系列演化阶段，每个阶段都会增加新能力，修改已有模块。系统设计也就一直在演变。开发之初无法构想出正确的系统设计；成熟系统的设计，更多取决于演化期间的修改，初始构想的影响相对较小。前面几章讨论如何在最初设计和实现时减少复杂性，本章讨论如何防止复杂性在系统演化中悄然积累。

    16.1 坚持战略式思考

    第3章区分了战术式编程与战略式编程。战术式编程的首要目标是尽快让东西运行，即使增加复杂性也在所不惜；战略式编程最重要的目标则是产出优秀的系统设计。战术式做法很快就会让设计杂乱无章。要得到易于维护和扩展的系统，“能运行”这个标准还不够高；必须优先考虑设计，进行战略式思考。修改已有代码时也一样。

    遗憾的是，开发者修改已有代码、修 bug 或添加功能时，通常不会从战略角度思考。典型心态是：“能满足需求的最小改动是什么？”有时他们以不熟悉代码为由，担心改动越大，引入新 bug 的风险越高。但这会导致战术式编程。每次最小改动都会引入一些特殊情况、依赖或其他形式的复杂性，系统设计随之差一点。系统每演化一步，问题便多积累一点。

    如果希望系统设计保持清晰，修改已有代码时就必须采用战略式做法。理想情况下，每次修改完成后，系统结构都应如同从一开始设计时就考虑了这项变化。为此，必须克制快速修补的冲动，思考在新的需求下，当前设计是否仍是最佳选择。如果不再合适，就重构系统，得到尽可能好的设计。这样，每次修改都会改善系统设计。

    这也是原书第15页介绍的投资心态：多花一点时间重构和改进设计，就能得到更清晰的系统，进而提高开发速度，收回重构投入。即使当前改动不要求重构，在阅读和修改代码时，也应留意可以修复的设计缺陷。每次修改代码，都尽量顺便让系统设计改善一点。若没有让设计变好，很可能就在让它变差。

    第3章也谈到，投资心态有时会与商业软件开发的现实冲突。如果按“正确方式”重构需要三个月，而粗糙的快速修补只需两小时，可能就不得不采用后者，截止日期紧迫时更是如此。如果重构会产生兼容性问题，影响许多其他人和团队，这种重构也可能不现实。

    尽管如此，仍应尽量避免这些妥协。问自己：“在当前约束下，为了得到清晰的系统设计，我是否已尽最大努力？”也许存在另一种做法，只需几天，设计质量却接近三个月的重构？或者，眼下无法做大规模重构，就请主管在当前截止日期之后安排时间回来处理。每个开发组织都应计划拿出一小部分总投入，用于清理和重构；长期来看，这项工作能够收回成本。

    16.2 维护注释：让注释靠近代码

    修改已有代码时，很可能会让部分现有注释失效。改代码时容易忘记更新注释，导致注释不再准确。这会让读者烦恼；错误注释一多，读者就会开始怀疑所有注释。好在只需一点自律，再遵循几条原则，就能以不大的投入保持注释更新。本节及后续几节给出一些具体方法。

    确保注释得到更新的最好方法，是把它放在所描述代码的附近，让开发者改代码时能看到。 注释离相关代码越远，越不容易得到恰当更新。例如，方法接口注释的最佳位置在代码文件中，紧挨着方法体。修改方法一定会接触这段代码，开发者很可能看到接口注释，并按需要更新。

    对于 C、C++ 这样将代码和头文件分开的语言，也可以把接口注释放在 .h 文件中方法声明旁边。但这离实现很远：修改方法体时看不到这些注释，还要额外打开另一个文件，找到对应注释再更新。有人主张接口注释应放在头文件中，让使用者无需查看代码文件就能学会使用抽象。但使用者应从 Doxygen 或 Javadoc 等工具生成的文档获取信息，无需阅读代码文件或头文件。很多 IDE 也会提取并展示文档，例如输入方法名时显示方法说明。有了这些工具，就应把文档放在最方便代码开发者的位置。

    编写实现注释时，不要把整个方法的注释全堆在方法开头。应把它们分散开，让每条注释尽量靠下，处于能够涵盖所有相关代码的最小范围内。例如，一个方法分为三个主要阶段，就不要在顶部用一条注释详述所有阶段。分别为各阶段写注释，放在该阶段第一行代码之前。同时，在方法实现开头用一条注释描述整体策略也有帮助，例如：

    //  We proceed in three phases:
//  Phase 1: Find feasible candidates
//  Phase 2: Assign each candidate a score
//  Phase 3: Choose the best, and remove it

    注释译文：分三个阶段进行：第一阶段找出可行的候选项；第二阶段为每个候选项评分；第三阶段选出最佳候选项并将其移除。

    更详细的内容可以记录在各阶段代码正上方。

    一般而言，注释离它描述的代码越远，就应越抽象，这样能降低代码变化导致注释失效的可能性。

    16.3 将说明写进代码，别只留在提交日志里

    修改代码时，一个常见错误是把变更的详细信息写进代码仓库的 commit message，却没有在代码中记录。日后虽然能浏览仓库日志查看提交说明，但需要这些信息的开发者未必想得到去翻日志。即使想到了，找出正确的记录也很费事。

    编写 commit message 时，问问自己：开发者今后是否还需要这些信息？如果需要，就把它记录在代码中。例如，某个微妙问题促成了一次代码修改，提交说明解释了这个问题。若代码中没有记录，后来的人可能会撤销这次修改，却不知道自己重新引入了 bug。提交说明里也留一份当然可以，但最重要的是让代码中有这项说明。这体现了一条原则：把文档放在开发者最容易看到的地方；提交日志很少是这样的位置。

    16.4 维护注释：避免重复

    保持注释更新的第二个方法是避免重复。文档有多个副本，开发者就更难找到并更新所有相关版本。每项设计决策应尽量只记录一次。如果一项决策影响代码中的多处，就找一个最容易想到的位置集中记录，无须到处重复。例如，一个变量存在容易误解的行为，影响多个使用位置，可以把它记录在变量声明旁的注释中。开发者看不懂使用这个变量的代码时，自然会到这里查找。

    如果某份说明没有一个开发者容易找到的明显位置，可以按13.7节所述创建 designNotes 文件，也可以从已有位置中选出最合适的一处。在其他位置添加简短注释，指向集中说明：“下面代码的解释请参见 xyz 中的注释。”如果主注释被移动或删除，引用就会失效，但这种不一致很容易显露：开发者在指定位置找不到注释，可以借助版本控制历史查明原因，再更新引用。相反，重复文档中的某些副本没有更新时，开发者不会收到任何提示，不知道自己读到的是过时信息。

    不要在另一个模块里重复记录某个模块的设计决策。例如，不要在方法调用前用注释解释被调用方法的内部行为。读者需要了解时，应查看该方法的接口注释。良好的开发工具通常会自动提供这些信息，例如选中方法名或把鼠标悬停在其上，就显示接口注释。应让开发者容易找到合适的文档，避免靠重复文档实现这一点。

    如果程序外部已有某项信息的文档，就引用它，无需在程序内部再写一遍。 例如，编写实现 HTTP 协议的类，无需在代码里描述 HTTP 协议。网上已有大量资料，只要加一条简短注释，附上其中一个来源的 URL 即可。用户手册已经说明的功能也是如此。假设程序提供一组命令，每个方法负责实现一条命令；如果用户手册已说明这些命令，就不用在代码中重复。在各个命令方法的接口注释里加一句即可：

    // Implements the Foo command; see the user manual for details.

    注释译文：实现 Foo 命令；详情参见用户手册。

    读者需要能方便地找到理解代码所需的全部文档，但这些文档无须全部由你亲自编写。

    16.5 维护注释：检查 diff

    确保文档及时更新的一个好办法，是在向版本控制系统提交修改之前，花几分钟查看此次提交的全部改动，确认每项改动都已恰当地体现在文档中。提交前的检查也能发现其他一些问题，例如意外遗留的调试代码，或尚未处理的 TODO。

    16.6 高层次的注释更容易维护

    关于维护文档，最后再说一点：比代码层次更高、更抽象的注释，更容易维护。 这类注释不反映代码细节，细小代码变更不会影响它们，只有整体行为改变才会影响。当然，第13章也说过，有些注释确实必须详细、精确。但一般而言，最有用的注释——那些没有简单复述代码的注释——也最容易维护。
