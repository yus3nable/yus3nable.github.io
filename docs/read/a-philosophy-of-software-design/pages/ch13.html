    第13章 注释应说明代码中看不出的信息

    写注释，是因为编程语言的语句无法记录开发者写代码时脑中的全部重要信息。注释把这些信息保留下来，让后来者容易理解、修改代码。指导原则是：注释应说明代码中看不出的信息。

    这类信息很多。有时是底层细节，例如一对索引表示范围时，索引对应的元素是否包含在范围内；有时是为何需要这段代码，为何采用某种实现；有时是开发者遵循的规则，例如“调用 b 之前始终先调用 a”。读完全部代码或许能猜出规则，但很费力，也容易出错。一条注释就能把规则说清楚。

    抽象是写注释最重要的理由之一，因为抽象包含大量无法直接从代码看出的信息。抽象提供思考某个事物的简单方式，但代码细节太多，仅看代码往往难以看到抽象。注释可以给出更简单、更高层的视图，例如“调用此方法后，网络流量将限制在每秒 maxBandwidth 字节”。即使能从代码推导出这些信息，也不应强迫模块使用者这样做：读代码耗时，还迫使他们考虑许多使用模块时无须知道的信息。开发者应该只看模块对外的声明，就能理解它提供的抽象。唯一的办法是用注释补充声明。

    本章讨论注释需要描述哪些信息，以及如何写好注释。好的注释通常与代码处于不同的详细程度：有时更具体，有时更概括、更抽象。

    13.1 选定规范

    第一步是确定注释规范，例如给什么写注释、采用什么格式。如果所用语言有文档生成工具，例如 Java 的 Javadoc、C++ 的 Doxygen 或 Go 的 godoc，就遵循工具的规范。这些规范并不完美，但工具带来的收益足以弥补。如果环境中没有现成规范，尽量借鉴类似语言或项目的规范，方便其他开发者理解、遵循。

    规范有两个目的。首先保证一致性，让注释容易阅读、理解；其次，帮助确保确实写了注释。如果不清楚要给什么写、怎么写，最后很容易一条都不写。

    多数注释属于以下几类：

    • 接口注释：紧挨类、数据结构、函数或方法等模块声明之前的注释块，描述模块接口。类注释描述类提供的整体抽象；函数或方法注释描述整体行为、参数、返回值（若有）、副作用或异常，以及调用前必须满足的其他要求。
    • 数据结构成员注释：位于字段声明旁，例如类的实例变量或静态变量。
    • 实现注释：位于方法或函数代码内部，说明内部如何工作。
    • 跨模块注释：描述跨越模块边界的依赖。

    前两类最重要。每个类都应有接口注释，每个类变量都应有注释，每个方法都应有接口注释。偶尔变量或方法声明足够清楚，没有有用信息可补充，getter 和 setter 有时如此，但这种情况少见；给所有对象写注释，比费心判断是否需要更容易。实现注释通常不必写，见第13.6节。跨模块注释最少见，也难写，但需要时相当重要，第13.7节详述。

    13.2 不要重复代码

    遗憾的是，许多注释帮助不大。最常见的原因是重复代码：所有信息都能轻易从旁边的代码推导出来。最近一篇研究论文出现了这样的代码：

    ptr_copy = get_copy(obj)              # Get pointer copy
if is_unlocked(ptr_copy):            # Is obj free?
    return obj                      # return current obj
if is_copy(ptr_copy):                # Already a copy?
    return obj                      # return obj
thread_id = get_thread_id(ptr_copy)
if thread_id == ctx.thread_id:       # Locked by current ctx
    return ptr_copy                 # Return copy

    注释译文（依次）：获取指针副本；obj 是否空闲？返回当前 obj；已经是副本？返回 obj；由当前 ctx 锁定；返回副本。

    除了“Locked by”透露了某些从代码未必能看出的线程信息，其余注释没有有用内容。它们与代码的详细程度几乎相同：每行代码对应一条描述该行的注释。这类注释很少有用。

    下面也是重复代码的例子：

    // Add a horizontal scroll bar
hScrollBar = new JScrollBar(JScrollBar.HORIZONTAL);
add(hScrollBar, BorderLayout.SOUTH);
// Add a vertical scroll bar
vScrollBar = new JScrollBar(JScrollBar.VERTICAL);
add(vScrollBar, BorderLayout.EAST);
// Initialize the caret-position related values
caretX    = 0;
caretY    = 0;
caretMemX = null;

    注释译文：添加水平滚动条；添加垂直滚动条；初始化与插入光标位置相关的值。

    这些注释都没有价值。前两处代码已经足够清楚，无须注释；第三处可能需要注释，但现有注释细节不足，起不到作用。

    写完注释，问自己：从没见过这些代码的人，只看旁边的代码，能写出这条注释吗？如果像上述例子一样能，注释就没有让代码更好懂。这类注释正是有些人认为注释无用的原因。

    另一个常见错误，是注释沿用被说明对象名称中的词：

    /*
 * Obtain a normalized resource name from REQ.
 */
private static String[] getNormalizedResourceNames(
        HTTPRequest req) ...

/*
 * Downcast PARAMETER to TYPE.
 */
private static Object downCastParameter(String parameter, String type)
...

/*
 * The horizontal padding of each line in the text.
 */
private static final int textHorizontalPadding = 4;

    注释译文：从 REQ 获取规范化资源名称；把 PARAMETER 向下转换为 TYPE；文本各行的水平内边距。

    这些注释只是从方法或变量名取词，也许再加几个参数名、类型中的词，组成一句话。例如第二条注释，只有“to”没有出现在代码中！无须理解方法或变量，光看声明就能写出来，没有价值。

    危险信号：注释重复代码

    注释中的信息如果从旁边的代码就显而易见，便没有帮助。例如注释只是重复被说明对象名称中的词。

    与此同时，重要信息却缺失：什么是“规范化资源名称”？getNormalizedResourceNames 返回的数组各元素是什么？“向下转换”是什么意思？内边距用什么单位？加在每行一侧还是两侧？在注释中说明这些才有帮助。

    写好注释的第一步，是采用不同于对象名称的词。选择能补充对象含义的信息，而非重复名称。例如，textHorizontalPadding 更好的注释是：

    /*
 * The amount of blank space to leave on the left and
 * right sides of each line of text, in pixels.
 */
private static final int textHorizontalPadding = 4;

    注释译文：每行文本左右两侧各自留出的空白宽度，单位为像素。

    它提供了声明本身看不出的信息，例如单位是像素，以及每行左右两侧都要留白。注释还解释了 padding 的含义，让不熟悉术语的读者也能理解。

    13.3 较低层次的注释提高精确度

    知道哪些做法不合适后，来看看注释该写什么。注释通过提供不同详细程度的信息补充代码。有些注释比代码更具体、更细致，说明代码的确切含义，提高精确度；有些比代码更高层、更抽象，提供直观理解，例如代码背后的理由，或一种更简单、抽象的理解方式。与代码处于相同详细程度的注释，很可能只是在重复代码。本节讨论前一种，下一节讨论后一种。

    为类实例变量、方法参数、返回值等变量声明写注释时，精确度最有价值。声明中的名称和类型通常不够精确，注释可以补充以下细节：

    • 变量的单位是什么？
    • 范围是否包含边界？
    • 若允许空值，空值代表什么？
    • 若变量引用最终必须释放或关闭的资源，由谁负责？
    • 是否存在始终为真的性质，即不变量，例如“这个列表始终至少有一个条目”？

    检查所有使用该变量的代码，或许能推导出部分信息，但耗时且容易出错。声明处的注释应足够清晰完整，让人无须这么做。所谓声明注释应说明“代码中看不出的信息”，这里的代码指旁边的声明，不是应用的全部代码。

    变量注释最常见的问题是太模糊。例如：

    // Current offset in resp Buffer
uint32_t offset;

    // Contains all line-widths inside the document and
// number of appearances.
private TreeMap<Integer, Integer> lineWidths;

    注释译文：resp Buffer 中的当前偏移；包含文档内的所有行宽及出现次数。

    第一条的“当前”含义不清。第二条没有说明 TreeMap 的键是行宽、值是出现次数，也没有说明宽度按像素还是字符计量。修改后补充了细节：

    // Position in this buffer of the first object that hasn't
// been returned to the client.
uint32_t offset;

    // Holds statistics about line lengths of the form <length, count>
// where length is the number of characters in a line (including
// the newline), and count is the number of lines with
// exactly that many characters. If there are no lines with
// a particular length, then there is no entry for that length.
private TreeMap<Integer, Integer> numLinesWithLength;

    注释译文：第一个尚未返回给客户端的对象在本缓冲区中的位置。第二段：保存 <length, count> 形式的行长统计；length 为一行的字符数，包含换行符；count 为恰好含这么多字符的行数。如果没有某种长度的行，就没有对应条目。

    第二个声明用了更长、信息更多的名称，还把“宽度”改成“长度”，更容易让人想到字符数，而非像素。注释既说明每个条目的细节，也说明条目不存在意味着什么。

    描述变量时，多想它表示的对象，少想操作动作。把重点放在变量代表什么。例如：

    /* FOLLOWER VARIABLE: indicator variable that allows the Receiver and the
 * PeriodicTasks thread to communicate about whether a heartbeat has been
 * received within the follower's election timeout window.
 * Toggled to TRUE when a valid heartbeat is received.
 * Toggled to FALSE when the election timeout window is reset. */
private boolean receivedValidHeartbeat;

    注释译文：FOLLOWER 变量：用于 Receiver 与 PeriodicTasks 线程通信的指示变量，表示 follower 的选举超时窗口内是否收到心跳。收到有效心跳时置为 TRUE；重置选举超时窗口时置为 FALSE。

    这段文档描述类中几处代码如何修改变量。描述变量的含义，比照着代码结构写更简短，也更有用：

    /* True means that a heartbeat has been received since the last time
 * the election timer was reset. Used for communication between the
 * Receiver and PeriodicTasks threads. */
private boolean receivedValidHeartbeat;

    注释译文：True 表示自上次重置选举计时器后收到过心跳。用于 Receiver 与 PeriodicTasks 线程间通信。

    有了这段文档，很容易推断收到心跳时应设为 true，重置选举计时器时应设为 false。

    13.4 较高层次的注释增进直观理解

    注释补充代码的第二种方式，是帮助建立直观理解。这些注释比代码更高层，省略细节，帮助读者掌握整体意图和结构，常用于方法内部和接口注释。例如：

    // If there is a LOADING readRpc using the same session
// as PKHash pointed to by assignPos, and the last PKHash
// in that readRPC is smaller than current assigning
// PKHash, then we put assigning PKHash into that readRPC.
int readActiveRpcId = RPC_ID_NOT_ASSIGNED;
for (int i = 0; i < NUM_READ_RPC; i++) {
    if (session == readRpc[i].session
            && readRpc[i].status == LOADING
            && readRpc[i].maxPos < assignPos
            && readRpc[i].numHashes < MAX_PKHASHES_PERRPC) {
        readActiveRpcId = i;
        break;
    }
}

    注释译文：如果某个处于 LOADING 状态的 readRpc，与 assignPos 指向的 PKHash 使用同一 session，且该 readRPC 中最后一个 PKHash 小于当前待分配的 PKHash，就把待分配的 PKHash 放入该 readRPC。

    这条注释层次过低、细节过多。一方面它部分重复了代码：“存在 LOADING 状态的 readRPC”重复 readRpc[i].status == LOADING；另一方面，它没有解释代码的整体目的，以及在所在方法中的作用，无助于读者理解。

    更好的注释是：

    // Try to append the current key hash onto an existing
// RPC to the desired server that hasn't been sent yet.

    注释译文：尝试把当前键哈希追加到一个已有的 RPC 中，该 RPC 发往目标服务器，且尚未发送。

    它没有细节，从更高层描述整体功能。有了这个信息，读者几乎能解释代码中的一切：循环遍历所有现有 RPC；session 检查大概用于判断 RPC 是否发往正确服务器；LOADING 检查表明 RPC 有多种状态，某些状态下不能安全追加哈希；MAX_PKHASHES_PERRPC 检查表明每个 RPC 能发送的哈希数量有上限。唯独 maxPos 检查还无法从这条注释中得到解释。另外，新注释给读者判断代码的依据：为了向现有 RPC 添加键哈希，代码是否完成了全部必要工作？原注释没有交代整体意图，读者很难判断行为是否正确。

    高层注释比低层注释难写，因为需要换一种方式思考代码。问自己：代码想完成什么？怎样用最简单的话解释全部代码？这段代码最重要的是什么？

    工程师通常关注细节，喜欢细节，也擅长管理大量细节，这是优秀工程师的必备能力。但出色的软件设计者也能退后一步，从高层思考系统：决定哪些方面最重要，忽略低层细节，只按系统最基本的特征思考。抽象正是为复杂对象寻找简单的理解方式，写高层注释也需要这样做。好的高层注释用一个或几个简单想法提供概念框架，例如“追加到已有 RPC”。有了框架，就容易看清各条语句与总体目标的关系。

    下面是另一个拥有良好高层注释的例子：

    if (numProcessedPKHashes < readRpc[i].numHashes) {
    // Some of the key hashes couldn't be looked up in
    // this request (either because they aren't stored
    // on the server, the server crashed, or there
    // wasn't enough space in the response message).
    // Mark the unprocessed hashes so they will get
    // reassigned to new RPCs.
    for (size_t p = removePos; p < insertPos; p++) {
        if (activeRpcId[p] == i) {
            if (numProcessedPKHashes > 0) {
                numProcessedPKHashes--;
            } else {
                if (p < assignPos)
                    assignPos = p;
                activeRpcId[p] = RPC_ID_NOT_ASSIGNED;
            }
        }
    }
}

    注释译文：本次请求未能查询部分键哈希，可能因为服务器未存储它们、服务器崩溃，或响应消息空间不足。标记尚未处理的哈希，使其重新分配到新的 RPC。

    这条注释做了两件事。第二句抽象描述代码做什么；第一句从高层解释为什么会执行这段代码。“为何执行到这里”的注释对理解代码很有用。例如，给方法写文档时，说明它最可能在什么条件下被调用，往往很有帮助，特别是仅在少见情况下调用的方法。

    13.5 接口文档

    注释最重要的作用之一是定义抽象。第4章说过，抽象是对象的简化视图，保留必要信息，省去可以安全忽略的细节。代码过于底层，还包含抽象不应暴露的实现细节，不适合描述抽象。描述抽象只能依靠注释。想让代码提供良好抽象，就必须用注释记录它。

    第一步是分开接口注释和实现注释。接口注释提供使用类或方法必须知道的信息，定义抽象；实现注释描述类或方法内部如何工作，以实现该抽象。分开两者，才能避免让接口使用者接触实现细节。而且两者最好确实不同：如果接口注释必须同时描述实现，就说明类或方法很浅。编写注释能为判断设计质量提供线索，第15章会再次讨论。

    类的接口注释从高层描述它提供的抽象，例如：

    /**
 * This class implements a simple server-side interface to the HTTP
 * protocol: by using this class, an application can receive HTTP
 * requests, process them, and return responses. Each instance of
 * this class corresponds to a particular socket used to receive
 * requests. The current implementation is single-threaded and
 * processes one request at a time.
 */
public class Http {...}

    注释译文：本类实现一个简单的 HTTP 服务端接口，应用可以用它接收 HTTP 请求、处理请求并返回响应。每个实例对应一个接收请求的 socket。当前实现为单线程，每次处理一个请求。

    这段注释说明类的总体能力，没有实现细节，也没有具体方法的细节。它还说明每个实例代表什么，以及类的限制：不支持多线程并发访问。开发者判断是否使用这个类时，这一限制可能很重要。

    方法的接口注释既要有用于抽象的高层信息，也要有保证精确性的底层细节：

    • 通常先用一两句话描述调用者所见的方法行为，这是高层抽象。
    • 描述每个参数和返回值（若有），必须精确说明参数值约束，以及参数之间的依赖。
    • 记录所有副作用。副作用是影响系统未来行为、却不属于返回结果的后果。例如往内部数据结构添加一个值，后续调用能读取它；写入文件系统也属于副作用。
    • 描述所有可能从方法中传出的异常。
    • 描述调用前必须满足的前置条件，例如先调用另一个方法，或二分查找要求列表已排序。应尽量减少前置条件，仍然存在的则必须记录。

    下面是从 Buffer 对象复制数据的方法的接口注释：

    /**
 * Copy a range of bytes from a buffer to an external location.
 *
 * \param offset
 *        Index within the buffer of the first byte to copy.
 * \param length
 *        Number of bytes to copy.
 * \param dest
 *        Where to copy the bytes: must have room for at least
 *        length bytes.
 *
 * \return
 *        The return value is the actual number of bytes copied,
 *        which may be less than length if the requested range of
 *        bytes extends past the end of the buffer. 0 is returned
 *        if there is no overlap between the requested range and
 *        the actual buffer.
 */
uint32_t
Buffer::copy(uint32_t offset, uint32_t length, void* dest)
...

    注释译文：从缓冲区复制一段字节到外部位置。offset：第一个待复制字节在缓冲区中的索引。length：要复制的字节数。dest：目标位置，必须至少有 length 字节的空间。返回值：实际复制的字节数；请求范围超出缓冲区末尾时，可能小于 length；请求范围与缓冲区完全不重叠时，返回0。

    这里的语法，例如 \return，遵循 Doxygen 规范。Doxygen 从 C/C++ 代码提取注释并生成网页。注释的目标是提供调用方法所需的全部信息，包括特殊情况如何处理。注意它遵循第10章建议，消除了范围指定相关的所有错误。开发者无须阅读方法体就能调用它；接口注释也没有交代实现细节，例如如何扫描内部数据结构寻找数据。

    再看一个更完整的例子：分布式存储系统中的 IndexLookup 类。系统保存一组表，每张表包含许多对象，还可以有一个或多个索引。每个索引按对象的某个字段，提供高效访问。例如，一个按姓名查找，另一个按年龄查找。应用可以快速取出指定姓名的全部对象，或年龄在给定范围内的全部对象。

    IndexLookup 为索引查找提供方便的接口。应用中可能这样使用：

    query = new IndexLookup(table, index, key1, key2);
while (true) {
    object = query.getNext();
    if (object == NULL) {
        break;
    }
    ... process object ...
}

    应用先构造 IndexLookup，用参数选择表、索引和索引范围。例如索引基于年龄，key1、key2 可以是21和65，选择两者之间的所有对象。然后反复调用 getNext，每次返回范围内的一个对象；全部匹配对象返回完后，返回 NULL。由于存储系统是分布式的，类的实现有些复杂。表中对象可能分布在多台服务器，每个索引也可能分布在另一组服务器。IndexLookup 必须先联系所有相关索引服务器，收集范围内对象的信息，再联系实际存储对象的服务器，取回对象值。

    现在考虑类的接口注释应包含哪些信息。对以下每项，判断开发者使用这个类时是否需要知道，答案在章末：

    1. IndexLookup 发往存储索引和对象的服务器的消息格式。
    2. 判断对象是否在范围内所用的比较函数：按整数、浮点数还是字符串比较？
    3. 服务器存储索引的数据结构。
    4. IndexLookup 是否向不同服务器并发发送多个请求。
    5. 处理服务器崩溃的机制。

    下面是 IndexLookup 最初的接口注释，还摘录了注释提及的几行类定义：

    /*
 * This class implements the client side framework for index range
 * lookups. It manages a single LookupIndexKeys RPC and multiple
 * IndexedRead RPCs. Client side just includes "IndexLookup.h" in
 * its header to use IndexLookup class. Several parameters can be set
 * in the config below:
 * - The number of concurrent indexedRead RPCs
 * - The max number of PKHashes a indexedRead RPC can hold at a time
 * - The size of the active PKHashes
 *
 * To use IndexLookup, the client creates an object of this class by
 * providing all necessary information. After construction of
 * IndexLookup, client can call getNext() function to move to next
 * available object. If getNext() returns NULL, it means we reached
 * the last object. Client can use getKey, getKeyLength, getValue,
 * and getValueLength to get object data of current object.
 */
class IndexLookup {
    ...
  private:
    /// Max number of concurrent indexedRead RPCs
    static const uint8_t NUM_READ_RPC = 10;
    /// Max number of PKHashes that can be sent in one
    /// indexedRead RPC
    static const uint32_t MAX_PKHASHES_PERRPC = 256;
    /// Max number of PKHashes that activeHashes can
    /// hold at once.
    static const size_t MAX_NUM_PK = (1 << LG_BUFFER_SIZE);
}

    注释译文：本类实现索引范围查询的客户端框架，管理一个 LookupIndexKeys RPC 和多个 IndexedRead RPC。客户端只需在头文件中包含 IndexLookup.h，即可使用本类。下面可以配置并发 indexedRead RPC 数量、单个 indexedRead RPC 一次容纳的最大 PKHash 数量，以及活跃 PKHash 的大小。使用时，客户端提供所有必要信息创建对象，再调用 getNext() 移到下一个可用对象。返回 NULL 表示已到最后一个对象。可通过 getKey、getKeyLength、getValue、getValueLength 获取当前对象的数据。三个成员注释依次是：最大并发 indexedRead RPC 数；单个 indexedRead RPC 可发送的最大 PKHash 数；activeHashes 一次可容纳的最大 PKHash 数。

    继续阅读前，试着找出这段注释的问题。我的发现如下：

    • 第一段大部分是实现信息。使用者无须知道与服务器通信所用 RPC 的名称。后半段提及的配置参数都是私有变量，只有类的维护者需要关心，使用者无须知道。这些实现信息都应删去。
    • 注释还有几处显而易见的内容。例如无须提醒包含 IndexLookup.h，任何 C++ 程序员都能猜到。另如“提供所有必要信息”，没有表达具体内容，也应删去。

    更短的注释已经足够，而且更好：

    /*
 * This class is used by client applications to make range queries
 * using indexes. Each instance represents a single range query.
 *
 * To start a range query, a client creates an instance of this
 * class. The client can then call getNext() to retrieve the objects
 * in the desired range. For each object returned by getNext(), the
 * caller can invoke getKey(), getKeyLength(), getValue(), and
 * getValueLength() to get information about that object.
 */

    注释译文：客户端应用使用本类通过索引执行范围查询，每个实例表示一次范围查询。开始查询时，客户端创建一个实例，再调用 getNext() 获取范围内的对象。对 getNext() 返回的每个对象，可以调用 getKey()、getKeyLength()、getValue()、getValueLength() 取得相应信息。

    严格说，最后一段并非必需，因为大体重复了各方法的注释。但类文档中提供方法如何协作的示例可能很有帮助，特别是使用模式不直观的深类。新注释没有提及 getNext 返回 NULL：它无意记录每个方法的全部细节，只提供高层信息，让读者了解方法如何协作、何时可能调用某个方法。具体细节可以查各方法的接口注释。它也没有提及服务器崩溃，因为崩溃对使用者不可见，系统会自动恢复。

    危险信号：实现文档混入接口

    方法等接口的文档，如果描述了使用它时无须了解的实现细节，就出现了这一危险信号。

    再看 IndexLookup 中 isReady 方法的第一版文档：

    /**
 * Check if the next object is RESULT_READY. This function is
 * implemented in a DCFT module, each execution of isReady() tries
 * to make small progress, and getNext() invokes isReady() in a
 * while loop, until isReady() returns true.
 *
 * isReady() is implemented in a rule-based approach. We check
 * different rules by following a particular order, and perform
 * certain actions if some rule is satisfied.
 *
 * \return
 *         True means the next Object is available. Otherwise, return
 *         false.
 */
bool IndexLookup::isReady() { ... }

    注释译文：检查下一个对象是否为 RESULT_READY。本函数在 DCFT 模块中实现，每次执行 isReady() 都尝试推进一点；getNext() 在 while 循环中调用它，直到返回 true。isReady() 采用基于规则的实现，按特定顺序检查不同规则，满足某条规则时执行相应动作。返回值：True 表示下一个对象可用，否则返回 false。

    文档的大部分又是实现信息，例如 DCFT 和整个第二段，不应该放在这里。这是接口注释中最常见的错误之一。有些实现说明有用，但应放入方法内部，与接口文档明确分开。第一句也很晦涩：RESULT_READY 是什么？重要信息还有缺失。这里也没必要描述 getNext 的实现。更好的版本如下：

    /*
 * Indicates whether an indexed read has made enough progress for
 * getNext to return immediately without blocking. In addition, this
 * method does most of the real work for indexed reads, so it must
 * be invoked (either directly, or indirectly by calling getNext) in
 * order for the indexed read to make progress.
 *
 * \return
 *         True means that the next invocation of getNext will not block
 *         (at least one object is available to return, or the end of the
 *         lookup has been reached); false means getNext may block.
 */

    注释译文：指示索引读取是否已推进到足以让 getNext 立即返回、无须阻塞的程度。此外，本方法完成索引读取的大部分实际工作，要让读取推进，必须直接调用本方法，或通过调用 getNext 间接调用它。返回值：True 表示下次 getNext 不会阻塞，即至少有一个对象可返回，或查找已经结束；false 表示 getNext 可能阻塞。

    这个版本更精确地解释了“就绪”的含义，还交代了重要信息：若想索引读取继续推进，最终必须调用本方法。

    13.6 实现注释：说明做什么及原因，避免复述做法

    实现注释位于方法内部，帮助读者理解内部工作方式。多数方法短小简单，只看代码和接口注释就能明白，无须实现注释。

    实现注释的主要目标是帮助读者理解代码在做什么，具体怎样做通常可从代码看出。知道代码的目的后，通常就容易理解工作方式。短方法只做一件事，接口注释已经描述，无须再写实现注释。长方法包含几段代码，分别承担整体任务的一部分。在每个主要代码块前，从更高、更抽象的层次描述其作用，例如：

    // Phase 1: Scan active RPCs to see if any have completed.

    注释译文：阶段1：扫描活跃 RPC，检查是否有已完成的 RPC。

    循环前的注释可以说明每次迭代发生什么：

    // Each iteration of the following loop extracts one request from
// the request message, increments the corresponding object, and
// appends a response to the response message.

    注释译文：下面的循环每次迭代都从请求消息提取一个请求，递增相应对象，并向响应消息追加一条响应。

    它用更抽象、直观的方式描述循环，没有解释如何提取请求、如何递增对象。只有较长或复杂、目的不明显的循环才需要这类注释。许多循环短小简单，行为已一目了然。

    实现注释也适合解释原因。如果代码中有仅靠阅读无法明显理解的特殊之处，应写下来。例如，为修复 bug 而加入目的不明显的代码，就解释为什么需要它。如果已有一份清楚描述问题的 bug 报告，注释可以引用问题跟踪库中的条目，无须重复全部细节，例如“Fixes RAM-436, related to device driver crashes in Linux 2.4.x”（修复 RAM-436，与 Linux 2.4.x 设备驱动崩溃有关）。开发者可以去问题库查看细节，这是避免注释重复的例子，第16章会讨论。

    长方法中，可以为几个最重要的局部变量写注释。但大多数局部变量只要命名好，就无须文档。如果所有使用位置只相隔几行，通常很容易从代码理解用途，让读者自行查看代码就可以。如果变量在很长一段代码中使用，则应考虑补充注释。描述变量时，重点是它代表什么，避免复述代码如何操作它。

    13.7 跨模块的设计决定

    理想情况下，每个重要设计决定都封装在一个类中。但现实系统难免有影响多个类的决定。例如，网络协议设计同时影响发送方和接收方，两者可能实现在不同位置。跨模块决定常复杂而微妙，是许多 bug 的来源，良好文档至关重要。

    最大的困难是把文档放在开发者自然会发现的地方。有时存在明显的集中位置。例如 RAMCloud 定义 Status 值，每个请求返回它来表示成功或失败。为新错误增加 Status 需要改多个文件：一个把状态映射到异常，另一个提供各状态的人类可读消息，等等。幸好新增状态必定要修改 Status 枚举声明。我们利用这一点，在枚举中注明其他必须改的位置：

    typedef enum Status {
    STATUS_OK = 0,
    STATUS_UNKNOWN_TABLET = 1,
    STATUS_WRONG_VERSION = 2,
    ...
    STATUS_INDEX_DOESNT_EXIST = 29,
    STATUS_INVALID_PARAMETER = 30,
    STATUS_MAX_VALUE = 30,

    // Note: if you add a new status value you must make the following
    // additional updates:
    // (1) Modify STATUS_MAX_VALUE to have a value equal to the
    //     largest defined status value, and make sure its definition
    //     is the last one in the list. STATUS_MAX_VALUE is used
    //     primarily for testing.
    // (2) Add new entries in the tables "messages" and "symbols" in
    //     Status.cc.
    // (3) Add a new exception class to ClientException.h
    // (4) Add a new "case" to ClientException::throwException to map
    //     from the status value to a status-specific ClientException
    //     subclass.
    // (5) In the Java bindings, add a static class for the exception
    //     to ClientException.java
    // (6) Add a case for the status of the exception to throw the
    //     exception in ClientException.java
    // (7) Add the exception to the Status enum in Status.java, making
    //     sure the status is in the correct position corresponding to
    //     its status code.
}

    注释译文：新增状态值时还必须：（1）把 STATUS_MAX_VALUE 改为已定义状态值的最大值，并保证它位于列表最后，主要用于测试；（2）在 Status.cc 的 messages、symbols 表中加入条目；（3）在 ClientException.h 加入异常类；（4）在 ClientException::throwException 增加 case，把状态值映射到相应 ClientException 子类；（5）在 Java 绑定的 ClientException.java 中加入异常静态类；（6）在 ClientException.java 增加该状态的 case，以抛出异常；（7）将异常加入 Status.java 的 Status 枚举，确保其位置对应状态码。

    新状态会加在现有列表末尾，注释也放在末尾，最容易被看到。

    遗憾的是，许多跨模块文档没有明显的集中位置。RAMCloud 处理僵尸服务器就是例子：系统认为服务器已崩溃，实际却仍运行。让僵尸服务器失去影响能力，需要几个不同模块中的代码相互配合，它们彼此依赖，没有哪处明显适合放总说明。可以在各个依赖位置重复部分文档，但很别扭，也难以随系统演化保持更新。也可以只放在其中一个需要的位置，但开发者可能看不到，也不知道去哪找。

    最近我在尝试把跨模块问题集中写入 designNotes 文件，分成标题明确的章节，每个主要主题一节。例如：

    ...
Zombies
-------
A zombie is a server that is considered dead by the rest of the
cluster; any data stored on the server has been recovered and will
be managed by other servers. However, if a zombie is not actually
dead (e.g., it was just disconnected from the other servers for a
while) two forms of inconsistency can arise:
* A zombie server must not serve read requests once replacement servers
  have taken over; otherwise it may return stale data that does not

    僵尸服务器

    僵尸服务器是集群其余部分认为已经死亡的服务器；它保存的数据已经恢复，交由其他服务器管理。但如果它并未真正死亡，例如只是暂时与其他服务器失联，就可能产生两种不一致：

    • 替代服务器接管后，僵尸服务器必须停止处理读请求，否则可能返回旧数据，无法反映替代服务器接受的写入。
    • 替代服务器开始在恢复中重放日志后，僵尸服务器必须停止接受写请求，否则这些写入可能丢失，新值可能没有存到替代服务器，之后读取也就无法得到。

    13.8 结论

    注释的目标是让读者看清系统结构与行为，迅速找到所需信息，并有把握地修改系统。其中一部分信息可通过代码清楚表达，但还有大量信息难以从代码推导，注释应补足这些内容。

    遵循“注释应说明代码中看不出的信息”时，“明显”应从初次读代码的人的视角判断。写注释时设身处地想想，读者最需要知道什么。代码审查时，审查者说某处不清楚，不要争辩；读者认为不清楚，就说明确实不清楚。尝试理解困惑在哪里，再用更好的注释或代码澄清。

    13.9 第13.5节问题的答案

    开发者使用 IndexLookup 时，需要知道以下信息吗？

    1. 向存储索引和对象的服务器发送的消息格式。不需要，这是应隐藏在类内的实现细节。
    2. 判断对象是否落在范围内的比较函数，按整数、浮点数还是字符串比较。需要，使用者必须知道。
    3. 服务器存储索引的数据结构。不需要，应封装在服务器中，连 IndexLookup 的实现都不应需要知道。
    4. 是否向不同服务器并发发送多个请求。可能需要。如果采用特殊技术提高性能，文档应提供相应高层说明，因为使用者可能关心性能。
    5. 处理服务器崩溃的机制。不需要。RAMCloud 自动恢复，应用层软件看不到崩溃，接口文档无须提及。如果崩溃会向应用暴露，接口文档就需要说明它的表现，但无须说明崩溃恢复的内部细节。
