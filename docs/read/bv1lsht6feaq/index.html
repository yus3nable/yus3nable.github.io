    Lauren Tan 访谈：一个月 2500 个 PR 的 AI 工作流

    嘉宾：Lauren Tan（poteto）　·　主持人：Matt

    原视频 · 约 64 分钟

    从信任阶梯谈起：经验、语言与 skill

    主持人： Poteto，欢迎你，非常感谢你能来参加。

    Lauren Tan： 谢谢邀请。很高兴能来，我一直是你的忠实粉丝。

    主持人： 我也是你的超级粉丝。大家之前一直在谈论这次交流，说这就像是 skill 领域两大顶尖大脑的碰面，甚至是 skill 界的奥林匹斯峰会，因为我们俩都有非常受欢迎的 skill 库。就像我们开录前聊到的，我其实还没怎么用过你的 skill，所以我今天想把你脑子里的干货彻底掏空，好让我自己也能用上。

    主持人： 我想先从你最近的动态聊起。大约十天前你在 X 上发了一个演讲视频，彻底火了，主题是《我上个月如何向生产环境交付了 2500 个 PR》，获得了大概三百万次浏览。我看了那个视频，非常喜欢也极力推荐。今天我想把这场访谈基本上作为那场演讲的问答展开，因为我对它有太多疑问，特别想深入探讨一下。

    主持人： 我想切入的第一个话题是你提到的针对 agent 的“信任阶梯”：随着你对 agent 的信任加深，你可以让它们去完成越来越出色的任务，或者扩展规模去调用越来越多的 agent。关于这个阶梯，当你加入 SpaceX 并开始运行越来越多的 agent 时，具体是怎样运作的？

    Lauren Tan： 我觉得这段历程其实在加入 Cursor（也就是现在的 SpaceX AI）之前就开始了。故事是这样的：离开 Meta 之后——我之前在 Meta 的 React 团队工作——因为感觉有些倦怠，我休息了一个月。人在倦怠的时候会做什么呢？当然是去开一个新的副业项目。于是我做了一个业余项目，理所当然地用 AI 来写代码。但我很快意识到，自己花了太多时间事无巨细地盯着并干预单个 agent。

    Lauren Tan： 那大概是在一月或者二月初的时候，大家对编排（orchestration）这个概念非常着迷。当时 Cursor 的 agents window 这类界面还没流行开来，大家还在终端里操作，到处都在说“看，我自己写了一套定制编排器”。我自然也被这个技术问题吸引、一头钻了进去。在做玩具项目的过程中，我一直在琢磨：怎样才能让我的 AI 编程工作流更高效？于是我停下来重新审视，整个探索就从那里开始了。

    Lauren Tan： 我当时把大量时间都花在事无巨细地盯和干预单个 agent 上。虽然我写了各种 skill，但很难衡量这些 skill 的输出、结果以及实际影响，基本上是在盲人摸象，不过我的迭代速度非常快。那个项目最终成了 pstack 的雏形，尽管我当时还没意识到这一点。

    Lauren Tan： 我在构建那一批早期 skill 时学到了很多技巧。那个项目现在依然开源，大家想看的话可以在 GitHub 上搜索 poteto/noodle，里面包含了一些 skill 和一个 brain 目录。我当时特别感兴趣的是：如何把我自己的能力提炼出来并交给 agent。因为我意识到，自己所做的一切，其实都是在教 agent 像我一样写代码、像我一样跑工作流，而 skill 就是实现这一点的切入点。

    Lauren Tan： 后来我加入 Cursor，开始参与 agents window 的开发。它当时有很多性能问题，界面相当卡顿。因为我之前有 React 相关的经验，团队就问我愿不愿意来帮着优化 agents window。所以刚加入 Cursor 的那段时期全靠手动：我整天埋头分析火焰图（flame graphs）和堆快照（heap snapshots），排查应用到底为什么这么慢。但我再次意识到自己成了瓶颈：所有事情都手动来做，在某种程度上，我成了 agent 和 Chrome DevTools 之间的人肉中转，这让我非常恼火。

    主持人： 那是大概几月份？我们在时间线上处于什么阶段？

    Lauren Tan： 我是 3 月加入 Cursor 的，所以大概是 4 月初。刚入职时我手头没有任何现成的 skill，或者说我已经把个人的 skill 库搁置了，因为我觉得它们可能不再适用了。但后来在开发 agents window 以及现在做 Grok Bot 的过程中，我渐渐意识到，最初构建那批 skill 时积累的很多经验依然非常切题，尤其是在实际运行和交互验证方面。

    Lauren Tan： 你需要对工作保持极高的严谨性。根据我的经验，即便是目前最顶尖的 agent 也倾向于走捷径、怎么省事怎么来。所以我构建的很多 skill，核心都在于如何让最省事的做法恰恰成为正确的做法，让它成为最优解。

    主持人： 这种提炼自身专业知识、把你每天做的事情转化为流程的想法，让我非常有共鸣，我在做 skill 时也完全是这种思路。但我由此联想到一个问题：随着大家越来越依赖 AI，很多人开始觉得领域专业知识正变得越来越不重要。在深入探讨之前，先做个大致的交流，你怎么看这个观点？

    Lauren Tan： 我其实觉得领域专业知识比以往任何时候都更重要。我之前在 X 上也发过类似的观点：随着模型变得越来越聪明、能力越来越强——现在的尖端模型实在太厉害了，顺便说一句，我很喜欢 Opus 5.5——瓶颈几乎已经不再是 agent 本身了，而是变成了你是否能把自己的意图和目标清晰地表达出来，让 agent 能够理解并付诸执行。

    Lauren Tan： 正因如此，我认为拥有深厚领域专业知识的人很有优势，尤其是当你还对技术保持一些好奇心的时候。比如像医生、律师这种在非工程领域拥有深厚专业背景的人，只要他们稍微懂点技术，搞清楚怎么使用 agent，其实就能做出非常出色的产品。只要他们脑子里有足够清晰的构想，并且能够清楚阐述出来让 agent 去构建——在我看来，现在的瓶颈就在于把你的意图和构想传递给 agent。

    主持人： 没错，自从 agent 问世以来，我基本上就对语言着了迷。我一直在琢磨词句的构成，思考怎样才能把表达磨砺得更精准，以及自己使用的措辞中可能潜藏着什么。我最喜欢的一种体验是，当你找准了一个词，agent 就会敏锐地抓住它，并在思维链中不断强化和复用这个词。我发现 TDD 就是早期的典型例证：最近关于 TDD 的讨论很多，有人问跟 agent 一起写代码到底该不该用 TDD？其实这不重要，核心在于你通过这个词让 agent 去思考 TDD、让它去编写测试，并以一种截然不同的方式排定优先级。这也是为什么我认为 grilling 这种盘问机制非常有效。

    Lauren Tan： 没错，grilling 能把那些精准的词汇从你脑子里引导出来，或者至少帮助 agent 理解你的思考方式，从而由它主动向你提议那些词，你就能顺理成章地说：“对，就是这个词。”

    Lauren Tan： 我也借鉴了你分享的一些技巧。这其中我最喜欢的一条，是你最近分享的关于减少或消除同义反复测试（tautological tests）——只复述实现、无法检验有效行为的测试。我对 agent 最反感的一点就是它们写出的大量无用测试。说实话，“tautology”这个词对于非英语母语者来说可能比较生僻，但这个词本身承载着非常丰富的含义。

    Lauren Tan： 这个词本身的信息密度极高，就像被高度压缩了一样，把大量的意图与含义都凝聚在词汇之中。所以我完全同意你的观点。我一直对语言很感兴趣，无论是编程语言、人类自然语言，还是它们的演进历程。如今有了 Agent，自然语言与编程语言在此交汇融合；剥离表象来看，底层全都是语言，全都是沟通。

    米其林厨房与验证循环

    主持人： 确实如此。我大学学的是戏剧，长期以来都在琢磨语言、莎士比亚这类东西，所以面对这些倍感亲切。在深入探讨之前，我想先聊聊“软件工厂”。这是眼下的大热门词，我也一直在思考这个方向，甚至正准备推出一门相关的课程。它探讨的是如何将个人的产出规模扩展到看似不切实际的 PR 数量——对于不理解其运作机制的人来说，这种 PR 数量听起来简直匪夷所思。我想探讨的是，大家如何从如今运行一到五个 Agent，跨越到同时运转数百个 Agent。因此我很想听你聊聊用“米其林厨房”代替“软件工厂”的比喻，因为我觉得这很能体现你思考这些问题的方式。

    Lauren Tan： 我其实一直不太喜欢“软件工厂”这个说法。很多人想到工厂时，往往不会把它同品质或工艺（craft）联系起来。而这些对我、对很多做产品的技术人员来说都至关重要，我们非常在乎用户体验，在乎自己亲手打造的产品。所以，尽管我认为“软件工厂”是一个恰当的词，但有时难免带来负面联想。相比之下，“米其林厨房”是我最终选定的比喻，我觉得它更有追求，也更令人向往。

    Lauren Tan： 我很喜欢这个比喻。一方面我很喜欢美食，我网名当然叫 poteto，自己也热衷于烹饪；另一方面，我从中看到了很多相通之处。比如做饭这件事，自己给自己做饭时带有很强的实用目的，纯粹是为了填饱肚子、维持生存；但它其实也可以升华成艺术。米其林星级大厨，甚至普通的厨师，都能把极其普通的食材变成美味佳肴，甚至带你重温童年的记忆。这几乎完全契合了我之前谈到的“信任阶梯”（trust ladder）。

    Lauren Tan： 你可以想象一下自己作为家庭厨师的演进历程：所有的饭菜都得自己做，切菜、备料、打扫清理，完全是一个人的独角戏。不妨做一个思想实验：如果你正在做饭，突然加进来几个人——你的伴侣、兄弟姐妹，整家人一下子全挤进了厨房，我想大多数人都会感到压力倍增。一想到有这么多人挤在我的厨房里添乱，而且他们连餐具放在哪儿都摸不清楚，那种场面想想就让人头疼。

    主持人： 我的厨房容纳上限也就是一个人。

    Lauren Tan： 确实如此，我觉得这个比喻非常贴切。当你思考这个问题：如何从一名独自掌勺的厨师，过渡到拥有一支队伍——哪怕算不上大军，只有几位副厨（sous chefs）在厨房里协助你？你该如何合理分工？这种分工旨在让整体效果大于各部分之和，绝不能单纯为了分工而分工。米其林厨房的比喻在这方面非常契合，因为一旦你成为主厨，你就不必事事亲自下厨了。

    Lauren Tan： 这时你更像是厨房的技术主管（Tech Lead）或者 CEO。主厨不仅要考虑烹饪，更要统筹整个厨房的运作：何时采购食材？如何妥善储存？如何备料？各项准备工作何时必须就绪？这是一整套系统性的职责，远不止炒菜做饭本身。这与今天工程师编写代码的方式如出一辙：你不再亲自手写每一行代码，而是拥有了 Agent；但作为人类，你依然要对最终的结果负责，你的名字与声誉始终与你的工作成果绑定。因此，你如何搭建厨房，如何配置技能（skills）、环境与代码库，这些最终构成了打造产品的“新食材”。

    主持人： 我很欣赏你的方法，尤其是你对 Agent 运行环境的高度重视。很多人总觉得：现在的 Agent 已经很强了，我自己大概也做不出什么改进，不如直接信任模型厂商在 Harness 与模型组合中封装好的魔法；反正我们又改动不了 Claude Code 或其他工具的底层内部机制，自己似乎无能为力。但我非常赞同你的思路——这也是我一直提倡的——那就是你可以改变 Agent 运行的环境。你可以在代码库中进行改造，并为它配备验证工具，让它能够检验自身的工作成果。看你的演讲时，最打动我的正是你对验证机制的极度聚焦，因为这正是开始建立信任的关键杠杆。你能具体聊聊这到底是什么样的吗？大家可以通过哪些切实可行的方式，来改善自己的流程与“厨房”？

    Lauren Tan： 是的，我经常强调这一点：哪怕你不用 pstack，也不用现成的 skills，你的工具箱里最重要的一项技能也必须是验证。对不了解这个概念的观众来说，它其实就是给 Agent 赋予“双手”和“眼睛”——我很喜欢这个比喻。这意味着 Agent 不仅能运行代码，还能像普通人类用户一样与程序交互，并且能够进行调试、抓取跟踪（traces）和快照（snapshots）。

    Lauren Tan： 这正是我加入 Cursor 时构建的第一个技能。它让我真正开始沿着“信任阶梯”向上攀登，而这是我之前尝试或构建的其他技能都未曾做到的。因为无论其他技能有多出色——比如 how、why 或是 unslop 这些技能——如果 Agent 无法亲眼看到自己的工作结果，它就根本无法自主迭代，而我依然只能充当 Agent 与输出结果之间的人肉中转。

    Lauren Tan： 这也正是大家开始谈论“循环”（loop）的原因。很多人会觉得循环这个概念有些抽象，疑惑到底什么是 Agent 循环；但对我而言，构成循环并使其真正成为闭环的核心，正是验证环节。因为 Agent 能够自行验证工作结果，这就把你从环节中解放了出来。

    Lauren Tan： 我最初应用验证的场景之一，就是在 Cursor 上优化 Agent 窗口的性能。我希望能实现所谓的“爬山算法”（hill climbing）——这也是前沿实验室经常提及的概念。它的核心思想是：你拥有一套评估基准或评分机制，正因为有了闭环，Agent 就可以不断尝试、持续进行优化改进。Andrej Karpathy 广为人知的 autoresearch 项目也融入了大量类似的思想。所以在我看来，验证绝对是 pstack 中最重要的一项技能。

    Lauren Tan： 在很多其他工具集里，验证同样是最关键的技能，也是我认为最需要重点关注的地方。所以我花了很多时间去调优验证机制，尤其是 create-verification-skill。现在在团队内部，我们已经积累了大量的验证技能，Cursor 或 SpaceX AI 的各个应用都配有能自动维护的验证技能。因为每个人都在用，它已经成了我们团队不可或缺的基础设施。

    用 CLI 固定可重复的工作

    主持人： 你在这方面确实走得很深。在你的演讲中，我看到你甚至专门为此打造了一个自定义 CLI。这个 CLI 具体做些什么？它是如何执行任务的？你又是为什么决定这么做的？这足以说明你在这个方向上钻研得有多深、探索得有多激进。

    Lauren Tan： 这是我早期学到的一个经验。大概在今年一月或去年年底，大家最焦虑的问题是上下文窗口。当时最核心的话题就是“该怎么管理上下文窗口”，因为那时的压缩和摘要能力还不成熟，社区里甚至有这样一个梗：agent 一旦做了一次摘要或压缩，在接下来的整个会话里就会变笨。所以大家都在琢磨如何极度精简地利用上下文，这也正是我们在验证技能中引入 CLI 的灵感来源。虽说到现在，上下文已经不再是核心瓶颈了，毕竟现在的 agent 和运行框架在摘要处理上已经大幅进步。

    Lauren Tan： 不过，保持上下文干净依然很有价值。这个 CLI 更多是我用来把技能中确定性的部分抽取出来，固化成脚本或命令行工具，从而省去那些不必要的模型判断。我把 agent 和技能看作一个连续的光谱：一部分工作完全依赖判断，需要结合多方上下文进行深度思考；另一部分则是高度确定性的。比如把代码从一种模式重构成另一种模式，这非常机械，根本不需要 agent 每次都重新动脑构思一遍。这也正是我开发该 CLI 的灵感来源。

    Lauren Tan： 在我构建的其他技能里，你也能看到同样的思路：尽量把确定性的环节抽离并转化为代码，只把真正需要主观判断的部分留给 agent。从某种意义上说，技能更像是一层轻量封装，里面附带几条指引，教 agent 如何调用技能内置的自定义工具。其实这个 CLI 单独拿出来看并没有什么高深之处，谈不上多具颠覆性，它无非是跟 Playwright 和 Chrome DevTools Protocol 交互、调用一系列 API 的胶水代码罢了。

    主持人： 不，这很精妙，因为它实际上是在向技能隐藏细节，从而精简技能的体量，让技能本身保持得非常小巧；随后你又能把更复杂的确定性逻辑委托给技能内部的脚本。这相当于在压缩信息，并让 agent 的行为更加稳定可预测。这确实非常有吸引力。

    Lauren Tan： 是的。而且如果你关注上下文窗口，它确实有直接帮助，因为 agent 不需要再去重新造轮子。早期我们还没做 CLI 时，我发现 agent 每次尝试验证自己的工作，几乎都要从头重建整套逻辑，而且每个 agent 的搞法还各不相同。这极其低效，不仅浪费上下文，更拖慢了执行速度——agent 不得不自己去写测试脚本或 CLI，写出来还经常报错；而上一个 agent 明明写成功了，却把代码随手丢弃。所以当时显而易见的解决办法，就是把它做成 CLI 内置在技能里，让后续所有调用的 agent 都能直接享受这份成果。

    Lauren Tan： 这也促使大家去反思：你的技能和规则里，究竟有多少本该是确定性的？这也是我反复思考的核心原则之一：如何高效划分确定性与非确定性。让 agent 在非确定性的领域大放异彩，因为这正是模型的专长；而更机械、更直接的任务，则完全交由确定性逻辑处理。比如在进行技术迁移时——这也是我经常强调的一大重点，即迁移到更适合 agent 工作的技术栈——很多迁移都可以依靠脚本和 CLI 这种确定性工具来完成。利用 codemod 遍历 AST（抽象语法树），纯机械化地完成代码转换，完全由脚本搞定，不需要 agent 介入。

    通过环境与约束减少出错

    主持人： 完全合乎逻辑。我觉得这里还有一层含义：你把任务从 agent 手中抽离出来，部分沉淀到了环境里。比如发现 agent 老是在某个环节犯错，你就在环境里直接杜绝犯错的可能。这在很大程度上也关乎代码质量。我经常探讨什么是“优秀的代码库”，我喜欢的一个定义是：易于修改、且修改时不会把系统搞砸的代码库。这意味着必须设置大量护栏，将 agent 或人类约束在极其狭窄的安全路径内，而这正是你在演讲里强调过的。

    主持人： 你不仅在自动化检查（比如代码检查、类型检查等）上落实了这种思路，更贯穿在抽象层的设计中，你们甚至专门为 agent 打造了一套工作框架。你显然把这件事看得极重，那么我很想知道：相比于去开发新功能或交付日常业务，打磨这种环境在你的优先级排序里究竟占多大比重？

    Lauren Tan： 是的，我甚至觉得工程师如今的新本职工作就是花精力打理环境。我昨天差点就发了一条推文聊这个。如果你不肯花时间去建立对 agent 的信任、构建配套的技能和工具，就会卡在“信任阶梯”的最底层。因为对 agent 的工作缺乏信任，唯一的应对方式就是寸步不离、事无巨细地盯着并干预它，这极其耗费时间。一旦陷入这种状态，你根本没有余力去思考更高维的问题，比如怎样真正大幅提升生产力。

    Lauren Tan： 如果你在经营一家米其林餐厅的后厨，而厨师们手头没有任何专业工具，那一切自然会变得极其低效，每个厨师都会自行其是。所以在我看来，工具与确定性正是为了消除这种随意性。正如你刚才所提到的，约束也是同样的道理。

    Lauren Tan： 顺着约束这个话题稍微展开一点，我觉得我们应该聊聊 TypeScript。因为我们其实都有 TypeScript 的背景——你在 TypeScript 和 Total TypeScript 方面做了大量工作，是该领域的领军人物；而我很早就开始使用 TypeScript，很多年前还在 TypeScript Conf 上做过一两场演讲。

    Lauren Tan： 我当时的一场演讲就是关于类型系统以及如何对类型施加约束。在 TypeScript 中，我最喜欢的功能之一就是类型收窄（type narrowing）。它的核心思想是：你从一个非常宽泛、可能代表任何东西的类型出发，通过类型守卫（type guards）、类型收窄以及运行时检查，逐步缩小可能性的空间，最终断定它不仅仅是一个普通字符串，而是一种非常特殊的字符串字面量常量。这一切都是通过类型系统确定下来的。

    Lauren Tan： 我认为这与在代码库中设立约束有许多相通之处，都是在收窄空间。如果从范畴论的角度来看，你是在约束可能存在的类型数量，明确规定只允许存在这一种类型。对我们来说，我正在构建的内部框架 Dune 就是这种理念的体现。它不是一个开源框架，我通常把它形容为专门用于我们 Electron 应用的内部 Next.js。但它内置了极其严苛的 lint 规则，整个代码库在设计上确保了做某件事基本上只有唯一的实现方式。

    Lauren Tan： 因此我们大量采用约定俗成的架构模式。比如所有功能特性都放在指定目录下，每个功能都有独立的专属目录，系统会通过注册表和扫描代码库来自动发现这些功能。这种约定模式结合严苛的 lint 规则，构建出了一个极难写出糟糕代码的环境。这不仅解放了我们自身的心智负担，也让 agent 不必再为此分心：如果想要添加新功能，直接放入新的 feature 目录即可，所有代码都归置在里面，绝不会发生往某个上帝文件里随意追加代码的情况。

    Lauren Tan： 这种特性目录的划分灵感，其实源于 Grok Bot 最初的几个版本——当时它由大约 8 个上帝文件组成，每个文件少说也有一万多行甚至更长，我不得不把它们拆解成更小的模块。而在这一过程中，更关键的是持续观察 agent 是如何出错的。每当你看到一个失误，或者发现某处可以做得更好，就要停下来重新审视：我该如何把这个教训转化成一条 lint 规则？怎样才能让代码库在机制上杜绝这种错误？这又绕回了我学习 TypeScript 和类型系统的背景——如何收窄可能性空间，以确保自己精确掌控所面对的代码。我认为两者在这点上有着极高的相通之处。

    主持人： 这完全说得通。不过你在同一句话里同时提到 TypeScript 和上帝文件挺逗的，因为 TypeScript 出了名地拥有一个处理类型的两万五千行大文件。

    Lauren Tan： 确实，我也意识到了，这我知道。不过我不知道他们有没有用 Go 重写过那个文件，大概已经重写了吧。

    主持人： 好，所以开发环境至关重要。你需要时刻密切注视 agent，确保把它的每一次失误都转化为环境中的机制。而依托环境的好处在于，你不会让规则超载 agent 的认知负荷，它不需要死记硬背那么多东西，因为规则就在环境中。agent 一旦偏离就会撞上规则被拦回来，恰到好处地触发纠正。

    2500 个 PR 背后的内外循环

    主持人： 回到正题，我们还没聊到那 2500 个 PR 是怎么来的。既然你已经建立起了信任阶梯，打磨好了环境，也清楚自己想要扩大规模，那么这种规模化的具体运转机制是怎样的？你总不可能一个月手动发起 2500 次对话吧，这显然说不通。所以代码库里是有什么自动化触发器吗？你是如何让这套软件工厂实现自动化触发、自行运转的？

    Lauren Tan： 没错。我必须说明，支撑起如此高体量 PR 的绝对前提就是环境，也就是我们刚才讨论的那些。如果我之前没有花时间去构思后厨该怎么搭、为 agent 打造怎样的刀具和工具，我绝对不可能做到这一点。从某种意义上说，这就像是我投入时间建好了一间厨房、开好了一家样板餐厅，而现在我已经完全不需要时刻亲自守在现场了，因为环境本身就能维系运转，这个比喻非常贴切。

    主持人： 相当于你开了一家连锁餐厅，对吧？

    Lauren Tan： 一点没错。这就好比你是戈登·拉姆齐（Gordon Ramsay），把构思绝佳菜单的所有诀窍都传授给了行政主厨，后厨搭建得极其完善，一切井井有条。你现在完全有能力去开第二家、第三家分店。在我看来，我负责的每个项目、每个大的对话窗口就像是一家餐厅，我可以同时运作好几家，就像乘直升机一样在它们之间来回穿梭巡视，根据自己需要介入的程度决定在每家投入的精力。

    Lauren Tan： 不过，这些项目本身并不具备外部触发器和外部上下文，在很长一段时间里，我都是在充当「人肉中转」。最典型的例子是：某个项目正在开发特性或修复 bug，外部陆续收到了问题反馈，但这些反馈都散落在 Slack、Linear 或 X 这类平台上，它们与内循环是脱节的。我喜欢用外循环（outer loop）和内循环（inner loop）来解释——我不确定自己的定义是否完全标准，但对我来说，内循环就是 agent 工程师在代码库里写代码，朝着我意图的某个快照去实现。然而这个意图快照是会过期的，一旦出现新情况，我就必须充当中转媒介，把这些上下文同步给 agent。

    Lauren Tan： 如果你没有自动化触发机制把信息拉回内循环，你就必须亲自去扮演那个角色——整天泡在 Slack 或 X 上收集上下文，梳理 bug 报告、功能请求，或是别人提到后端基础设施的某种限制，然后一点点把所有这些信息人肉搬运给 agent。这也是为什么我认为像 Grok Bot 这样的工具极其出色，因为它们能帮你把外循环也实现自动化。当把这两个循环真正打通时，威力是极其惊人的，因为 agent 突然之间具备了自行获取上下文的能力。

    Lauren Tan： 举个简单的例子，比如你接入了 Slack MCP，或者在自己的运行框架（harness）里为某个特定的 Slack 频道配置了订阅。这样一来，你就可以直接吩咐 agent：去订阅这个 Slack 频道，一旦出现 bug 报告，就立刻去分流排查，利用我们之前花时间打造的验证技能（verification skills）以及其他各项技能去复现问题。正因如此，我对它们有了极高的信任度。

    Lauren Tan： 我很信任这些 agent，它们能够自主理解 bug，验证该 bug 是否确实仍在 main 分支上存在，同时排除用户配置、数据问题或漏装依赖等情况。在当下，建立这样的两个闭环并将它们连接起来至关重要，特别是当你思考如何成倍扩展自身生产力的时候。

    Lauren Tan： 这里的核心主题，是始终审视自己究竟在哪个环节成为了流程的瓶颈：为什么 agent 需要我来解答这个问题？我一直在琢磨如何让 agent 依托真实数据自行找到答案，避免依赖幻觉或猜测。很多人热衷于谈论“公司大脑”或“上下文图谱”这类概念，但在我看来，这些说法被包装得过于复杂甚至抽象了。对我而言，事情很简单：如何把 agent 需要、原本得由我手动传递的信息，转化为直接教会它如何自行获取。一旦做到这一点，我就彻底从流程中解脱出来了。

    Lauren Tan： 我能产出两千甚至更多 PR，关键就在于搭建好了这些闭环。这就像开连锁餐厅一样，让我能够实现真正的并行化运作。我当然不可能自己守在屏幕前开 2500 个聊天窗口。Cursor 最近推出了名为 Projects 的新功能，它包含被称为协调 agent（coordinator agents）的机制。这种协调 agent 非常擅长分派任务，本身并不亲自干活，而是管理并监督任务清单，再调度下属 agent 去执行。我只需要源源不断地提供上下文，或者教会它们如何自行获取上下文，它们就能自主替我推进工作。

    Lauren Tan： 最后我想补充的是，我能实现 2000 个 PR 的最大突破，其实来自于逆向推导这样一个问题：怎样才能让 agent 达到能够自主合并代码的程度？因为每当我告诉别人自己上个月提交了 2500 个 pull request 时，大家最直接的反应通常是：“你怎么审得过来的？要审那么多 PR，你的团队肯定恨死你了吧。”

    协调者、例程与代码维护

    主持人： 我们可以稍后再深入聊代码审查这个话题吗？因为……

    Lauren Tan： 当然可以，完全没问题。

    主持人： 我很喜欢你刚才那个开连锁餐厅的比喻，想顺着它再往深探讨一下。以前如果你手动去开启那些对话，就相当于亲自把点单送到每位厨师手里；而现在如果有 agent 负责统筹传菜，后厨自己就能运转起来。这在具体操作中到底是什么样的？你通过 Grok Bot 订阅频道并抓取 Slack 消息，听起来还配备了几个类似幕僚长的协调 agent 来负责监控。当你坐在电脑前管理这些 agent 时，眼前的实际工作流是怎样的？

    Lauren Tan： 目前这套机制理解起来可能略显复杂，我们正在努力做简化与统一。但我大体上把这类工具视作外层闭环（outer loop）——当然除了 Grok Bot，你也可以选用其他工具。它们是具备连接器属性的工具，许多人称之为个人 agent。它们能对接你的邮件、日历、Slack、Plaid 等各类服务，是向工作中拉取上下文的绝佳来源。

    Lauren Tan： 这就像人类团队的管理方式一样。我以前在 Netflix 工作时，管理者最常挂在嘴边的理念就是“提供上下文，而非实施控制”（context, not control）。有趣的是，这个原则在 agent 世界里同样非常契合。你固然可以通过事无巨细地严密盯防来达到预期结果，但更理想的路径是提供充分的上下文，教会 agent 和工程师自立自强，这样你就不必事无巨细地插手了。这两者之间有着极大的相似性。

    Lauren Tan： 具体来说，我设定了一些 Grok Bot 来持续监控我的 Slack 频道、X、邮件或 Linear。它们通过预设的例行订阅保持实时观察，例如我会指示它留意 Grok Bot 桌面端的 Bug 反馈。一旦抓取到问题，它就会将其转派给我的 Cursor 项目。正如我前面提到的，Cursor 的 Projects 功能会在云端运行一个拥有独立运行环境的协调 agent。它本身不直接写代码，而是扮演总厨或幕僚长的角色，专门负责编排、委派下属子 agent 的工作，向它们传递上下文并推动执行。

    Lauren Tan： 如果你突然收到一波密集的问题——比如一批载荷里一下子涌进来 30 个问题，协调 agent 就会自行研判。它可以组织起多种不同的 agent 拓扑架构，派出子 agent，找到最高效的任务分配方式。因此我重度依赖 Cursor Projects 和 Grok Bot：Projects 是我的内层闭环，Grok Bot 则是外层闭环。Grok Bot 负责抓取全部外部上下文并直接发送给 Projects，我甚至都不用打开 Cursor，只需让 Grok Bot 为这一组相关联的任务创建一个项目即可。

    Lauren Tan： 比如你突然收到大量关于性能变慢的反馈，这些问题彼此关联，甚至可能适用同一种修复方案。如果简单地为一个任务派生一个 agent，你就会丢失问题之间的关联脉络，不仅可能导致重复劳动，也无法站在更高维度审视问题。在排查 bug 时，对比多份略有差异的报告往往大有裨益，因为这能帮你跳出局部细节看清全貌——单看一份报告时你以为问题出在 A 点，但汇总综合多份报告后，才发现根本症结其实在更高层的 B 点。

    主持人： 明白了，所以你在闭环中引入这种架构，是为了避免每来一个 bug 报告就单开一个 agent，导致多个 agent 针对同一类问题做重复劳动。由真实用户提交的真实反馈构成了源源不断的触发源，如同为这座代码工厂不断注入新订单。那么除了 bug 报告之外，你还有哪些来源用于驱动和加速这数千个 PR 的产出？

    Lauren Tan： 说来有趣，其实有一部分来源正是阅读代码本身。需要澄清的是，这 2500 个 PR 显然不等于 2500 个新功能。其中大量工作实际上是在做持续维护整理（gardening），这是我非常喜欢的一个概念。当你与一个庞大的人类工程师团队协作时，这一点尤为关键；同时这也回到了我们之前聊到的环境搭建——构建一个良好的开发环境，受益的不仅是你和你的 agent，还有团队里的每一个人。

    Lauren Tan： 良好的环境不仅能帮到你和你的 agent，还能让团队里的每一个人受益。试想一下刚入职的新员工，他们对团队的所有工程实践都缺乏上下文背景；但如果有一个足够好的环境，他们从第一天起就能高效产出，不需要去提一堆低质量 PR，而是直接开始持续产出真正优质的代码。……抱歉，我好像有点跑题了。

    Lauren Tan： 我也确实有一些类似的 routine。举个简单的例子，大家都知道 React 有很多容易踩的坑，所以我设了一个 agent 持续排查不良模式。但有趣的是，我不会让它立刻去修，而是让它把问题先追加记录到一个文档中。每隔几天我去看一眼，往往会发现“其实这些都是同一类问题”。比起直接派生出大量子 agent 去修复每一个琐碎问题，这种缓冲队列的方式有时候更有效。

    Lauren Tan： 因为当你处于纯粹的执行模式、忙于应付快速涌入的指令时，往往会看不清全局。设置缓冲能迫使你去思考全局，通过这些沉淀下来的文档记录，你可以借助人类的判断力——当然也可以交给 agent——去识别那些单打独斗逐个修 bug 时容易遗漏的共性模式。这正是“幕僚长 agent（chief of staff agent）”的优势所在：它不仅能负责具体执行，更能见树又见林，纵观全局。

    抽样审查、自动合并与适用边界

    主持人： 太精彩了，在软件工厂里引入幕僚长 agent 的思路让我大受震撼，我甚至可能得改一改下周要录制的课程内容了。那我们来谈谈代码审查（review）吧，这也是外界常有的质疑：流水线上滑过的这 2500 道菜，你每一道都亲自品尝了吗？我猜你的回答在某种程度上是否定的。

    Lauren Tan： 你肯定不想落到完全不再品尝食物的境地；但为了规模化，你也不可能尝遍厨房端出的每一道菜，尤其是在拥有多家餐厅的情况下。所以核心在于“抽样（sampling）”，并在流程机制上下功夫。如果用工厂来打比方可能更贴切：作为工厂质检主管，你不可能检查每件出厂产品，只能进行抽检。你每天都要严格审视 PR 的质量和 agent 写的代码，找出其中的低效和不良模式，然后思考如何对“环境”进行纠偏，避免单抓某一个 agent。

    Lauren Tan： 如果只是偶发事件倒无所谓，可能根本不需要专门去修；但如果你注意到多个 agent 都出现同类问题、走相同的捷径、在各处散播同一种临时变通方案，这就表明你该去改造你的“厨房”或“工厂”了——比如重新审视并调整你的 skills、约束、lint 规则和类型系统，杜绝该问题再次发生。当你反复打磨之后，代码库环境的约束就会足够严密、引导足够清晰，你就可以放心地抽身走开——这正是终极理想。

    Lauren Tan： 但我必须说明，要做到这一步其实非常困难。我不想把它吹嘘成只要用上 pstack 就能轻松搞定的事；你必须投入大量时间和心血去思考代码，观察 agent 在哪些地方容易失败，深思熟虑地设立护栏和约束，让它们默认就能把事情做对。

    主持人： 回到软件工厂的比喻，这不算黑灯工厂吧，灯还亮着？

    Lauren Tan： 其实有点算。

    主持人： 是吗？

    Lauren Tan： 说它算黑灯，是因为如果我的 agent 在自行合入 PR，那它确实有点变成黑灯工厂了——我去睡觉，而 agent 在 7×24 小时工作。我现在拥有相当于 10 多个幕僚长（chief of staff）agent，各自负责不同的领域。比如有一个在优化 Grok Bot 桌面应用的性能，有一个在修复用户反馈的 bug，还有一个纯粹出于好玩在探索用其他语言重写原生版本。花精力建好环境后，我现在已经达到了可以在 PR 合入之后再去复查的程度。

    Lauren Tan： 在 pstack 里你可以开启全自动驾驶（full autopilot），这会触发一套极其严密的验证闭环：针对每个 PR 派生出一批验证 agent 进行模糊测试（fuzzing）。这里的模糊测试是指它会实际运行应用，像真人一样在界面上点击操作，排查实现中的回归和 bug。发现问题后它会自行修复并再次验证，直到 PR 达到能够合入的状态。

    Lauren Tan： 这种机制确实非常消耗 token，当然你也可以调节，比如不用 10 个验证 agent，改成只用 1 个，或者让 agent 验证自己的工作。但关键在于，验证环节与环境的结合，给了我足够的信心放手让 agent 自行合入。我第二天早上通过查看提交历史来复查，如果发现问题再去纠偏、回滚或者补充新的 lint 规则。要走到这一步确实需要时间，但一旦做到了，感觉真的很神奇。我跟别人说我现在睡得好多了，因为第一天开启这种黑灯模式时其实非常害怕，生怕夜里搞出线上事故，确实需要很大的勇气。但现在，我的 agent 已经完全可以在我睡觉时自行合入代码了。

    主持人： 从这个角度来说确实算黑灯。因为在我看来，黑灯工厂更接近 Karpathy 最初对 vibe coding 的定义：代码几乎不存在，你甚至忘记了代码的存在。但我认为你的方法与此完全不同——代码和环境是至关重要的；如果代码和环境很差，那你得到的就会是劣质产出，垃圾进、垃圾出。

    Lauren Tan： 我明白你的意思。是的，我觉得这是两码事。这更像是有个调光开关（dimmer switch），有些地方暗，有些地方亮。这也是为什么餐厅可能是一个更贴切的比喻——即使作为餐厅老板，你依然会时不时到各个分店看一眼、尝尝菜品的味道，对吧？

    Lauren Tan： 我认为，用抽样检查来代替直接卡关，这个思路确实非常重要。

    主持人： 那你对那些在特定行业工作的人有什么建议？你显然处在一个对安全性要求极高的工作环境，但可能有些人在医疗、法律或金融等领域工作。有些 PR 属于“双向门”，合入之后随时可以回滚撤销；但也有些 PR 是“单向门”，可能会导致数据丢失或造成难以轻易挽回的后果。如果一个团队的大多数 PR 都是这种“单向门”，该如何应对？这种情况下你是不推荐这种自动化合入，还是有其他看法？

    Lauren Tan： 我觉得这是个极好的问题。归根结底，核心在于你能从 agent 那里获得多高水平的验证质量。在工作本身可验证的领域，这会容易得多，单向门在某种意义上也就变成了双向门。但如果你所做的工作极难通过程序来自动化验证，那确实很难做到这一步。因此，领域的可验证性是实现这种工作流的关键前提；而软件工程在很多情况下恰好是高度可验证的，尽管可能无法做到绝对完全的验证。

    Lauren Tan： 像数学等领域也是如此，虽然不是全部，但如果你写出形式化证明，某些部分是完全可验证的。所以这确实是个好问题，我目前也没有确切答案，需要整个行业和我们工程师共同探索。我对未来的期许和预测是，会出现越来越多面向 agent 的新编程语言。目前我见过最引人注目的就是 Bend（B-E-N-D），它把编程与形式化证明融合在了一起。过去你必须用不同的语言来写证明——给不熟悉的人解释一下，证明就是通过数学手段形式化验证代码的正确性，尤其适用于函数式编程；此前很长一段时间，你都必须借助 Lean、TLA+ 这类独立语言构建数学证明，再通过求解器检查是否覆盖了所有情况、是否存在竞态条件等。

    Lauren Tan： 回到最初的问题：如果你能找到让 agent 真正验证工作成果、并给你足够信心的方法，你确实可以直接合入 PR。因为如果代码能编译通过，形式化证明也显示它是正确的，为什么不直接合入呢？当然，并不是所有领域都具备可验证性，这确实是个难题。
