    数学的美与计算模型的边界

    原片 00:00:00–00:08:00

    今天继续讲 DeepSeek Harness。上次从代码结构看了它的插件设计、Event Bus，以及怎样通过许愿扩展插件，今天继续深入。不过，最近“震惊瘫坐”的频率又变高了。

    今天早上看到消息，OpenAI 声称找到了一个挑战 Exponential Time Hypothesis（指数时间假设）的算法。原来认为，一些 3-SAT 问题有一个难以突破的指数时间界线，它说把这条界线往下压了一点。它并没有找到多项式时间算法；如果找到了，那就意味着 P = NP，影响会大得多。这个结果，以及同期其他一些结果，颠覆了不少人的直觉。

    这让我想到，我们上数学、理论计算机课时追求数学的美：用一个很小的内核推导出许多结论。它确实美，但这种美也可能带有人的认知局限。以 P 与 NP 为例，保研面试时老师可能会问：NP 中的 N 是什么？它指 non-deterministic，也就是非确定性图灵机。接着就可以问：为什么用 P 来刻画“可以有效计算”？

    图 1：00:00:40，课堂展示的指数时间假设论文。

    为什么多项式时间就算有效计算，NP-complete 就被当作困难问题？中间还有没有别的情形？n 的 100 次方也属于多项式时间，可 n 取 10 时，这个算法在现实计算机上就没有实用意义了。n² 和 n¹⁰⁰ 都属于 P，这种划分抹去了很大的实际差别。

    选择多项式时间，有一个数学上的好处：它对复合封闭。一个多项式时间程序可以调用另一个多项式时间程序。外层程序在多项式时间内，至多生成多项式长度的输入；内层程序再对这个输入做平方、立方或更高次的多项式运算，组合起来仍然是多项式时间。

    这样就可以自由使用已有算法库，只要调用次数和外围计算仍在多项式时间内，整体就留在 P 中。这种封闭性简化了数学推导，也带来美感。不过，从另一个角度看，这也像一种 workaround：人脑能同时容纳的抽象有限，我们用这种方式弥补理解能力的限制。

    当我们问“有些问题是否必须花 2ⁿ 的时间才能解决”时，往往并不知道算法里还有什么技巧，可以继续压低复杂度。前几年出现的近似线性时间网络流算法，就让人意外。网络中任意两个节点都可能相关，却仍能在近似线性时间里求出结果。这说明，我们对数学问题结构的理解还有很大缺口。

    如果问理论计算机科学究竟想了解什么，可以先给定一个计算模型，例如 RAM model。它和真实计算机仍有差异——真实计算机有 memory hierarchy——但我们可以定义一个 CPU，规定 load、store、加法、乘法等指令，每次从 RAM 读写花一个周期。这台计算机可以被形式化；我希望大家学完离散数学后，能写出这样的数学定义。

    随后问一个明确的问题：允许这台计算机运行 k steps，它能解决的所有问题是什么？换个方向说，我们造出一台计算机，想知道它能做什么、不能做什么。而研究算法时使用的多项式时间分类，只是一个很粗的近似，许多细节被抹平了。

    在限制为 k 步的模型里，每条指令都要精打细算。数据怎样放在内存中，怎样排布，要不要压缩，都会影响结果。内存地址本身也许没有影响，但组织方式会影响步数。多项式时间的分类宽松得多，调用别的多项式时间函数，仿佛不必关心具体增加多少代价。

    人类长期习惯研究比较干净的问题。生物分类就是一个例子：界、门、纲、目、科、属、种，人类花了很长时间构建物种的 family tree，这些工作代表了文明的积累。但现代生物学也对简单的树状模型提出了挑战。猫和狗在宏观上很好区分；到了微观生物，边界可能模糊得多。两个对象是否来自同一个祖先，有时甚至更适合用 graph 表达。我并非这个领域的专家，只是借它说明：现实世界的结构未必像我们使用的模型那样整齐。

    还有一种可能：物理世界整体很复杂，我们恰好处在一个比较“平坦”的区域。在某个宏观尺度上，规律比较稳定，于是经验可以被压缩。

    教育投资、就业与 AI trajectory

    原片 00:08:00–00:18:00

    昨天我和 GPT 聊过对称性与能量守恒：假定物理规律在某种变换下保持一致，就能推出相应的守恒量。更准确地说，是得到一个守恒量；在相应情形下，我们把它叫作能量。假如世界整体结构很差，而我们恰好生活在有这些规律的区域，经验才可以被压缩，压缩又可能产生智能。也许正因为处在这样的区域，scaling 才能带来今天看到的结果。这些只是 AI 引发的一些大胆想法，今天不继续展开。

    最近看过我小红书的同学，可能看到过一些“暴论”。我想解释一下它们背后的担忧。过去，家庭投资教育，学生在中学努力学习、考大学，大学培养人才，企业再购买毕业生的劳动力，这样形成了一个循环。

    现在，这个循环越来越难维持。如果一个 senior 带着 Agent，能超过一个 junior，企业为了竞争，可能先巩固自己的优势，暂时不招应届生，把培养新人的问题交给后来的人。这意味着大家毕业时会面临很大的职场压力。

    图 3：00:08:00，宏观规律与“平坦”区域的设想。

    图 4：00:08:55，压缩、预测与智能：观察者的猜想。

    图 5：00:10:00，AI 对教育与就业循环的影响。

    企业可能会问：既然可以使用 Agent，为什么还要花很长时间培养新人？我知道大家对此焦虑，有一个可以尝试的方向：用自己的 AI trajectory 证明自己。

    从现在开始，把与 AI 共同工作的记录保存下来。可以压缩记录，去掉没有必要的 tool call 输出，保留有价值的图片、代码及其他 assets，形成属于自己的时间轴。现在，大家做很多事都会问 AI，连今天吃什么、附近有没有新店都可以问。我上周去 CNCC，到了另一座城市想出去走走，也会把位置、偏好和想找的东西告诉 ChatGPT，让它尽可能全面地搜索，再给出选项。

    这样的记录首先提供可审计的事实：今天聊物理，明天聊天文，自己的想法是什么，AI 给了什么，自己又怎样反馈；最后生成的代码能不能运行，哪些想法来自自己，哪些来自 AI。任何评价方法都可能遇到应对办法，但不可变的日志会让用人单位更容易审查。例如，面试官可以随机挑出 2026 年 3 月 10 日的一次讨论。

    面试官可以问：还记得当时讨论的内容吗？用今天的眼光，怎样看那次对话？只要随机抽样，就很难临时伪装。能够解释当时的想法、回应相关细节，通常说明确实参与过。即便伪造了整份记录，进入面试后也容易暴露。

    这份不可变记录还可能反映成长潜力。两个人高考总分相同，科目和题目的得分分布未必相同；进入南京大学时起点相近，之后的发展也可能不同。有的人入学就是能力高点，以后很少再学进东西；有的人持续成长，不断发现新的模式和方法。

    比如，在某个时间点发现了更好的 AI 沟通方式，把一个 skill 沉淀到 harness 里，此后做事的方法发生了变化。记录里可能看得出方法论乃至人生观的变化。学生的学习内容通常是人类已有知识，也未必涉及商业机密；在自己愿意的前提下，把学习历程提供给用人单位，对方就能更全面地评估能力与潜力。但这同时提出了隐私问题：身体暴露所损失的隐私，与这些记录所暴露的内心，可能还不是同一种程度。

    图 6：00:13:20，用 AI trajectory 证明自己，以及成长曲线板书。

    AI trajectory 可能让别人窥见内心、判断潜力，甚至预测未来的行为。这令人不安，却又很有吸引力：把它保存下来，再适当地投影成简历，短期内可能得到回报。有时像是在与魔鬼订立契约。如果把所有 ChatGPT 对话都交出来，我会觉得连自己的灵魂都交出去了；当生活中的大量事情都交给 AI，它就可能对自己在这个世界上的位置了解得很清楚。

    再往后想，交朋友是否还需要先见面、花很长时间聊天？我经常和来找我的同学聊 AI、Agent OS，聊着聊着，观点逐渐收敛，发现彼此想法相近；有时经过分歧，最后取得一致。

    当双方都有 trajectory 时，也许可以先派各自的 Agent 交流，很快列出观点一致和不一致的地方，再由人围绕分歧继续讨论。

    讨论以后，Agent 又能继续补充。我现在思考问题时，会把 AI Agent 当作一个能够调用大量领域知识的对象：我提出想法，它补充细节，指出哪些部分别人已经想过、相关论文是什么，哪里考虑不周，哪里可能尚未被探索。这样扩充知识的速度会变快。至于某一天会不会突然出现灾难性的后果，那是另一个问题。

    这些能力也可能催生颠覆性的产品。比如，当 personality 已经编码在 AI trajectory 里，也许可以拿来匹配朋友，甚至让 OpenAI 分配对象——这当然是个玩笑。

    我一方面觉得这种世界可怕，另一方面又难以抵御它的吸引力：AI 在了解我的内心，也不断给我反馈和帮助，使我可能在竞争中获得优势。给大家的一点实际建议是，可以先保留这些记录，尽量控制分享范围；然后用合适的 skill，把 trajectory 提炼成简历或个人网站。

    未来投资与 Agent 生态

    原片 00:18:00–00:24:00

    这样的简历或网站，也许能让用人单位眼前一亮，带来一个好 offer。等大家都想到这件事，它又可能变成普遍做法，进入新的竞争，大家开始 reward hack 评价过程。如果较早意识到它，竞争者还没有大量涌入，就有机会少做一些迎合，多追随自己的兴趣。

    上学像是对未来的一次投资：投入青春，期待毕业后得到回报。再激进地设想，未来会不会出现“贷款上班”？先承诺自己能超过 AI，缴纳保证金，在 mentor 的带领下工作；如果确实创造价值，就得到回报，如果始终没有成长，保证金就不退。这样的情形未必不会出现。

    我们也许会走到类似核不扩散条约的讨论：AI 能力是否应停止增长？Anthropic 和 OpenAI 都在讨论相关问题，但目前看不到明显缓和的趋势。以上是今天看到新闻后临时加入的思考，下面回到 DeepSeek Harness。

    上次说它像一个操作系统，everything is a plugin。这样的设计意味着内核本身不携带具体应用功能。操作系统提供的也是基础 API，例如创建进程的 spawn 或 fork，以及管理系统对象的接口。

    图 7：00:18:40，上学、未来投资与就业的讨论。

    操作系统用 handle 或文件描述符引用对象，通过文件描述符 read、write，管理持久化数据。DeepSeek Harness 与此类似：它提供 Event Bus、原生插件，以及 Agent 交互方式，例如 agent.inject，也规定了怎样操作模型的上下文。

    用航母作比喻，航母已经造出来了，上面的飞机还在试验阶段。它暂时还没有确定应该搭载什么武器，也还没形成今天这种航母战斗群。我期待这个生态长大；最后成功的未必是 DeepSeek Harness，但围绕 Agent 形成的生态，会让使用它的人更方便。

    它似乎准备发布移动端应用。如果 PC 长期开机，手机与 PC 建立通道，PC 就能一直在后台工作，类似某些 Agent 产品的方式，只是使用自己的电脑。在中国，这可能是一个很有前景的模式。

    大家也可以回去许愿一个插件：基于 Agent trajectory 构建人物画像。既然 everything is a plugin，就可以监听插件行为、人与插件的交互、插件与上下文的交互，还可以持久化模型上下文，再把这些记录投影成有用的内容。

    例如做一个“实时简历”：每天自动更新，无须手工维护，再配上直观的界面。GitHub 的贡献墙就提供了一个参照：时间轴上的方格颜色越深，代表当天贡献越多；提交五次是深绿，两次可能是浅绿，什么也没做则是空白。当然，它也可以被伪造；我的贡献墙现在就很绿，因为很多 commit 是 AI 帮忙做的。实时简历可以借鉴这种呈现方式，但承载更丰富的活动记录。

    插件生态会像操作系统生态一样演化。Unix 诞生时，人们很难想到今天会把 cat 的输出通过管道交给 claude -p。过去可能把手册送给 pager 阅读，如今又出现新的组合。DeepSeek Harness 未必是最后留下的产品，商业公司的产品也可能胜出，但围绕基础平台形成生态，是值得期待的方向。

    航母是怎样造出来的

    原片 00:24:00–00:28:00

    2019 年，我去过 San Diego 的 USS Midway 博物馆。课件上这个观察航母的位置，我也拍过一张照片。中途岛号在 1945 年下水；按我的印象，它准备投入使用时二战已经结束，日本已经投降，不必再去太平洋战场作战。后来它服役了很长时间，按我印象，1970 年代经历过现代化改造，应该在 1992 年海湾战争时担任旗舰。

    走进航母后，最强烈的感受是震撼。我做软件，看到这样复杂的系统，也很难想象它是怎样构建出来的。它内部有大量管线：蒸汽、通信、电力都需要不同的线路。今天许多设备可以用电驱动，当时则有更多种介质和系统交织在一起。

    它还是一台战争机器，必须考虑损害管制，随时可能受到鱼雷或轰炸机攻击。博物馆里的志愿者中，有曾在舰上服役的老兵。我当时很好奇，就向其中一位请教：这样的系统究竟怎样设计和维护？

    图 9：00:24:00，USS Midway：从参观航母提出复杂系统问题。

    老兵当然未必知道整套系统是怎样设计的，但他知道出了故障该怎么办。他告诉我：设计由很有才华的工程师完成，舰员不必理解所有内部原理，每个人都会拿到操作手册，明确写着遇到什么情况、应该做什么。

    这和飞机的操作手册类似。玩过模拟飞行就知道，手册会规定各种程序；例如某处起火，要把几号阀门从什么状态改成什么状态。设计者推演了各种可能性，使航母能在战争中发挥作用。我也由此理解，尽管已经能造很多船，造航母仍然困难，因为它还必须应对战争中的破坏。

    但当天最有启发的，是甲板底层的一个陈列柜。那里展示了美国海军从第一艘航母到现代航母，一代代演化的过程。航母没有在第一天就变成今天的样子；把历史追溯到最早的起点，那个起点可能很简单。今天要讲的软件演化，也是这样的故事。后面再看 DeepSeek Harness，先看航母如何一步步走来。

    从帆船、汽船到飞行甲板

    原片 00:28:00–00:34:00

    从 1945 年的 USS Midway 往前追，古代文明已经有桨船和帆船。经过几千年积累，有了足够好的材料和航行经验，人类终于知道怎样造出可以长途航海的船。

    Santa Maria 原来是一艘商船，1492 年成为哥伦布首次远航发现新大陆的旗舰。看这种船，复杂度还比较容易理解：上面主要是机械装置，似乎在人能够驾驭的范围内。再往后，大家有没有看过《泰坦尼克号》？在我们那个年代，它是很热门的电影。

    比泰坦尼克号更早，1811 年的 New Orleans 汽船沿 Ohio River 和密西西比河航行，1812 年抵达新奥尔良。高压蒸汽推动的轮子露在船外，这也是“轮船”名称的直观来源。今天的船往往用水下的螺旋桨，表面已经看不到轮子。

    把这些放在一起，会发现它们平滑地演化。Everything is a state machine：不管是一艘船，还是一个代码仓库，都从 initial state 出发。

    图 13：00:28:40，1492 年 Santa Maria：风帆与长途航行。

    图 14：00:29:20，1811 年 New Orleans：蒸汽动力与明轮。

    受到人脑能力和物理实验条件的限制，人类每次通常只能增加一个小小的 delta。发现某个结构有用，就加上；发现没有用，就删掉。桨和帆曾长期并存，后来远航船上发现桨已经派不上用场，便把它去掉。轮子、螺旋桨和舵也可能有过并存阶段，最后才逐渐留下更合适的形式。

    航母以及其他复杂事物，都是这样一点点造出来的。汽船能够赚钱，人们就继续研究更好的汽船。从 1492 年到 1811 年，再到 1913 年，结构不断变化。

    接着由工程师推理、计算、做实验：跑道多大才够？飞机放在哪里？陆地机场可以在旁边建机库，船上空间有限，就要充分利用上下空间，把飞机放在中间的机库，把跑道放在上面的甲板。这样又需要电梯，把飞机从机库送到甲板。

    沿着历史理解复杂软件

    原片 00:38:00–00:44:00

    人的成长也有时间轴。Everything is a state machine。起初可能看不出变化，某一天忽然领悟一件事，随后能力持续提高。大家应该都有过这样的时刻，可能写过日记；再过三五年，记忆尘封，偶然想起来时，又重新感受到当时的启发。知识就在这个过程中积累。

    人、软件以及其他复杂事物，都有类似的成长过程。最早的想法往往很简单：看到一段木头，能不能挖掉一块，让我从河这边到那边？试一试，就有了船，然后继续发展。

    成功的软件通常也从一个实际问题出发。Linux 的想法可以简单地表述为：做一个免费的 Unix 克隆，供大家使用，先实现 Unix 的功能。如果这个想法确实解决现实问题，方向合适，就能通过持续改进逐渐发展起来。

    图 23：00:38:40，软件的时间维度与演化过程板书。

    AI 可以一下跨出很远，也会给出架构。但随着软件维护、修改次数增加，系统可能越来越难改；essential complexity 增长之后，就会发现最初的架构可能不合适。大家用 AI 编程时，应该有过这样的体验。

    人类软件史中，一些架构经受住了时间考验，同时也有许多部分被重构。就像今天仍叫“轮船”，却已经没有过去露在外面的轮子。理解软件，不能漏掉时间维度。

    为什么计算机专业要学习基础课？一个重要原因，是了解软件系统早期的设计，以及它们怎样随时间演化。课件里 AI 给出的调度器、Python、Kubernetes 等例子，我觉得都没有航母那么贴近我想表达的意思。AI 还未必能准确体会这种表达意图。

    在早期模型里想清楚，再向后 rebase

    原片 00:44:00–00:50:00

    有些数学课按“定义、定理、证明”的顺序，把最终结果直接交给学生，却不展示人类走过多少弯路、经历多少失败，才找到这条路线。这样的学习方式，对人的理解并不友好。

    回到早期 Linux，系统调用 read 就容易理解了：进入内核，像函数调用那样执行几步操作，再返回，和 xv6 类似。我大约从 Linux 2.6 进入这个领域；今天 Linux 已经复杂得多，但理解问题时，仍会先问：在 Linux 2.6 里会怎样做？这样做有什么优点、缺点，今天又该怎样改？很多问题甚至可以退回 Linux 0.11 的模型来思考。

    例如，应用程序想向操作系统获取一些信息，是否每次都必须跨过系统调用边界？能不能让内核和应用程序共享一个页面，应用程序只读它？页面里可以放 CPU ID、当前时间等。内核每秒更新一次时间；进程创建或切换 CPU 时，再更新对应信息。用户进程直接读取这个共享页面，就能获得这些数据。这个思路在 Linux 0.11 的简化模型里就可以想清楚。

    接着再把这个 feature 带到现代系统。可以用 Git rebase 作比喻：先在自己理解的早期版本里实现功能，再把这个 commit 沿历史不断向后移动。

    历史中增加了一个调度算法，会不会影响这个功能？没有影响，就继续向后走。会发现多数新增内容与它无关。一个可维护的软件，不会让所有部分都搅在一起；好的架构把复杂度分配到不同部分，虽然 essential complexity 仍然带来交互，但一个新 feature 与系统大部分内容的耦合通常较松。

    真正需要理解的，是几个关键 commit：自己的功能在这里与谁发生冲突，最简单的模型为什么不再够用，又怎样解决冲突。这与数学史类似，人类走了很多弯路，后来发现某些东西应该放在一起理解，才形成群论等理论。

    这也帮助解释了为什么在大模型普及前，程序员会谈“三大浪漫”。

    图 26：00:47:20，通过早期模型和 rebase 理解功能变化。

    传统说法是自己做一个操作系统、一个编译器、一个数据库，也有人会加上 CPU。今天投 AI infra 的同学，简历上常写的是修改 NanoGPT、nano-vLLM，把它迁到多卡，或者用几块树莓派、RK3588 之类带 NPU 或其他加速器的小板，做并行推理加速，再接入自己改过的 nano-vLLM。

    这些事情有意义，值得动手做。但大家可能没意识到，它们与造航母、学习复杂系统可以用同一个 Git 模型理解：先掌握较小的状态，再理解变化。

    如果直接面对今天的航母、软件或 DeepSeek Harness，新手会感到无穷的复杂性。通过发展历史，把自己关心的 feature 一步步 rebase 过来，就有机会理解它。演化既反映人类能力的限制，也提供了一种学习复杂事物的方法。

    软件演化于是成为研究对象，Git history 是一座宝藏。有了计算机，我们才可以从 initial state 开始，完整保存人类创造软件的过程；类似的创造过程，在人类历史中早已存在。

    SWE-bench 为什么重要

    原片 00:50:00–00:56:00

    到了 AI 时代，如果还要发挥人类的创造力，能不能做更大的事？例如构建数学发展史的 Git tree，或者整理造船、航母的历史脉络，把知识历史中的分支及其相互影响呈现出来。Git 这个比喻并不完全准确，但它能提醒我们关注不同路线之间的关系。我不知道 OpenAI 或 Anthropic 是否正在做类似的事情。

    回到软件工程，前面的故事带来一个基本假设：无论历史是否线性，系统由一系列提交组成，每个提交通常是一个小任务。绝大多数 commit 处理 bug fix、小的 feature request 之类事情。

    那么，AI 能不能把这些小任务做好？SWE-bench 是这类工作里知名度很高的一个，后来也出现了 Pro 等版本，以及 Terminal-Bench 等基准。它们衡量模型处理软件工程任务的能力。对 SWE-bench，我更关心它在这段演化史中的位置。

    图 27：00:50:40，SWE-bench：真实 GitHub issue 的小任务评估。

    SWE-bench 问的是：大模型能不能做好一件小事？最早的时候，答案显然还不乐观。这篇工作大约来自 2023 年、GPT-4 的时代。看它的例子，输入仍是 model input，还没有今天成熟的 Agentic workflow。虽然已经有 Agent 的想法，也有人担心模型是否会逃脱控制，GPT-4 的幻觉仍很严重。

    任务包含 issue、golden patch、模型生成的 patch，以及一组测试用例。测试并不完美，我们仔细研究过 SWE-bench。有些 bug 来自更早的设计缺陷，不断修补只是维持现状；如果由我处理，可能更愿意重构代码。

    不过，它确实给出了明确任务和反馈信号，可以评估这件事是否完成。看历史结果，Claude 2、Claude 3 Opus 当时还不像今天这样受关注。OpenAI 很强势，Claude 更多强调自己在某些专业、垂直领域的优势。

    图 28：00:52:40，SWE-bench 的 issue、生成 patch 与测试示例。

    表里 Claude 3 Opus 的 resolved rate 只有 3.79%。当时的结论可以说是“还做不好”，但它指出了一个方向。

    现在每年有大量 benchmark 论文，有些同学也可能在课题组做基准研究。评估它们，不能只看测试本身，还要问：从人类工程活动来看，这个小任务值多少？如果软件演化的大部分步骤都是小事，能够把这些小事做好，就意味着已经走通演化路线中的很大一部分。

    从 GitHub 随机取 issue，常见的是程序崩溃需要修复，或者日期格式、日期计算不准确，需要考虑闰秒、增加星期显示，做一个小功能改进。日常开发中，大量工作就是这些。

    SWE-bench 代表了这种工作。如果有一天它被很好地解决，工程中大量琐碎任务也会被自动化。这隐含着对初级工程师工作的冲击，也预示了今天大家面对的焦虑。

    小任务之外：架构与 Taste

    原片 00:56:00–01:04:00

    接着还可以问：SWE-bench 没覆盖什么？首先是 initial state。决定造一艘怎样的“航母”、建立 repo、写下初始计划，这种工作很难用同样方式评估。

    还有架构上的问题。我们见过一些任务，代码逻辑复杂，是因为两个模块在设计时没有分开，写一处代码必须同时携带两边的状态。为了评价自己的方法，我们曾把整个模块重构，重构完成后，原来的 bug 直接消失，那个 issue 根本不再需要单独修复。

    当琐碎 bug fix 积累太多，维护者可能终于受不了，决定重构。重构意味着架构发生变化，可能是局部的，也可能涉及整个系统。顶层架构往往很难改，因为影响范围很大。

    图 30：00:56:40，从规范能力到 Taste 的评估问题。

    比如，前段时间 Claude 把 Bun 从 Zig 迁移到 Rust 的事情，让我很惊讶：这样做可以吗，会不会留下严重 bug？当时看起来并没有出现预想中的后果，当然也与项目结构有关；若迁移的是 MySQL 这种项目，我会更谨慎。

    架构有不同尺度：顶层系统架构、子系统架构，甚至函数内部采用 functional code 还是 imperative code，也可以看作很小的结构选择。达到子系统尺度时，什么时候应该改、怎样算改得好，都很难简单判断。

    这类任务在人类历史里就相对稀少，模型难以依靠大量样本和反馈学习。人类却是很好的 few-shot learner：我在 San Diego 看到航母，联想到软件，展开一长串推理，认知就发生了变化。

    模型能否也从一个或几个案例里产生这样的变化？不只是像做数学题那样，在三角函数、列方程、数形结合之间选择一个更有利的 next token，而是从案例中重新组织自己的理解。

    它能不能因为一个案例，调整一大片已有认识，学到案例真正表达的内容：为什么这个软件在某个时间点决定做一件事，而且做对了？为什么 Linux 的 USB subsystem 到 4.0，或者说 3.4 左右，会让大家觉得难以维护，必须整体重构？起初设备种类少，看起来不重要，后来却到了非改不可的阶段。这里提到的具体版本，我是凭记忆举例。

    我们现在可能需要一个足够好的 Taste Bench。无论数学、造船还是软件，演化都由大量小事和少量大事组成。小任务已经有了比较明确的评估，大事则需要从 yes/no 或单一分数，转向多维度评价。

    SWE-bench 用测试用例判定任务完成与否，模型原则上不应看到这些测试。为了刷分，也可能出现间接泄漏：不直接把测试交给模型，而是让训练或方法带上适合这类任务的倾向，例如看到 SWE-bench 式任务，就特别积极地自己写测试，结果分数更高。无论如何，这类评估最终仍主要回答：小任务做完了没有，修改对不对。

    大任务的强化学习反馈稀疏得多。回头看，Linux 当时作出的决定也未必就是最好的，后来还会出现新经验。重构通常有多个可选方案：采用 Event Sourcing？连底层架构一起换？给数据库增加缓存？还是通过 scale 解决性能问题？不同选择未必能排出一个统一的优劣顺序。

    可以像考试一样，把多张卷子的分数相加。但科目、题目反映的是不同能力，一个人的能力画像更像 vector。设想一个 Human-to-Vector，根据 AI trajectory 描绘一个人；总分最高的人，也未必最适合某个具体项目。

    真实项目的 trade-off 有时无法同时消除。大幅改成 Event Sourcing，重构成本和引入风险会增加；想降低风险，改动幅度就要缓一些，工期可能拉长，一次重构也可能到不了目标。面对十几个目标时，往往必须作出取舍。

    从 RFC 到 ADR：设计决策有来由

    原片 01:12:00–01:16:00

    RFC 是 Request for Comments，名字带有征求意见的意思。Internet Protocol 以及各种网络协议都有 RFC。在项目内部，也可以用类似形式提出设计草案。

    例如，要不要放弃 TUI？Event Bus 应该怎么设计？这些都是可能出错的架构决定，先提出 RFC，再由团队讨论。我们做项目时，也会把设计放到飞书共享文档，先批注，需要的时候再开会。

    现在开发原型便宜得多，有一个想法，可以另开分支，先 vibe 一个 MVP 看效果。实验结束后，丢掉原型，再回头逐步实现。讨论确定后，形成 ADR，即 Architecture Decision Record。

    现场让 Agent 找一个从 RFC 到 ADR 的具体例子，看看这段历史里有什么。

    图 37：01:12:40，让 Agent 查找 RFC 到 ADR 的设计实例。

    它找到了一个架构问题：System Prompt 原来存在 request header 中，其他消息存在 surface 事件里。一开始这样实现似乎可以，后来有了新需求：支持在对话中途替换 prompt 的模型，需要向历史追加一条 system role 消息。原来的 header 设计就难以自然支持，需要改用统一抽象。

    这种变化比给航母增加飞行甲板小一些，但对于模型上下文的设计仍很重要。最初先讨论，不改代码；到了 9 月 5 日，把方案提升为 ADR，再进入实现，最后标为 implemented。我猜那时项目可能已经在内测。

    这个过程本身也是状态机：对不确定、需要较长时间推进的任务，保存其讨论和实施状态，Agent 的工作也能沿着这些状态继续。

    协作、验收与人类驾驭

    原片 01:16:00–01:20:00

    这些设计记录都在 Git repository 中。再看协作边界，现在有多少提交？以前我们可能自己写脚本，琢磨 grep 什么、怎样用 word count 统计；现在直接交给 Agent 就能得到答案。当然，过去那些操作也提供了编程练习，我常说，打开 Unix shell 时就已经在编程。

    现场查到大约 22,000 个提交。每个小提交之外，还有团队自己的协作模型。我们现在团队小，用 linear history，不保留 merge commit，好处是历史中的每一步都清楚；以后如果有 external developer，这种方式可能麻烦：主分支持续移动，其他分支反复 rebase，又触发 CI。

    此外还有验收层次，例如逐文件 100% 覆盖率，以及真实产品、发布产物的验证。提交历史中可学的东西很多，这里不逐一展开。但即使有这么多人类制定的要求，仍无法彻底阻止 AI 生成 slop。

    图 40：01:16:40，仓库提交与协作统计的现场查询。

    大家用过就知道：没说清楚的事情，Agent 会猜。用了 Grill Me 一类 skill，它可能反复提问，问到让人厌烦；没有澄清，它又会为了完成任务自行作主，添加许多东西。原本只是实验，它却做大量不必要的测试、验证，让后续维护和修改复杂起来。

    DeepSeek Harness 最终仍由人驾驭。人很难在短时间内亲手写出这么大的系统，AI 使建造速度提高，也需要防止它破坏项目。

    上次讲过 i18n 的例子：README 有中文和英文，两份文档要求严格一致，于是用 YAML 记录关系并检查。它确实阻止了不一致，却让 repo 膨胀，多出一堆不好理解的 YAML。IDE 可以隐藏这些文件，但它们仍然存在。

    这也是我认为软件项目仅用目录存储不够理想的原因：项目里的对象有复杂关系，应当能保存这些关联。现在用 YAML 文件表达，可能只是一种 workaround。DeepSeek Harness 为了让 AI 产出与人类要求相符的代码，做了很多工作。

    用检查器约束代码和文档

    原片 01:20:00–01:30:00

    它采用的办法，是找到不希望出现的特征，一个个排除。预想到 AI 可能生成哪种 slop，就写验证器，在 commit、push 到 remote 或每日运行时检查，发现错误就阻止提交或报告问题。

    我让 Agent 总结这些 gatekeeping 措施时，它激活了项目里的文字规范 skill dsh-prose-standard。这有一点 unslop 的意味：删除推理过程、重复和无用修饰。

    AI 写文档时，常把自己的思考也塞进去：为什么这样设计、怎样验收、不要做什么。这会造成问题。假设文档说“做了 A、做了 B、没做 C”，这些陈述都对应某个实现文件，例如 implementation.ts。它们会形成额外的维护关系。

    图 42：01:20:40，项目如何把关一次代码改动。

    图 43：01:21:20，文字编写规范 skill 与文档要求。

    实现变化时，文档也要同步修改，这引入了额外成本。AI 迭代几轮后，可能删掉了 A、B 对应代码，却错误地留下“不要 C”这句话。很多本该清除的东西，就这样留在 repo 里。

    DeepSeek Harness 的检查大致分七类：代码与类型质量、架构与依赖约束、行为正确性、持久化与兼容性、文档、构建交付、评审。先看 lint 和类型检查，它们能挡住许多低级错误。模型能力强，并不保证不会犯这种错误，大型代码库里尤其如此。

    例如，改接口时必须一起修改全部调用方，确保所有东西仍能编译。自己做小项目时，也许编译过一次，随后随手改一点就 push；正式项目要防止 Agent 这样做，就需要更严格的自动检查。

    不同用途的 ID 即使都以字符串表示，也不能随意混用；同一份代码也要遵循同一套 lint 规则。

    图 44：01:23:20，代码质量与严格类型检查。

    第一门程序设计课就应该教 lint。连空格格式都不统一的代码，可以直接由工具指出；更重要的是类型安全与异步正确性，例如丢失的 Promise、没有妥善处理的异步任务、危险或冗余的断言，以及已废弃 API。

    个人 hobby project 可以自行承担某些不安全特性的代价。严格项目则可以明确限制：例如某些 Rust 包不需要 unsafe，就在规则中禁止它。Agent 做实验时也许用了 unsafe，但要让代码通过 lint 并推到远端，就必须修改到满足要求。

    no-unused-vars 也是有用的规则。对人写代码尤其如此：声明变量却没有使用，可能意味着拼写错了，或者该用这个变量的地方用了另一个。

    图 45：01:24:00，类型安全、异步检查与 lint 规则。

    比如写循环时混淆 i、j，该递增 i 却写成 j++，或者条件里引用了错误变量，编译器和 lint 都可能帮助发现问题。现场写出的例子还涉及未初始化变量，它也会被检查出来。

    除此之外，还有 prefer-const、禁用 var、no-unused-expressions、作用域等规则。项目自己的检查则更具体：非第三方代码的导出项需要 JSDoc，UI 文案不能硬编码，还会验证 runtime closure、client domain graph、Cordis 配置等约束。

    这些检查分布在不同阶段。pre-commit 会执行一批检查，包括 i18n 配对：中文、英文文档的对应关系若不一致，关联的 commit hash 对不上，就拒绝提交。pre-push 做 type check，CI 再执行更复杂的检查。

    图 46：01:25:20，项目检查器、导出文档与架构约束。

    图 47：01:26:40，变量 i、j 的现场代码与 lint 工具。

    架构约束也需要检查。Agent 为了完成一个功能，可能把整套实现另写一份，再在现有代码中硬编码一行函数调用。功能看似完成了，却绕开了项目架构。

    对人来说，既然架构设计清楚，通常默认大家遵守；对 Agent，可能还需要显式写出要求。写进提示词也许提高指令遵循，却会让文档越来越难读，这又是一项取舍。

    也可以用检查器直接约束控制流：规定相关调用必须由插件发起。Agent 若偷偷加一个绕开插件的硬编码调用，就拒绝它。这些细节往往来自开发者的经验和直觉，逐步积累。

    其他例子包括：浏览器代码不能无意依赖 host 实现，浏览器请求应相对当前文档解析，网络调用不能悄悄绕过用户代理，vendor 更新应遵循规定。测试也有一系列 gatekeeping，后面会专门讲。

    反例清单的限度

    原片 01:30:00–01:36:00

    课堂上无法逐个讲完这些检查。它们与具体语言、项目架构和功能绑定，也不是每位同学都对 DeepSeek Harness 感兴趣。我更想展示一种方法：遇到自己需要理解的项目，例如做 bioinformatics、要依靠某个工具完成 PhD，可以按这个方式查看它——整理文档质量保障，分析提交，把它画成 commit 时间轴，帮助理解。

    即使已经尽力，问题仍没完全解决。AI 能力很强，却不总能分清轻重。有时过分自信，以为完成了，结果没有达到预期；有时又过度谨慎，给一个实验加上很多不必要的测试。

    纠正它也可能带来新问题：一句“不要这样”，它会先写进文档，再写进代码、注释，上下文不断膨胀，每个词都在争夺注意力。好比告诉它做番茄炒蛋“不要放蒜”，这句话被反复强调；可是还有无数同样不该加的东西没有写出来，它们原本也应有相同地位。

    图 51：01:31:20，表达“坏”容易，表达“好”很难。

    不放韭菜、不放蘑菇，也不应该需要逐条列出。只是要一份番茄炒蛋，模型却未必理解这些约束的相对重要性。它有自己的倾向，人也有自己的偏见，人类社会就在不同判断中前进。

    这让我想到以前做的 program synthesis，也就是程序合成。它与许愿编程有点像：给出 specification，希望得到正确实现。比如已知 f(1)=2、f(2)=3、f(3)=4，就可能合成 lambda x: x + 1。

    这类技术大约在 2011 年引发过一阵关注，Excel 的智能填充就是常见例子。我以前上研究生课常用它讲解：从邮件、报表收集电话号码，大家写法不统一，有人写 02512345678，有人写 025-12345678。怎样让不会编程的人，把区号 025 与电话号码分别整理出来？

    通过一些输入、输出例子合成程序，叫 Programming by Examples。

    对于字符串，可以合成基于正则表达式的程序。还有 Programming by Demonstration：用户操作一次，系统据此生成程序。在我看来，今天这两类问题已经完全被大语言模型解决。

    以前有一种热门方法，今天仍有人研究，叫 Counterexample-Guided Inductive Synthesis。它与我们不断纠正大模型的过程相似。先给 f(1)=2、f(2)=3、f(3)=4，模型产生 x+1；再补充先前没给出的条件 f(4)=6，要求修改。模型可能只加一个例外分支。比如它又写出“x 等于 6 时返回 4，否则返回 x+1”这样的例外分支。这个分支的输入输出还与前面的 f(4)=6 对不上；不断补反例，仍可能只得到零碎补丁。

    选择什么 counterexample，才能让系统生成真正符合要求的程序，很难。番茄炒蛋“不放蒜”的提示也有类似问题：不放香菜、韭菜、辣椒同样重要，不能靠无穷列举完成要求。

    刚才看到 DeepSeek Harness 的文档 skill，这里再看来自 Cursor 的 Unslop。写英文论文时，它可能有帮助。GPT 经常使用 ensuring、highlighting 等词，生成文字后又影响人类写作。某些词本身没错，却未必适合具体语气。

    从写作实例蒸馏出原则

    原片 01:36:00–01:39:52

    例如 ensure 的断言可能太强，学术写作时往往需要更谦虚；showcase、framing 也容易被反复使用。还有 Additionally、interplay、intricate，以及 “not just X, but Y” 这样的句式。

    Unslop 体现了一种 counterexample-guided 过程：发现 AI 常做 A、B、C、D，就逐条要求不要 A、不要 B、不要 C、不要 D。但更高层的 guideline 究竟是什么，仍不清楚。

    我尝试过一个实验，希望找到能更有效阻止 AI slop 的 prompt 或 skill。手里有自己回复过的全部邮件，但 AI 自动回复仍不理想：短邮件也许可用，长邮件就不行。即便把过去的邮件都放进上下文，让它模仿风格，也经常做不到。它还不擅长从这些实例提炼真正适用的规则。

    于是我尝试了一个 recursive self-improvement loop：希望得到 Unslop 或 WriteEmail 这样的 skill，但事先不知道它应该是什么样。

    图 54：01:36:19，Unslop 的词汇、句式与样式规则。

    图 55：01:36:28，Unslop 的长规则清单。

    评价过程是可建立的：有很多过去写的邮件和人工文稿，可以比较回复长度、词频、句子长度、标点使用等统计信息。让模型用当前 WriteEmail skill，回复过去收到的邮件，但不看我当年的回复；随后计算各个 metric，看生成结果离我的风格更近还是更远。

    更近，就保留这次修改；更远，就要求它提炼一条更 general 的 guideline。希望得到的规则能覆盖一类问题，少一些“不要用某个句式”这样的逐条禁止。就像“不放蒜”背后，也许应提炼出“不要加入无关内容”之类原则，再把这个 principle 写回 skill，使它的判断力提高。

    今天还没做到，但我对此乐观。整堂课讲的过程有相似结构：软件、工程、知识都在演化。有没有可能构建一个 self-improvement loop，让模型在做好小事的同时，也能逐渐做好大事？今天下课。
