    数据分布工程的飞轮

    原片 00:10:05–00:18:52

    这对我们有什么启发？比如 OpenAI 说要 all in RSI。回头看 The Bitter Lesson 和 scaling law，这条规律可能仍未停止。GPT-6 发布后，我最大的感受是，OpenAI 可能找到了一个门道。我暂且称它为“数据分布工程”。GPT-6 有惊人的空间推理能力，能理解图片里的空间关系，因而在画图、生成模型上表现很好。我认为这显然与训练时加入了这类数据有关：基模阶段可能已有空间数据，后训练和强化学习又通过更多数据与反馈，帮助它分辨空间任务中的好坏与对错。

    图 4：10:08，《The Bitter Lesson》。OpenAI All In RSI。支撑新一轮 scaling law 的是数据分布工程：学什么、何时学，怎样学，再按学习进展、迁移和泛化去改训练分布。页上还写着 DoReMi 的实验。页码 3/8。

    这样，scaling law 就多了一个维度。过去讲的是训练数据越多，基模越好，所以 Anthropic 去买书、烧书；按这个思路，掌握别人没有的数据就有优势。到了强化学习时代，我觉得他们看到了另一点：一个已经很好的基模，再加入一个没见过的领域进行强化学习，可能在所有任务上都变得更好。这让我感到震动。

    回看模型的演进：最早训练语言 token，后来加入数学语言与视觉多模态，再进一步学习空间感知。随着能力积累，新领域需要的数据可能越来越少。从零训练具身智能模型时，通常需要大量模拟器数据，但模型容易 reward hacking，例如根据脚部光照渲染中某个像素亮不亮来获得奖励，学到的行为无法泛化。一个既会语言又会编程的大基座模型，再接受空间感知训练，所需数据可能就少得多。我的猜测是：每增加一个人类知识领域，模型可能用更少的数据就能泛化。这个趋势让我感到可怕。

    人的学习顺序与模型相反。婴儿先与世界交互，学习世界模型，一两岁时说话还不利索，经过一到三年的学习才逐渐掌握语言。之后才学数学，再像我这样读 PhD，训练 research taste。大语言模型走了相反的顺序，但两条路都走通了：只要数据足够、scaling law 继续发挥作用，不同顺序也可能训练成功。基模厂商也许已经找到了数据分布工程的循环，只需决定何时、以什么比例注入什么数据。在这个思路下，架构和算法的重要性可能下降：只要训练不崩、训练与推理一致，避免训练时一个参数、推理时又变了这些工程问题，十倍、一百倍的数据就可能解决问题。更好的算法和结构仍能带来提升，但只要这个循环有效、资金足够，他们就能继续扩大规模。

    我把它看成数据依赖

    原片 01:08:18–01:16:23

    AI 能做越来越多的事，甚至可能从这些论文中学会品位，确实让人焦虑。人类现在仍希望理解它做了什么、判断它做得对不对。假如有一天 AI 的所有工作都远超人类、只有人会犯错，我们也许会放弃理解。但今天，能驾驭和理解 AI 的人仍更有机会适应变化。门槛不断提高，就更需要学会使用 AI，理解其中的软件工程经验。

    作为计算机科学背景的人，我把 Royce 的模型理解为 data dependency，并假定修改有成本。这是我的一种理解，可以继续与 AI 讨论。需求分析、系统设计、实现、测试、交付维护，每一步都可以看成一个程序，把人也看成处理信息的程序。至少我思考时，会在脑中用语言组织步骤：要怎么做，会有什么后果。人学会语言后，也能用类似 chain of thought 的方式思考。把这些过程及其产生的 artifact 连起来，就得到一个 data dependency graph，一张有向无环图。

    再展开来看，需求中有多个点，彼此有些关联、有些独立；设计依赖需求，后续实现又依赖设计，这些关联会传递。如果测试失败，向上追溯发现某几个设计错了，依赖它们的所有工作都可能要重做，成本自然很高。这也解释了 Royce 描述的问题。每个人的经历不同，对模型可以有不同理解，所以个性化教学很重要。我做过一些系统和操作系统工作，就自然用学过的计算机科学概念解释软件工程。这种依赖视角也能成为继续推导方法的起点。

    图 18：69:16，《瀑布模型就是 Data Dependency Graph》。需求分析到系统设计、系统实现、测试验证、交付维护。不做需求，设计就会漂移；设计错了，实现就会漂移。TDD 是拿测试用例当需求与设计。产物之间有依赖，不等于所有阶段只能完整地做一遍。

    知道了 data dependency，怎样降低上游修改的代价？可以先缩小范围，避免一次产生太多依赖：从 breadth-first 铺满整层，改为 depth-first，先沿一条重要路径走通。MVP 先完成优先级最高的一组依赖，再向旁边扩展，这与敏捷开发的思路相通。越早得到反馈，越能收窄不确定性与 gap。需求阶段主要澄清 intent，设计阶段确定 spec，需求阶段也可能涉及部分 spec，编码和测试则实现 implementation。每项 intent 会细化为多个点，并产生下游依赖。沿这条关系看，就能理解为什么 MVP、敏捷和 TDD 能减少返工。

    图 19：73:25，《用 Data Dependency 理解开发过程》。瀑布是晚验证、长返工。MVP／Pilot 先做一个最小实现，验证高风险假设，再修订需求与设计。敏捷是小批量、短反馈。比较的是多晚才得到反馈，得到反馈时已经做了多少依赖它的工作。

    阅读经典著作能看到一个领域最早面对的根本问题，以及当时找到的出路。后人可以用新的概念重新理解、改进它。我喜欢 data dependency 这个视角，沿软件工程历史看下去，还能用它推导更多概念。

    这可以作为学习软件工程的起点。软件当然可以定义为代码和数据，但用依赖关系和产物演进的视角理解它，还能继续推导出后续方法。

    经过几十年发展，软件工程为每个阶段建立了方法和工具，以减少返工。学软件工程时，老师可能要求写文档、填很长的 checklist，逐项确认是否满足要求、是否沟通过。习惯做 OJ 的同学容易觉得这些没意义。但例如最后一项“是否与客户确认”，真正完成沟通再打勾，便能降低 intent 不符合客户要求的概率。这就是方法，也是工具；它完全可以通过人的行动发挥作用，不需要代码。

    图 20：75:11，《软件工程的方法和工具》。没有大语言模型这种“万能编译器”的时候，需求分析用文档、用例和界面原型，系统设计用实体关系、状态迁移、模块和接口，代码实现另有语言。Computer Science 大部分课程集中在代码实现，是 bottom-up。页码 1/5。

    今天的软件工程研究还包括自动测试、检测 bad smell 等，相关论文很多，我也觉得其中不少是在灌水。以前看到等号两边不留空格的代码，我们常会判断它质量不好。但 GPT-6 学会节省 token 后，情况有些变化：它把很多语句挤在一行，代码难读，却仍然能正确运行。我不知道它如何保证正确，也许将来我们未必应该直接阅读这种代码。

    软件工程包含许多细小方向。读研究生时，可能只研究编码阶段中 Java 的某一种 bad smell，以及怎样改进检测。深入具体问题时，别忘了回看整个领域与经典工作。深度训练让思维链更长，广度训练则帮助人理解问题在整体中的位置，两者都需要。

    为不同阶段创建工具，往往也需要不同语言。大语言模型出现前，checklist 通常写在 docx 文档中，打印存档，客户沟通记录可能还是手写的；编码时则使用编程语言。今天的大模型像一个通用编译器，能把自然语言转成多种表达，过去却没有这种能力。1970 年设计主要靠自然语言文档，我上软件工程课时也先写需求文档，再写设计文档，沿着瀑布流程走。文档的弱点是由人撰写：人会出错、写错字，同一句话还会被不同的人理解成不同意思。室友之间经常需要花时间对齐理解，恋人之间有时更难。

    要在设计阶段减少返工，就会想到创建一种介于自然语言和编程语言之间的设计语言，也就是某种 domain-specific language。Checklist 也是中间语言的例子：它用自然语言，却规定必须逐项列出，每项打勾或打叉。虽然由人检查，但勾叉的语义比自由文档更明确。沿着需求、设计、实现往下，表达逐渐形式化，语义越来越确定，这与收窄 intent、spec、implementation 的差距相对应。

    过去学习通常 bottom-up，先学编程，因为不理解代码就难以理解整个过程。AI 出现后，也许可以先从产品经理做起。我设想第一门课就让学生设计产品，后续实现交给 AI。初学者还看不懂代码，也不必在这门入门课上控制实现质量，但仍能提出好想法、做出产品，并先了解整个开发过程。

    Checklist、决策表等方法里都包含经验。理工科学生可能觉得软件工程课像文科：“所有勾都打上才能进入下一阶段”，听起来毫无必要。但这赋予流程明确语义，帮助避免遗漏与矛盾。有些 checklist 甚至要求把所有文档两两对照审查，程序员可能不愿做，却正是这种检查能减少文档间的偏差。这些方法来自失败教训和团队管理经验，做软件的人同样可以学习。

    图 21：83:12，《方法和工具的智慧》。决策表把条件组合和预期结果对应起来。QuickCheck 让人描述性质，由工具生成输入、寻找反例。需求追踪矩阵用来检查覆盖和分析变更影响。页码 2/5。

    测试领域也有经典工作，例如 QuickCheck：由人描述性质，工具生成输入、寻找反例。其出发点是，任何从规格到代码的翻译都可能出错。程序不 crash、没有空指针错误、资源不泄漏，也是需要遵守的隐含规格。能否写下一个 property，让工具生成大量测试？全部通过以后，对代码就多一些信心。单写一份代码，很难知道它是否正确；独立做测试、观察结果、增加质量保障，能逐步提高信心。如果还能写出清晰的正确性证明，信心会进一步增加。这些都是软件工程研究的问题。

    再看需求追踪矩阵。前面讲过 traceability，它把 data dependency graph 中原本没有显式记录的关系补上。文件系统里，一个项目只是很多文件：docs 下的 Markdown、source 下的 TypeScript、README 等。这种组织受文件系统约束，成了我们承载软件的惯常办法。Traceability 要求通过链接或文档，把代码与需求点、需求与需求、需求与设计对应起来，使它们可以交叉检查。人的能力有限。学生可能觉得只要成为最强程序员，就能在企业里找到好工作；可项目组织者面对的是没有一个人能独自做完的任务，必须考虑成员水平、雇用人数、成本，以及最终怎样交付。

    今天每个人都可以尝试做产品经理，把第一门课变成调动开发能力做产品。DeepSeek 在我看来已相当于资深程序员，超过普通本科毕业生，而你马上就能拥有 2500 个并发的 DeepSeek。刚高考完的学生，过去不会想到自己能管理 2500 个“程序员”。这种工作方式要求我们改变 mindset。

    其中还有 design by contract，契约编程。Bertrand Meyer 的 Eiffel 大约在 1986 年出现，把 Hoare 三元组直接写入代码。它的语法包括 function、is，赋值用冒号等于；函数先写文档，再写 require 前置条件、do 实现、ensure 后置条件。它鼓励先不写控制流，先把各模块的说明、precondition、postcondition 写清楚。比如账户取款，写契约时自然会问：余额不足怎么处理？第一个 MVP 可能直接 crash，或者把这种情况排除在规格之外；随着软件演进，这些 contract 就越来越重要。Eiffel 希望在语言中直接表达它们。

    图 22：88:00，《契约编程：Design by Contract》。Bertrand Meyer 的 Eiffel。调用者保证前置条件，实现者保证正常返回后的结果。例子是不允许透支的账户取款：调用前金额大于 0 且不超过余额，返回后余额等于旧余额减去金额，并且余额不能为负。

    图 23：89:56，《把契约写进语言》。Eiffel 示例依次写出注释、require 前置条件、do 实现、ensure 后置条件；下方列出 Dafny、Verus 等后续工具。

    多年来，软件开发者一直在探索怎样表达 spec：从自然语言，到带逻辑公式、能表达设计的半形式语言，再到编程语言。有时无需写实现，就能检验函数调用之间的逻辑关系。今天这仍是活跃方向。AI 又可能改变它：自然语言理解和 checklist 检查更容易了，剩下的 gap 更多来自我们自己没有想清楚、说清楚。若这些都能明确，也许后续工作就能完成。Dafny、Verus 等工具延续了相关探索，希望自动证明函数满足前置条件时，执行后满足后置条件，并进一步证明各模块连接起来能满足整个系统的 intent。

    ChatGPT 出现前，大约 2020 年或 2022 年，我在操作系统课上预测过三十年后的编程方式。先说“程序过不了编译”不准确，我想表达的是：程序里可以写任意业务相关的 assert，或前置、后置条件。例如双向链表向左再向右、向右再向左，最终都要回到原节点，就把这个性质写成断言。编译器如果证明不了，就不允许程序编译；编译通过则保证这些性质已有证明。到那时，类似 property-based test 的工作就可以直接交给证明机制。现在看，也许不用三十年，从当时算起十年或十五年就可能实现。

    这个过程中还有一个集大成者：UML，Unified Modeling Language。需求用自然语言，设计有专门的领域语言，实现用 C、Java 或 Eiffel；UML 想提供一种中间语言，统一面向对象世界的表达，解决语义对齐。人靠自然语言交流，而自然语言连接各自大脑的 latent space。比如我说“今天看到一个美女”，每个人想象的形象都不同；要求用 Blender 建模，结果也会不同，让不同模型生成也一样。开个玩笑，豆包生成的人好像又都长得很像。数学语言则从很小、容易达成共识的公理开始，例如自然数与 Peano 公理，再逐步构建更大的体系。我们希望计算机里的形式表达也具备这种明确语义。

    UML 想把需求、设计中能够对齐的部分明确表达出来，同时保留尚不能对齐的部分。它通过模型元素及其语义做到这一点。比如类图有一个 student 类，包含 name 字段，这个关系可以对应到代码；sequence diagram 则规定事件的时序。仅用自然语言描述并发中的先后关系，常会出现歧义，UML 用明确规则表达顺序与并发，尽量减少尚无代码时的语义偏差。它并不能让所有内容百分之百对齐，但能把可确定的部分固定下来。

    我个人觉得，今天 UML 已经“死了”。它需要多层中间语言，是因为原先很难在自然语言与形式语言之间直接对齐；AI 能通过提问帮助完成这个过程，UML 的一些前提就改变了。但它设计时遵循的 first principles，仍然能指导今天的开发。

    我特意让 AI 帮我重读 UML spec。自己写的阅读工具可以处理很长的文档，几千页也能用，体验接近 PDF。Kimi 团队看到我的视频，送了一个月 699 元套餐，我便让 AI 直接读规范并备课。做法是分配 subagent，每个读 50 页，相邻分段留 overlap；把 lecture notes 交给它们，提取软件工程经验，排除在 AI 时代已不必要的部分，再整理成课件。最后花掉五小时额度的 18%，我折算约为 5.3 元。这也带来一个问题：好模型与一般模型会造成学习效率和成本的差距。我猜 GPT-6 因为省 token，可能在类似价格下给出更高质量。对学生来说，100 美元的 Codex 套餐大概够学习使用；维护大项目才容易把 100 万上下文装满，消耗大量 token。日常学习通常不必像我这样整份加载 UML spec，也可以读已经整理过的内容。但将来是否人人都学得起，仍是现实问题。教育平权需要算力与资源，而资源未必足够。怎么办？We don't know，这可能要由社会共同面对。
