    GPT-6 来了，设计上我还是要骂

    原片 00:00:00–00:09:10

    前几次课讨论了怎样使用 AI。生活中遇到许多琐碎的不便，都可以向它说明真实意图，尝试让它协助处理。有效的流程还可以整理成 skills，减少反复沟通。

    GPT-6 发布后，我试用了一段时间，仍有惊喜。编程能力的提升在我看来有限，复杂任务的速度却确实变快了，我专门测过。设计方面，它仍更倾向于完成任务，工程品味还需要人指导。我经常批评它，也觉得自己暂时还有用。

    图 1：00:08，仙1-107。讲者在讲台，右侧课件是《快讯：GPT-6 发布了》。

    图 2：00:44，《快讯：GPT-6 发布了》。图上是一只手把写着 Ultra、GPT-6 的卡片递出来。

    为什么模型的设计仍会让人不满意？意图、规格和实现的选择空间很大。面对“做一个国民级应用”，不同产品经理都会有不同想法，AI 也只能按自己的理解补全。我还发现，从 GPT-5、5.6 到 6，思维链和代码越来越紧凑，人读起来更吃力。过去会明确要求符合人类工程习惯，现在我越来越少逐行检查，更关注它能否把结果做对。

    GPT-6 让我惊喜的是空间感知。我猜 OpenAI 的路线是先让模型学数学：数学有共同的推理规则，证明是否正确，相比开放的软件需求更容易判断。这也能成为其他推理的基础。例如中午去哪吃饭，看起来是个人选择，也可以分析成理由之间的关系：我选择在楼里订餐，因为更快，下午有会，省下时间还能休息。这些关系可以联系到离散数学中的命题逻辑。

    我的猜测是，数学能力增强后，还可以通过强化学习训练空间能力。例如鲁班锁的第一块如何抽出，立方体的投影怎样对应，骰子展开图如何折回去。人依靠空间想象处理这些题，模型也可能从简单任务开始学会。

    GPT-6 发布前，我们做了小半年的 3D 打印研究。GPT-5.6 的空间理解较弱，我们通过多轮对话，仍能生成符合一些规范的模型。例如左右观察呈现不同图案的光栅玩具，需要一棵较长的搜索树。结果新模型一次就做出来了，这让我们重新思考后续研究方向，也让我心疼学生此前的投入。

    空间理解与数学能力结合后，具身应用也有了更多可能。发布后，小红书上很快出现用 GPT-6 控制机械臂抓取物体、叠衣服的演示。它是带视觉能力的语言模型，依然通过一帧帧观察、决定下一步来操作；在提示词还没有充分优化时，就表现出相当的能力。

    模型还会继续进步，也许某天这门课的部分内容就不必讲了。但今天仍需要软件工程。至于 AI 时代是否还该学操作系统、数据库，我也在思考。可以类比早期汽车：经常出故障，司机必须理解原理，知道怎么修。那时会开车和会修车联系得很紧。

    今天，自动驾驶已经让乘客能在不了解整套系统的情况下出行。AI 对智力工作的影响也可能类似，范围还更广。我的当前答案是继续学习：理解概念有助于调动 AI 的能力，也便于借用其他领域的方法。未来该怎样学，我还没有确定答案，欢迎一起讨论。

    图 3：02:58 前后一直留着的课件《但设计上还是要骂》。页上写：面对开放的 intent-spec-impl 空间，“做一个好用的界面”往往要看到第一版才说得清，实现还会反过来改需求。下面引 Herbert Simon 1973 年《The Structure of Ill Structured Problems》：结构良好和结构不良的问题之间，边界是流动的。

    图 4：06:47，《Anyway... 我们还是要学习的》。创造力需要正确的概念和理解。页上引 How People Learn（2000）：专家的知识围绕核心概念组织。今天进入真正的软件工程任务：从零开始构建一个项目。

    一个目录，就是一个项目

    原片 00:09:10–00:15:20

    今天从零开始一个软件项目。做课程作业时，老师通常给好下载入口和框架；做自己的项目，则可以先建一个目录、起个名字，比如“我的小游戏”，再开始工作。

    面对空目录，我们怎样知道该放什么？很多经验来自观察老师的工程、同学推荐的项目或 GitHub 仓库。看到文件、文档怎样组织，就逐渐学会自己该怎么安排。

    项目里的文件共同构成可交付的产品。让 agent 运行后，可能弹出窗口或打开网页。但本地运行成功，只说明自己的机器能访问。网上有个笑话：用新模型做了很多“杀手级产品”，地址却全是 http://localhost:5137。localhost 指向自己的机器，其他人无法通过这个地址访问你的应用。

    希望全世界都能使用，就应把这个要求写清楚。否则模型可能按开发者习惯先启动本地开发服务器，等待检查后再部署。这些流程也是需要了解的专业知识。

    图 5：11:29，《什么是一个软件工程项目？》。一个目录、一组文件、一个可交付的东西。目录里混着 intent、spec、impl。经过 build 或运行，可以得到 npm run dev 的本地窗口，也可以是一个 .exe。

    刚学编程时，大家可能在 VS Code 里一键运行，后来才知道 build 目录是命令行工具生成的。用 GCC 把 hello.c 编译成 hello 二进制文件，已经具备了一个小软件项目的基本过程。

    软件包括代码、文档和其他相关材料。教室的屏幕、讲台设备、升降桌，都依赖软件；眼前桌子还显示着 106 厘米的高度。我常把软件理解为现实需求在信息世界里的投影。现在这个投影表现为目录、源文件和构建产物。这样的组织未必符合今天的全部工程惯例，但十多年前许多人就是这样开始的。

    我的第一个博士生 2012 年入学时，嫌笔记本屏幕小，常去机房写代码。今天可以买较便宜的外接屏，当时则没有这么方便。为了在机房和笔记本之间切换，他把代码放在 U 盘里。到了大二，U 盘坏了，早期作业也全丢了。这个故事反映了当时常见的项目管理方式。

    我上学时常把作业压缩后发邮件，现在多在网页上传。这些都在解决项目保存、交换和交付的问题。

    标准答案是 Git

    原片 00:15:20–00:24:00

    今天管理项目版本，通常应该使用 Git。它既能保存代码、文档等当前内容，也能比较、恢复历史版本。这种能力对软件开发很重要。

    Git 让分发和更新更方便。课程作业通过 git clone 获取，老师在远端更新后，同学执行 git pull 即可，不必逐人重新发文件。课程里的 make submit 还能打包并上传作业，已经有一些持续集成、交付的味道，后面值得专门讲。到了 agent 时代，自动执行的范围又进一步扩大，连写投诉信等事务也可以交给它，再按自己的信任程度决定如何检查。

    图 6：15:14，《今天：Git》。项目版本管理有了标准答案：保存当前文件之外，还能保留、比较和恢复历史版本，页上链到 Pro Git。作业用 git clone 获取，git pull 拉更新，make submit 提交。make submit 是课程项目约定的入口，由项目里的 Makefile 定义。

    学习工具越来越容易，观察和主动学习的习惯就更重要。看过许多仓库后，应该留意文件、文档和组织方式的差别，逐渐理解别人为什么这样使用 Git。

    中学任务多，照老师要求完成可能最省时间；到了大学，如果只把作业拉下来，绝不多看一步，就会错过学习机会。那有点像只接受指令并执行的 agent。多花一点时间打开文件，可能就会发现值得借鉴的做法。

    现在有些 README 很长，堆满字符画和目录，带着明显的 AI 生成痕迹。再看维护十多年的成熟项目，有的 README 很短，几个链接就能把人带到需要的内容。这种对比会让你学会另一种文档组织方式。

    路牌设计也给过我类似启发。以前在香港找路，每到容易犹豫的岔口，前面就有清楚的指示；在南京一些地铁站，我却常要环顾甚至走一段路，才能找到出口地图。由此想到界面设计：用户站在这一页，会想去哪些方向？怎样用少量信息帮助不同的人找到路？

    看过好的 README 后，还可以马上问 AI：它为什么让人容易理解，没有那种冗长的生成感？让它帮助分析具体差别。

    图 7：17:46，《学习变容易以后，学习意识更重要》。别人的项目就是学习素材。公众号上满是 GitHub 链接，没人告诉你哪个好，看得多了也会有感觉。“上课耽误学习”的本质是：课外的信息量和密度已经很大，但我们从未教过怎么用好。

    成熟开源项目里积累着工程师多年的经验，可能经历过失败、重构，才形成现在的做法。课外材料的信息密度远超课堂能全部覆盖的范围，但传统教学很少教大家怎样利用这些材料。这也是“上课耽误学习”抱怨背后的一个问题。

    我的习惯是，先暂时不看答案，想一想自己会怎样解决，再与眼前方案比较。自己的方案更好，就分析对方的不足；对方更好，就追问它为什么好。持续比较这些细节，外界信息才会转化成自己的知识。

    这个方法也叫 virtually implement：先在脑中实现，再看作者做法。它适用于论文、高等数学和计算机系统基础。方案一致，说明已经掌握；不一致时，可能学到教材里更简洁的设计，也可能偶尔发现自己有更好的方法。这样的发现会带来很强的学习动力。

    图 8：24:06，《留意：让每一次阅读都成为学习》。Virtually Implement：看到问题先问自己会怎么做，再看作者的做法。一致就很好，不一致就是学习的机会。页下引 Chi 等人 1989 年关于自我解释的研究。

    冲突的时候，两边都要摊开

    原片 00:24:00–00:29:00

    接下来用 Git 的细节练习这种观察能力。读别人的仓库或 AI 生成的代码，都可以这样学。

    GitHub 让代码分发变得方便，如今又成了 AI 工具经常依赖的平台。npm 项目、编辑器配置等大量资源都能从这里获得。

    上周推免面试，我问同学什么是 Git。多数人能说出下载、分发代码，有人还知道项目目录的快照。问到 git rebase，回答普遍不好；更意外的是，问 git merge 冲突后会看到什么，也很少有人能描述出来。

    本地改过作业，老师又发布更新，很容易发生冲突。如今我也会让 agent 修好并运行测试，但学习时值得停下来看看：文件里会出现尖括号、等号等标记，把双方修改摆在一起。冲突需要开发者判断，工具应当把判断所需的信息呈现出来。

    假设同一文件第二行，一个人改成 2，另一个改成 3，Git 无法替人决定采用哪个。它会把双方内容放在冲突位置，标出 HEAD、incoming 等来源，IDE 还可能提供接受某侧修改的按钮。开发者决定保留或组合哪些内容，再提交解决结果。这和前面说的路牌设计一样：把所需信息放在发生疑问的位置。

    回答不好，一方面可能没有真正协作开发过，另一方面是用过却没观察。即使用 agent，不同分支也会发生冲突。值得亲自使用，并留意过程。

    图 9：27:54，《Git：听说过，还是用过？》。保研面试里，多数同学能解释 Git，却不熟悉 rebase 和合并冲突。冲突时，双方内容和标记会写入工作区文件，git status 显示 both modified。

    从复制目录，自己长出 Git

    原片 00:29:00–00:40:40

    只在 U 盘保存一个目录不够可靠。以前常见的做法是复制整个项目，命名为作业 v1、v2、最终版。虽然笨重，却满足了一个真实需求：改坏后能找回旧状态。

    从这个需求出发，就能设计简化的版本管理工具：只保留一个工作目录，用命令列出历史版本，恢复到指定状态。目录里可以有代码、文档、规格和测试。继续遇到与室友同步、同时修改同一文件等问题，就会逐步需要分支和合并机制。

    图 10：29:11，《Git 之前，版本怎么管？》。最直接是复制整个目录，叫作业-v1、作业-v2、作业-最终版。RCS 这类工具替你保存历史版本。CVS、SVN 把历史放在一台服务器上，大家取出、修改、再交回。Git 保存项目的一个个版本，也记录来路。页上链到 Pro Git 里版本管理的几种做法。

    Git 以前还有 SVN 等工具，使用检出、提交的协作方式。课堂里，我用“记录变化”与“保存快照”来对比设计思路：若恢复旧版需要逐次应用增量，就要考虑性能和缓存；Git 的快照模型更直接地表达了回到任一项目状态的需求。我个人更喜欢这种概念。

    Git 的作者也是 Linux 的作者 Linus。早期 Linux 通过邮件列表交换补丁，由维护者纳入代码再发布，后来用过 BitKeeper。2005 年，Linus 开发了 Git，希望得到简单、高效、概念清楚的版本控制工具。有兴趣可以继续读 Pro Git，也可以请 agent 协助理解。

    我们需要项目级的时间回溯，允许犯错后找回历史。这些概念可以从已有经验和需求一步步推导出来。我讲课也希望呈现这种联系。它们与逻辑推理有关，这让我想到：先训练好数学推理，也许确实有助于 AI 理解更多问题，甚至形成设计判断。

    图 11：34:15，《从已有经验，长出 Git 的概念》。改错了想撤销，所以项目要能回到旧状态；几个文件要配套，所以要记住同一时刻的样子；多人同时修改，所以要知道各自从哪里出发。页上还留了一个预测：删掉一个已经提交过的文件再提交，旧版本还能找到吗？新快照里没有它，旧快照仍然记着它。

    开始新仓库，先执行 git init。它会输出一些提示，值得让 agent 解释。完成后生成隐藏的 .git 目录，项目便由 Git 管理；之后可以配置远端，获取或推送版本。

    创建 hello.c 后，用 git add hello.c 暂存，再用 git status 查看状态。随后通过 git commit 保存带说明的快照。Git 鼓励围绕有意义的修改提交，例如修 bug、加功能、调整脚本或文档，逐步记录项目怎样变化。只把它当作“作业 v1、v2、v3”，还没用好这份历史。

    提交时会打开编辑器，我这里是 nano。写清本次修改、保存后，提交就完成了。观察其他项目能看到大小不同的提交，但仍需要理解何时暂存、何时提交、怎样写说明。遇到新操作，可以问 agent：刚才的做法符合工程惯例吗？

    我故意把说明写成“I did some cool stuffs”，再让 agent 检查。它指出提交信息没有说明做了什么，代码本身也有问题。配合语音输入，这样的追问很快就能完成。

    图 12：39:00 前后，终端里 git add hello.c 之后做了第一次提交。信息是 “I did some cool stuffs”，hello.c 是新文件。

    快照记录状态，commit message 则解释版本之间的变化。沿历史阅读，应能了解修了哪些 bug、加过什么需求、经历过什么重构。如果一万次提交都只写“I did some cool stuffs”，这份说明就失去了作用。

    空提交、编译产物，和该问的那一句

    原片 00:40:40–01:00:00

    版本收尾时，有时希望不改文件也创建一个提交。普通提交会拒绝无改动的状态，但 Git 确实支持显式创建空提交，agent 也知道怎样使用。

    空提交偶尔可用于触发 CI 或留下流程标记，不宜大量使用。发布版本通常还可以打 tag，例如 v0.1。把最后一次 bug 修复与发布准备区分开，有时有意义，但应根据项目流程选择。

    会 push、pull 只是开始，工程惯例背后还有很多经验。反过来问为什么要这样写提交信息、这样组织历史，能学到更多。模型知道大量资料，也有时间展开解释；老师即使理解这些知识，现场讲授时仍受精力和注意力限制，未必能给出最好的讲法。

    再做一个不理想的提交。编译 hello 后，目录里出现未跟踪文件，用 git add . 可以一次加入所有变化，Git 允许这样操作。让 agent 评估，它先指出提交说明没有信息量，建议用祈使语气描述具体修改和动机，例如修正 off-by-one，并考虑项目采用的 Conventional Commits 格式。

    它还指出内容混杂，hello 二进制是构建产物，应由构建系统生成，并放进 .gitignore。多人在不同环境编译，产物可能包含时间、哈希或本机信息，即使源码相同，二进制也可能不同。不断提交会让仓库膨胀，还会制造难以合并的冲突；图片等二进制内容也有类似问题。

    我让它处理这些问题。它先确认仓库没有 remote、没有共享给别人，再重写本地历史，移除空提交和构建产物，整理成两个各自有明确目的的提交。新说明有简短标题，也有解释正文。这里先检查是否影响协作者很重要。

    GitHub 还识别关联 issue 的提交语法，例如满足平台条件的 fix #123 可以关联并关闭对应 issue。实际使用才能逐渐熟悉这些能力。Agent 时代可以少记一些具体命令，但仍应理解 Git 能做什么、怎样判断操作是否合适。至于能力来自自己还是工具，也值得思考。

    提交前逐个查看文件变化，能发现问题。我故意修改出不能编译的代码，让 agent 提交。它建议先修复，解释提交应该是完整、自洽且能通过构建的快照，并提到坏提交会妨碍 git bisect。课堂的系统提示词还要求它用中文详细解释，这也帮助了学习。

    git blame 能查看每一行来自哪个提交。git bisect 则能在历史上二分定位 bug：已知一个好版本和一个坏版本，并有可判定结果的测试，就可以逐步缩小引入问题的范围。在“此前都好、此后都坏”的情形下，像是在前缀为 0、后缀为 1 的序列里找第一个 1。定位提交后，再结合 blame 理解修改来由。

    每次提交前通过构建和测试，是基本工程要求。实践中反复遵守，才会成为习惯。Agent 也指出 AGENTS.md 可以作为项目协作规则提交。很多这样的知识，适合边做边问。

    以前新同学进组，第一周搭好仓库，我检查时常会发现各种版本管理问题。

    例如把 dist、日志、本机 VS Code 路径配置提交进去，甚至泄露仍有效的 API key。Mac 的 Finder 还会在目录留下隐藏的 .DS_Store，保存显示相关信息，容易被 git add . 一起跟踪。隐藏文件也可能是必要配置，例如 .github workflow，所以 Git 不能一概排除；临时文件需要明确忽略。

    生成文件也不能一概禁止。package-lock.json 往往应该提交；有些生成的头文件也值得保留，让没有那套生成工具链的人仍能编译。需要按文件用途判断。

    过去可以研究怎样用规则检查仓库是否符合这些惯例，比如提交前警告 .DS_Store。现在模型能逐项检查，还能耐心解释。老师批评时，即使想温和表达，学生也容易有压力；向 AI 反复请教，就减少了这种顾虑。

    图 13：49:59，《获取下一级知识》。能运行以后，为什么别人还要写 .gitignore？文件都在以后，为什么换一台电脑就编译不了？Best practice 是约定俗成的，每一个都是血的教训，或者对旧设计忍无可忍的产物。源码和编译产物一起提交，源码改了、产物忘了更新，同一件事就有两份互相矛盾的状态。

    大写还是小写，以及目录怎么长成一棵树

    原片 01:00:00–01:08:20

    检查规则有几十条，名字用大写还是小写？功能上都没问题，但呈现上仍需要选择。遇到这种小问题，多追问一句，也能增加理解。

    图 14：62:23，《大写还是小写？》。同一个检查可以写成 [TYPO-CHECK] 或 [typo-check]。他的直觉是大写似乎更好，但不是极强，也不太说得出原因。页上问：方括号里的字符，是一句话的一部分，还是一个可以被引用的规则名字？

    进一步可以研究 Git 的内部实现。操作系统课里有更完整的讲解，这里先介绍一个起点：Git 用持久化的数据结构保存目录树的一系列快照。

    假设根目录下有 a.txt、b.txt 和目录 d。已有一个快照，现在只修改 b.txt，无需复制所有文件。保存新的文件内容，再为从它到根的路径创建相应的新节点；未变化的 a.txt、d 可以继续引用原来的对象。新根引用新版本，旧根仍保留旧状态。

    即使项目有上百万文件，目录通常也不会深到上千层。借助这种共享未变部分的方式，每次只增加较少内容，就能表达一个完整的新快照。

    .git 中的对象由哈希标识。这里主要看三类：commit、tree 和 blob。Blob 保存字节内容，tree 描述目录项，commit 把一次提交与目录树、历史关系等联系起来。数据不断增加，历史状态便得到保留。从需求一步步推导，大学生也有机会设计出类似结构。

    纸面解释之后，还可以继续问：真正的 Git 里是否确实有这些对象？从 v1 分出两条开发路线，会产生怎样的关系？合并时又发生什么？带着这些问题去观察实际仓库。

    今天讲 Git，也是在讲工程惯例。注意演示中的提交说明：最初英文格式一致，后面却混入中文；不过仍有标题、范围和详细正文。Conventional Commits 就提供了一种可参考的约定，例如用 feat 表示新功能，fix 表示修复，类型之后接冒号和空格。文档很短，值得读。

    图 21：88:08，同一份说明翻到 Specification。类型是名词，比如 feat、fix，后面是冒号和一个空格。feat 用于新功能，fix 用于修 bug。正文按 RFC 2119 理解 MUST、SHOULD 这些词。

    Git 的实践建议有很多，例如经常提交。复杂项目中，大改动可能同时引入多个问题，一个上万行提交后再补上百个修复，很难判断何时修好。围绕一个目的做小提交，则更容易把问题与修复对应起来，保留审查和追溯的能力。项目刚开始时，大一些的初始化提交可能合理，后面要关注改动之间的关系。

    快照要小，架构要先定

    原片 01:32:50–01:40:13

    今天要记住的思想是：用一系列有明确目的的变更推进项目快照。这样可以从当前状态开分支探索，失败后放弃分支，成功后合并，也能让不同方向同时推进。

    一次同时改很多地方，容易让需求和代码纠缠。把工作安排为可理解、可审查的小任务，出了问题便于 bisect、blame，也便于解决冲突。即使一条分支上做了很多事，只要每次提交清楚，就更容易识别哪项修改冲突、哪些可以直接组合。

    有些项目要求 main 保持线性历史。我目前也偏好这种方式，尽管它并非只有好处。合并提交可以有两个 parent，完整记录分支合流；线性历史则有时便于追溯、cherry-pick 和 blame。清楚的历史还能帮助 agent 少读无关文件，降低维护成本和 token 消耗。

    实施前，我会先与能力较强的模型串行讨论架构。接口没有定好，后面就容易不断返工。教学 playground 的程序执行、编辑器、画面和时间轴彼此关联，我尽量用纯函数组织接口：程序生成 trace，按统一结构展开，跨组件状态集中管理。共享状态保持很小，其他组件通过接口协作。生成可视化时，我要求 agent 只读接口，不展开库函数实现，所以几万 token 就能完成一个示例。
