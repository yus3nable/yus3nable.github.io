    从软件演化回到质量保障

    原片 00:00:00–00:08:00

    今天讲软件质量保障。上一课用造航母来理解软件演化：站在一艘真正的航母上，很容易惊讶于人类怎样造出了如此复杂的系统。操作系统、编译器和应用服务器也一样。同学们都听说应该研究大型软件系统，可把 GitHub 上几十万行代码下载下来，读完 README，往往就不知道从哪里开始了。

    能够在工业环境中使用的系统，常常已经是一艘“航母”。它在演化中不断加入新需求：飞机要能起降，系统要能容错，结构也随之复杂起来。回头看，最初可能只是一只能够浮在水上的独木舟。这是系统最简单的状态，可以类比 repository 的初始版本。

    此后，人们不断提交修改、增加功能。每遇到新需求，就推理怎样实现；多人协作，社会中也形成相应的组织。这和今天 Agent 推理、多 Agent 协作有相似之处。状态持续演进，最后才成为复杂系统。用这个过程，也能解释许愿编程为什么经常让人觉得“还差一点”。

    图 1：00:00:40，回顾：复杂系统从最初状态逐渐演化。

    直接说“我要一艘能起降先进喷气式战斗机的航母”，再让 AI 动手，通常无法得到预期结果。它不知道全部意图，也没有在这个项目中经历从简单到复杂的一轮轮思考。即使模型知道相关知识，直接生成最终产物时，也可能漏掉历史演化中逐渐发现的问题。缩小到教务系统，情况仍然如此：intent、specification 与 implementation 之间始终有缺口。

    理解复杂系统，可以从某个 feature 开始，追问它何时引入。带着引入它的那次提交，从软件早期状态向后看，仿佛不断尝试把这项改动 rebase 到更早的系统上：在独木舟阶段，起降飞机显然不合理；船足够大之后，这个需求才开始合理。接下来就能理解，为什么会在运煤船上加甲板，甲板又怎样继续演进。

    软件演化是连续的。选择一个能理解的历史状态，再理解后面的变化，会比直接面对全部复杂性容易。这也是大学里安排操作系统、编译器等大作业的一个原因。

    图 2：00:04:00，从历史与 rebase 理解软件变化。

    亲手实现精简系统后，就有了理解大型系统的基础。借助 AI 完成大作业很方便，但把实现全部交出去，会损失一部分学习机会。自己调过几天的 bug，与听 AI 解释有哪些坑，留下的理解不同。传统编程积累的许多经验，都来自亲自试错。

    现在我也使用许愿编程，断网时甚至会不知道怎样继续。但这种开发方式可能让人逐渐失去对软件内部的掌握。以前由人编程，通常遵循小步提交的习惯：一次只做一件事，便于审计、追踪、使用 git blame，也为回看和重放历史提供基础。

    如果 AI 每次提交都修改一两万行，几百次提交就造出一艘航母，人可能只知道：测试通过，基本功能能运行，飞机也能起飞。至于它怎样工作，内部设计有什么限制，就不清楚了。Agent 声称设计优雅、质量很高，这些评价究竟意味着什么？它还能怎样扩展？

    扩展能力往往要等到新需求到来，才会暴露。模型可能诚恳地道歉，说此前对架构的理解不充分，但道歉之后仍然修不好。只了解软件的外在表现，会让后续维护困难。

    这门课仍然面向接受过计算机专业训练的同学。亲手写操作系统、编译器和数据库的经验，在这个时期仍然有价值，值得静下心来学习。即便人已经无法掌握 AI 生成的全部实现，也仍要对软件质量作出承诺。质量保障在 Agent 时代变得更加重要。

    今天主要讲测试，以及调试的一项基础理论。这部分内容在计算机系统基础课中就会讨论，操作系统课有时也会讲，具体取决于课时安排。先问一个每天都在面对的问题：什么是 bug？如果软件是物理世界过程在信息世界中的投影，缺陷又意味着什么？

    人和 Agent 都会犯错

    原片 00:08:00–00:12:00

    先承认一个前提：程序员也会产生幻觉，不能因为代码是自己写的，就相信它正确。计算机系统基础课会强调“机器永远是对的，代码永远是错的”，目的是提醒大家先检查自己的程序。写过考试题、调过很久才调通的人，都知道人的判断同样不可靠。

    相比传统开发，如今 Agent 的能力已经带来巨大变化。我们很快习惯了它，甚至会嫌回复慢、服务又降速。回想 GPT-3.5、GPT-4 的时期，模型已经掌握大量知识，但在软件维护任务上仍容易失败。给它一段代码，让它提供能修复问题的 patch，它会认真写出补丁，应用之后却修不好。

    课件回顾了早期 SWE-bench 上的结果，包括 GPT-3.5、Claude 2、Claude 3 Opus，以及当时的 Llama 系列等模型，解决率还很低。不过，人在批评模型犯错时，也要看看自己。人最常见的一类错误就是手滑：即使已经熟练使用 Shell，也会输错命令、参数或文件名。

    图 3：00:08:40，早期 SWE-bench 结果：程序员与模型都会出错。

    大模型流行之前，就有工具专门修正 Shell 命令错误。课上打开的 thefuck 项目已有多年历史，最近的开发活动很少。它的用法很直观：刚才的命令运行失败，用户再输入一句粗口，工具就读取 Shell 历史，用一组匹配规则识别常见错误，再给出修正。我今天没有现场安装演示。

    人会犯很多错误，但人也是 reactive agent：看到反馈，就调整行为、快速修复。如果不给编译器、不允许运行程序，要求一次写对，很多人同样做不到。不能只看模型第一次输出的错误，就忽略人类也是依靠反馈完成任务的。

    当然，人和模型的错误分布不同。接受过良好训练的人，在架构设计上可能更稳定；到了具体代码和命令，仍然会出现各种疏漏。

    图 4：00:10:40，现场打开 Shell 错误修正工具 thefuck。

    Fault、Error 与 Failure

    原片 00:12:00–00:20:00

    即使只是从 1 数到 300，人也可能因为短时记忆出错。写循环时也类似：外层是 for (i = 0; i < n; i++)，内层准备写 j = 0、j < n，最后却把递增变量也写成了 i++。注意力被上一行吸引，就可能发生这种手滑。可以借用 self-attention 来类比这个现象，但人的错误并不限于这种情况。

    这样的代码缺陷称为 fault，也常叫 bug。它可能是拼写或变量写错，可能遗漏一种情况，也可能整个算法就不正确。

    如果把错误藏在一百行代码里，肉眼不一定能立即发现。脑中已经有了“输入、预处理、二重循环、输出”的设计，扫一眼实现，就容易觉得它符合预期。

    图 5：00:12:40，二重循环中误写递增变量的板书。

    我们倾向于相信眼前代码与脑中的设计一致。Agent 也会犯这种看起来很简单、甚至会被人嘲笑的错误。每天 GitHub 都有大量修复提交，说明软件中持续存在缺陷。为什么这些 bug 难找？

    静态看代码时，整体结构可能满足要求；只有把程序执行起来，具体状态才会出现。初始 i = 0，随后进入内层循环，得到 i = 0, j = 0。循环体第一次执行，例如 sum++ 后变成 1，这一步可能符合预期。

    接下来我顺着正常循环的思路，先说它会到 i = 0, j = 1，再继续往后。这里需要马上纠正：内层写的是 i++，它根本不会按这个顺序变化。

    图 6：00:14:40，循环代码与执行状态的对应。

    第一次内层迭代结束后，实际状态就变成了 i = 1, j = 0。刚才连我也顺着脑中的正确循环说错了。要求的执行顺序应该先保持 i = 0，让 j 从 0 变化到 n - 1，再进入下一轮外层循环。

    此时，程序实现与 specification 已经不一致。规格可能没有写下来，也可能写得不够清楚，但我们对程序要做什么确实有要求。缺陷难以从纸面上识别，正因为实现与真实要求的差别可能非常细小。

    缓冲区越界、下标计算错误、整数溢出，也可能藏在这些细节中。比如用无符号整数记录余额，如果某条错误执行路径允许从 0 扣去 100，数值可能回绕成一个很大的正整数。代码执行后，状态已经偏离要求，这样的错误状态称为 error。接下来还要把它与 fault、failure 区分开。

    图 7：00:16:40，Fault、Error 与 Failure 的区分。

    fault 是实现中的缺陷；只有在一次具体执行中触发，才会形成 error。代码有许多执行路径，有些可能一直符合规格。单元测试通过、系统能启动、航母上的飞机能起飞，都只说明相应执行表现正常。

    难点在于，error 往往不会主动报告自己。CPU 按指令运行，遇到 load 就读取，遇到 store 就写入，并不知道程序员希望二重循环怎样推进。错误状态形成以后，程序还可能继续执行很久。

    循环运行几秒，i 已经变得很大，j 仍然是 0。此时人才察觉：这个测试本应很快结束，为什么还在运行？当错误变成可以观察到的失效，才称为 failure。

    图 8：00:18:40，错误状态如何继续传播到可见失效。

    缺陷的触发条件与火箭事故

    原片 00:20:00–00:24:00

    缺陷有一条传播路径：程序员写入 fault，合适的执行触发 error，错误继续传播，才可能出现 failure。程序员通常已经尽力，却没有意识到自己写错了。

    触发还需要条件。假如错误分支只有在一个随机值恰好等于特定数字时进入，测试很多次也未必覆盖。即便进入了错误状态，也未必影响可见结果。例如越界写覆盖了一块在这次执行中没有使用的栈内存，程序仍可能正常输出；没有专门检查工具，就很难发现。

    程序有 bug，不保证这次执行出现 error；出现 error，也不保证能看到 failure。维护 specification 与 implementation 的一致性，一直是困难的问题。课件接着用 1996 年 Ariane 501 火箭事故举例：起飞后仍在运行的一段对准代码，进行浮点数到 16 位整数的转换，却缺少范围保护，最终触发异常。

    这个缺陷一直存在于代码里，却没有在发射前的审查与测试中暴露。执行达到特定条件后，越界转换才触发异常。我推测，测试没有充分覆盖当时的完整运行情形；具体事故过程还需要结合课件中的调查材料理解。

    系统虽然设计了异常处理和容错，仍未正确应对这个情况，错误的控制信息最终导致了严重事故。它还有主、备惯性导航系统，但两套系统使用相同的软硬件。冗余可以应对部分偶发故障，却可能被相同的软件缺陷同时击中；两套系统几乎同时停止工作，备份也就无法接管。

    规格本身也可能不完整。“程序不应崩溃”听起来明确，但哪些异常可能发生、每种异常该如何处理，必须进一步说明。团队努力维护规格与实现的一致性，仍可能遗漏这些情况。

    先用语言与架构减少缺陷

    原片 00:24:00–00:30:00

    开放系统会与外界交互，传感器可能出错，异常也可能发生。不能只要求“不要有异常”，还要规定异常发生后该怎样处理。道理容易讲清，实现却很困难。

    承认寻找 bug、测试和调试的困难之后，才有必要讨论系统化方法。但提高质量，首先仍应选择合适的架构、语言和编程方式：减少容易误用的机制，采用防御性编程。测试数量无法替代这些设计选择。即使为火箭开发软件、投入大量审查，团队仍可能遗漏缺陷。

    Java 迅速成为主流面向对象语言，一个原因就是把许多指针相关的未定义行为从普通程序员的工作中移走。相比之下，C/C++ 提供直接操作指针的能力，也把相应责任交给了开发者。

    在 C 中，可以进行整数与指针转换、解引用，也可以借助函数指针组织类似面向对象的结构。这些机制很灵活，同时容易误用。

    动态内存管理包含明确约束：一次成功的分配，在需要释放时必须有对应的 free。程序可能有多条分支，提前 return 时容易忘记清理；setjmp、longjmp 等控制流又增加了复杂性。无论走哪条相关路径，都要正确处理这份资源，避免漏释放或重复释放。

    释放之后，也不能再通过原指针访问那块内存，否则会产生 use-after-free。释放的内存可能被重新分配给其他对象。若仍持有旧指针，就可能读写新的对象，甚至访问敏感数据。例如系统把用户数据或密钥相关内容放到这块内存里，旧指针就可能带来安全问题。

    图 10：00:26:40，质量保障的基本方法与内存管理板书。

    “分配后正确释放，释放后不再访问”说起来简单，在复杂控制流中却很难始终做到。不同入口、分支、返回路径交错，连熟悉代码的程序员也会疏漏。不能把全部正确性都寄托在一个会输错 Shell 命令的人身上。

    对 Linux 等遗留系统中的内存安全问题，研究已经持续多年，今天仍可以研究怎样发现 use-after-free。托管运行时则通过改变编程方式，减少这类负担。Java 付出一些运行成本，换取普通代码不必自行维护这些指针规则。

    它仍有空引用问题。Tony Hoare 用“billion-dollar mistake”形容空引用设计带来的代价。但 Java 中访问空引用会产生有定义的异常，例如 NullPointerException；外层也可以捕获并处理。程序员仍然要处理错误，却不必同时担心任意指针访问导致的未定义行为。

    课堂作业出错，通常只是扣分，甚至可能没被发现；为火箭写程序时，显然不能采用同样的质量标准。

    代码审查、测试与检查

    原片 00:30:00–00:36:00

    如果每次解引用都要考虑内存是否仍然有效，认知负担就很大。编程规范也能帮助减少错误，例如 Linux 代码常把资源释放集中到清理路径，通过跳转统一处理。选择合适的技术路线同样重要：Safe Rust 的类型与借用规则，可以消除许多内存安全问题。

    这些措施仍无法消除所有 bug。今天主要讨论测试，不过先介绍一种可以直接尝试的 Agent 用法：找一个成熟项目，再对照缺陷类型数据库，让模型检查某一类问题。例如明确要求审查 use-after-free，比笼统说“看看有没有问题”更有针对性。

    也可以把几类问题放在同一轮审查中。检查范围和投入成本有关：想发现哪些问题、愿意消耗多少资源，可以自行选择。

    即使有经验的程序员，也很难始终集中全部注意力。最好的一档程序员仍可能在某个条件下写错。让 Agent 对照已知缺陷类型检查，就有机会发现此前被遗漏的问题，包括只在特定条件下触发的逻辑错误。

    可以把审查投入想成一个滑杆。轻量做法是让一个模型写、另一个模型看，例如 GPT 与 Claude 相互检查，确实可能找到问题。更严格的做法，是按问题数据库逐类审查。对安全要求很高的软件，可以投入更多资源。

    接下来回到系统方法。fault、error、failure 的区分看似只是几个术语，却指出了两个可以改善的环节：怎样让潜在缺陷进入错误状态，以及怎样让错误状态变成能观察到的失效。

    从 fault 到 error，需要能触发问题的输入；从 error 到可见的 failure，需要合适的检查。希望发现更多问题，就要围绕规格生成输入，覆盖不同情况，同时检查运行状态和结果。

    只有大量输入还不够。假如所有错误状态都触发了，却没有任何检查指出它们，测试仍可能看起来正常。程序未必崩溃，也未必访问非法内存；它可能只是算出一个错误整数。

    动态规划题就容易遇到这个困难：样例能通过，随机测试数据也很好生成。例如输入一个 n 和 100 个整数，程序输出 1384。它没有崩溃，但这个数字究竟对不对？没有判断依据，单纯增加随机输入并不能解决问题。

    把测试接入开发流程

    原片 00:36:00–00:40:00

    需要找到合适的检查方法，并决定在哪个位置检查。这里既有系统方法，也需要经验判断。之后会专门用一课讲检查，今天先讲测试。

    运行样例，是大家最熟悉、成本也很低的质量保障方式。刚学编程时，常常运行程序、打开终端，再手动复制粘贴输入。重复很多次之后，才会意识到可以用管道、构建规则或 IDE 自动任务，把编译和运行测试连在一起。

    按一个键就能编译并运行样例或自建数据，质量保障便自然进入日常开发流程。大学阶段的成长，也包括逐渐发现这些重复工作值得自动化。

    图 13：00:37:20，从运行样例到环境与依赖管理。

    顺着这个思路，就能理解 CI/CD 中持续集成的价值：编译后自动测试，通过时继续工作，失败时及时报告。需要参加编程机试的同学，也可以预先熟悉这种流程。花一点时间配置编译、运行，甚至保存后自动执行，能节省反复操作的时间。

    真实系统的测试更复杂。算法题通常有比较明确的输入和输出要求；实际软件要在真实环境中运行，还要正确反映物理世界中的过程。

    自己的环境与别人的环境可能不同。Windows 上能运行的代码，在 macOS、Linux 上是否也一样？过去写网络程序，还常常要面对机器字节序的差别：有的机器是大端，有的是小端。

    环境、字节序与非确定性

    原片 00:40:00–00:46:00

    假设一个整数占四字节，值是 0x12345678。内存可以看作字节数组，那么从低地址向高地址排列时，大端顺序是 12 34 56 78，小端顺序是 78 56 34 12。

    可移植性问题常来自对底层表示的假定。按数值取低八位，与直接读取内存中的第一个字节，是不同操作：对无符号整数使用 % 256 或 & 0xFF，取的是数值低八位；直接读取第一个内存字节，才依赖字节序。网络程序经常需要在主机字节序和网络字节序之间转换。

    编译器、运行库、机器平台都可能不同。现代语言与运行环境替开发者处理了不少差异，JavaScript 就让许多应用无需直接面对这些底层问题。

    图 14：00:41:20，四字节整数的两种内存排列。

    例如在 macOS 上生成一个 Three.js 游戏，通常也希望它在 Linux、Windows 的浏览器里运行。运行时屏蔽了部分平台差异，但 JavaScript 也无法解决所有环境问题：第三方库不同版本的行为，仍然可能改变。

    我曾被 Python 的 lxml 库困扰。它用于解析 XML；Agent 编辑 Word、PowerPoint、Excel 时，也可能借助它修改文件内部的 XML。这个库曾在版本变化后，对某些 Unicode 字符的处理不同，原本能工作的程序就开始报错。代码仍然只是导入同一个库，环境却已经变了。

    如果要求在任何环境、任何输入下都符合规格，光运行环境就需要大量探索。即使两边环境完全相同，两次执行也可能因 API 返回、系统负载等因素而不同。顺序程序通常描述指令先后，并不保证每一步在何时完成。

    图 15：00:43:20，程序正确性与 specification。

    除非有相应的实时保证，普通操作系统不会承诺某条指令一定在下一毫秒执行。系统变慢，可能触发超时；原来来得及处理的有限队列，可能被填满，进而丢弃数据。同样的输入，也会因为执行时机不同而出现不同结果。

    网络延迟、中断、线程调度，都属于需要考虑的因素。操作系统课会讲一个放射治疗设备的并发事故：操作较快时，系统内部状态出现不一致，导致过量照射并伤害患者。这里不展开事故细节，但它说明非确定性也是输入的一部分。

    寻找环境、构造输入、检查功能正确性，本来就已经困难。再退一步，即便能生成规格允许的所有输入，运行结束后，也未必容易判断每个结果是否正确。

    测试为什么仍然有用

    原片 00:46:00–00:52:00

    此外还有非功能需求：不能崩溃、不能出现内存安全错误，性能和安全性要达到要求。产品还可能需要满足无障碍要求，让听障、视障等用户能够使用。不同环境和输入下，这些条件都需要考虑。

    Dijkstra 在《The Humble Programmer》中强调，测试可以显示缺陷的存在，却无法据此证明缺陷不存在。前面的传播路径一旦走通，发现一个 failure，确实能帮助改善质量；但通过若干测试，不能等同于证明所有执行正确。

    尽管有这些困难，测试仍然很有用。要理解它的价值，可以把规格、环境和输入形成的空间画出来，再看系统测试实际关注其中哪些点。

    图 18：00:46:40，测试能显示缺陷存在，无法证明缺陷不存在。

    系统测试通常优先覆盖最重要、最典型的业务场景。这些场景表现正确，会增加我们对正常使用的信心。程序员通常是为了满足整体需求编写程序，期望同一份逻辑能够推广到更多输入。

    当然，也能写出只对测试数据有效的程序。比如考试时，针对某几个已知输入直接输出答案，这就是对测试用例过拟合，没有泛化能力。但正常的软件开发目标是实现需求说明书，而非只应付已知样例。

    当程序按整体需求设计，又通过许多有代表性的场景，就有理由对相近情况建立一定信心。这仍留下许多问题：极限性能下是否可用，调度发生变化时是否正确，与其他程序交互或换到另一台机器时是否还能工作？这些边界需要继续检查。

    图 19：00:48:40，规格、环境与输入组成的测试空间。

    换一台机器、与其他程序交互后，它还能正常工作吗？没有这些场景的测试，我们就缺少相应信心。但正常程序本来就是为了泛化而写的，所以每通过一个测试，也会让我们对与它相关的一类行为多一点信心。测试只能说明 bug 的存在，不能证明完全没有 bug，但仍能不断增强信心。

    失败的测试还会提供有价值的反馈：哪里出错、运行到哪一步出错。这让我们回到调试循环，知道程序里存在 fault，再根据错误信息缩小范围。例如 NullPointerException 的调用栈，往往让我们优先检查空指针使用位置附近的代码。错误也可能在很早时埋下，经过很长执行过程才暴露，但更常见的是某个值刚算错，在不久之后使用时就出现问题。

    可以把这些信息理解成条件概率：已知程序有 fault，又看到特定的 test failure，就能更准确地猜测 fault 在哪里，排除与本次失败无关的部分。

    用失败反馈定位与修复问题

    原片 00:52:00–00:56:00

    有了失败测试，就可以逐步检查执行过程中的状态。假设状态一旦出错，后续一直带着这个错误，那么可以对 trace 做二分：检查中间状态，正确就往后找，错误就往前找，直到找到第一次从正确状态转为错误状态的操作。程序不断进行状态迁移，引入这次错误的语句很可能与 bug 有关。

    回到刚才的例子，代码把 i 从 0 变成了 1，而我的意图是把 j 从 0 变成 1。于是 i 的状态错了，修改 i 的这条语句就是 root cause，修正后问题也解决了。这种定位并非百分之百成功，但失败用例通常能提供很多有用信息。

    相关论文也很早就出现了。这里的 SWE-agent 论文是 2024 年的，arXiv 编号以 2405 开头，早于 Claude Code 产品的开发。我相信 Claude Code 借鉴过这类工作。2024 年 GPT-4 展示出较强能力后，大家开始尝试让 agent 参与修 bug，形成通过 ReAct 循环不断获取反馈的探索。

    图 21：00:53:25，SWE-agent 论文与反馈驱动的软件修复。

    例如把测试运行失败的结果交给 agent，让它继续修改 patch。随着尝试次数增加，修复成功率确实会上升，虽然当时还远达不到今天的水平。这些工作很有前瞻性，不过那时谁会成功还不清楚。我自己看论文时也没那么看好，因为还没有形成 scaling law 的判断。

    相信模型会继续扩展的人，赌的是这条成功率曲线能随模型能力不断上升。Claude Code 背后的选择也是如此：通过强化学习和后训练，获得更强的 coding 模型，更准确地从测试失败定位原因。大模型表示一种概率分布，训练可以让它逐渐接近正确的判断，学会测试与调试的过程，而这一过程由数据驱动。

    其实大模型出现前，软件工程已经很清楚测试应该从局部走向整体。做 OJ 时通常只跑 system test 或验收测试，把动态规划题的一大串输入放进去，检查输出。可 bug 可能只是很低级的局部错误。一个有 100 万行代码的系统，就更需要分别测试小模块。

    用例设计与覆盖率

    原片 00:56:00–01:02:00

    局部测试能及时暴露小模块的问题。系统测试则主要检查模块连起来以后，协作机制是否正常。用一次昂贵的 system test 发现本可由 unit test 找到的小错，会浪费更多时间和钱。

    人容易偷懒，想把系统整体跑一遍再看；模型也会这样。它有信心时，可能一次写出两三千行代码，不留单元测试，直接跑系统，甚至只截张图看一眼，就说完成了。但真正做工程，按层次测试通常成本更低。

    测试也可以分为黑盒与白盒。OJ 很典型地体现了黑盒测试：只看输出和可观察行为是否正确，有没有 hang、timeout。一次通过以后，结合程序的泛化能力，我们会对附近的一类输入多一些信心。设计用例时，还要关注容易出错的边界，例如数组长度为 0、1、允许的最大值，以及 -1 等非法输入，也可以使用决策表、状态转换表等方法。

    图 24：00:57:20，黑盒测试：等价类、边界值、决策表与状态转换。

    把测试想象成发射子弹：每生成、运行一个输入，就在执行空间里探测一次，但每次都有成本。单元测试便宜，可以多跑；系统测试昂贵，数量通常少一些。目标是在有限成本内覆盖足够多的输入和行为，建立对软件的信心。

    我们还可以从代码出发，统计一次执行经过的语句。比如 Test 1 覆盖第 1、3、6 行，Test 2 覆盖第 1、3、9 行，而所有测试都没走到第 7 行，那就没有建立对第 7 行的信心。我常开玩笑说，计算机系统里“未测代码永远是错的”。语法错误可能被编译器发现，但能编译的逻辑错误仍需要测试暴露。

    于是有了语句覆盖、分支覆盖、路径覆盖等指标：希望每条语句至少被执行一次，每个条件的不同分支都走过；有时还需要区分循环一次与两次，因为它们可能触发不同的行为。

    图 25：00:58:40，白盒测试：覆盖与结果断言。

    今天大模型生成测试用例已经相对容易。理解了这些概念，就可以要求它为项目建立合适的单元测试，统计覆盖率，对未覆盖部分报警，甚至继续补充用例直到覆盖率达到 100%。过去这些往往只有严肃的软件项目或大公司的管理者才会要求，写完代码还得补测试，对人来说负担不小。

    但某个测试真可能救你一次。当前路径看起来没问题，别人组合调用这段代码时，却可能从另一条路径触发错误。覆盖要求就是一种防御性的工程约束。今天可以把期望说清楚，让 agent 帮忙执行。

    测试金字塔、mock 与回归测试

    原片 01:02:00–01:06:00

    顾客问：“洗手间在哪里？”酒吧却突然崩塌起火，程序 crash 了。

    这位测试工程师并不敷衍，负数等边界确实可能让程序出错。但他的测试都围绕 order something，在一个功能上反复探测，没考虑另一个入口。程序的输入空间很大，未想到的场景仍会出问题。GPT 有时又会走到另一个极端，为每种非法输入分别写大量防御性检查；对某些任务，统一抛出一个异常可能已足够。

    我们的信心来自对现实过程的理解，以及是否覆盖了其中可预见的情况。我自己做测试研究，教材讲的原则大体都对：大量快速单元测试、适量集成测试、少量端到端测试。预算有限，就要分配成本。必要时可以用 stub 或 mock 替代真实环境，例如程序要取当前时间、读取文件、接收网络数据时。

    假如为智慧教室开发软件，需要接收摄像头发来的画面，难道每次系统测试都得连上一台摄像头？初学者可能因此不愿测试，因为连接设备费时、麻烦。测试经验会提醒我们，可以做一个假的设备，持续提供图像。

    Android 的 AVD，也就是 Android Virtual Device，就体现了这种办法。没有手机也能开发应用，它提供模拟摄像头。早期打开摄像头可能只能读到静态数据，后来才支持传入视频，但静态输入也足以让不少应用流程运行起来。例如申请摄像头权限、打开相机、拍照、关闭相机，这些代码不应完全依赖真机才能测试。

    原则就是尽可能让每一份测试成本转化为对正确性的信心。还有 regression test，回归测试：一旦修改代码，原来测试对相关行为建立的信心需要重新检查，受修改影响的测试应当重跑，再从局部逐步走向整体。

    架构决定质量

    原片 01:12:00–01:20:00

    我的 prompt 大概只有一句：“实现一个相对精美的 CS。”没有详细设计，也几乎没有配置 skill，用的就是 Pi。它的完成度不错，却仍有很多 bug，交付质量显然不够。相比之下，前面那个 ESP32 项目可能更简单，交付质量也高一些。

    系统越大，整合测试成本就越高，而有些问题必须让模块跨过接口边界协作，才可能暴露。对我来说，质量保障最重要的一点是架构决定质量：各部分应尽量能够独立验证。

    例如假设要做智慧教室的人脸识别与到课监测。最近大家在讨论这类系统，我没收到本校官方消息，只是拿它举例。若采用 event bus、event sourcing，人脸模块与到课模块就应有清晰边界，使每个子系统能单独测试，并独立建立正确性信心。

    图 37：01:12:03，CS:THREE 项目的开发记录。

    图 38：01:13:20，系统越大，整合测试成本越高。

    人脸模块可以面对一万张或一百万张图像的 benchmark，检查识别效果、输入格式、帧率与性能。它向到课模块传递人脸向量，到课模块则针对输入向量验证自己的输出，最后再接入 event bus。接口足够清楚，每个模块才容易分别验证，这需要好的架构。

    刚才那个游戏引擎完全由 agent 自行设计。我现在问它，为什么会出现悬空、穿箱子等问题，是否与设计有关。它当然有设计，但在我只要求游戏效果的情况下，未必会优先构造一个便于验证的物理引擎。

    如果由我设计，会希望每个物体、每个部分都能用代码单独检查，不必每次靠截图。Agent 从某个阶段开始大量截图，然后直接下结论，这种验证方式就很难覆盖所有情况。

    我再举一个童年老游戏《红色警戒 2》中的架构问题。这个游戏里有许多离奇 bug，有些很晚才被发现，例如船厂能修飞机、维修厂能卖步兵，现代 CS 游戏引擎里很难想象这种组合。

    纯函数与独立验证

    原片 01:20:00–01:24:00

    为什么喜欢 functional design、函数式编程？纯函数比较容易验证。假设一个函数里先调用 global.get，过一会儿又调用一次，那么正确性就依赖全局状态：对所有可能状态、所有执行路径，都要考虑它能否工作。

    如果放在 CS:GO 这样的系统里，测试前可能还要构造或 mock 整个相关环境。即使模型能帮忙，这仍有成本。还得考虑并发：两次读取之间是否有人修改状态？哪些全局状态可能发生，哪些不可能发生？这些都会增加思考与测试负担。

    纯函数则像数学函数，没有副作用，相同输入 x 总会给出相同结果。其行为主要由自己的输入与实现决定，单元测试更容易组织，也更容易分析正确性。

    图 43：01:20:40，全局状态与纯函数的测试成本。

    针对这样的函数，充分的单元测试能提供信心，形式化证明也相对容易。Rust 的价值也不只在于严格的生命周期要求：编译器会迫使你重新思考哪些状态应该放到全局，使你更倾向于清楚的 functional design，或明确地把对象交给对方处理、再取回结果。引用计数等常见模式也能帮助管理共享对象生命周期，这些设计更容易测试。

    函数式设计同样有限制。组合高阶函数时，参数可能是函数，返回值也可能是函数或 lambda，各函数的 specification 仍然会互相依赖，仍要明确谁负责什么。偏向函数式设计能获得收益，却不能自动解决所有问题。

    对我来说，优先原则仍是架构决定质量。架构清楚以后，许多常规测试工作可以按教材要求交给 agent。除此之外，质量保障与编程一样，还需要经验和灵感，也就是模型尚未完全学会的品位。

    从 NEMU 到差分测试

    原片 01:24:00–01:30:00

    我相信模型会继续进步，只是好架构的反馈周期较长。快速堆代码，前期生产效率很高，需求增长到某一点却可能无法继续维护；好架构一开始搭结构、做验证，效率看似更低，要到后期才体现持续扩展的优势。强化学习完成眼前任务就能得到奖励，未必能及时获得长期架构的反馈，刚才 DeepSeek Flash 的选择也与此有关。

    质量保障还可以从具体问题出发提出新办法。例如 Differential Testing。计算机和人工智能专业做过 NEMU 的同学，可能都经历过这个实验：实现 RISC-V 或 x86 全系统模拟器，带声音、图形和外设，构成完整计算机。

    大约 2013 年，子豪同学在毕业设计中实现了最初的 NEMU，很快就变成计算机系统基础实验。第一批学生当然苦不堪言，要把这样的系统调对并不容易。

    图 45：01:24:00，灵光一闪：质量保障也依赖经验。

    图 46：01:26:40，NEMU 与《仙剑奇侠传》的运行画面。

    当时只有子豪手里一个能运行的版本，它未必完全没有 bug，但至少可以展示《仙剑奇侠传》，相关固件也准备好了。学生缺少辅助工具，调试自然困难。

    大概在 2013、2014 年，或 2014、2015 年，我们在学院楼下的咖啡厅聊天，讨论能不能减轻这种困难。我提了一个想法：把 CPU 做成可插拔的动态链接库，接口类似总线，包含握手、数据进出、中断等。将 CPU core 与外围设备分开，同一套外设状态就能接两个 CPU 实现。

    我们把同样的状态送给两边，保留同一次外设交互的结果，用来比较执行行为。当时选 QEMU 作参考：把寄存器和内存状态送进去，让 QEMU step 一条指令，再导出结果。那时主要是 x86，今天 RISC-V 版本的组织稍有不同。

    QEMU 已经能跑 Windows XP 等复杂系统，我们把它视为 golden version，相信它在相关行为上的结果。它跑一步，NEMU 也跑一步，再逐项比较，定位问题就容易多了。

    图 47：01:29:20，两个 CPU 实现共享外设并比较状态的板书。

    比如程序看起来能运行，EFLAGS 中却有一个位算错了。Zero Flag 表示结果是否为零，Parity Flag 也有自己的语义。单个测试可能恰好没触发问题，或者错误要在两条指令组合时才显现。两三千行模拟器代码看起来都在解码、计算、执行，光靠最终输出很难找到问题。

    Differential Testing 能更早暴露状态差异。EAX、EBX、EFLAGS 等寄存器原本只算出了一个值，没 crash 就只能猜它对；有参考实现以后，立刻知道哪条指令之后 EFLAGS 不一致，查手册便有了方向。这与前面“找到首次错误状态”的调试思路相通。

    编译器也能做差分测试，但 C、C++ 有 undefined behavior。两个编译器生成的程序输出不同，可能是编译器 bug，也可能是源程序本身触发了未定义行为。生成测试程序时就必须约束这一点，问题会复杂一些。

    昨天看到一条朋友圈提到 DiffTest，还向包老师致敬。它让我想起，当年这个机制也是大家聊天时提出愿望，再逐步做出来的。

    用 fuzzing 自动探索输入

    原片 01:30:00–01:34:00

    最早与 QEMU 对接的实现由子豪完成。原本的目标是帮助计算机系统基础实验，后来才用于龙芯杯等场景。2019 年第一期“一生一芯”也采用了这类机制，此后不断改进。今天还能借助 FPGA 等硬件加速比较过程：CPU 执行可以由软件模拟，也能由硬件模拟，从而更快地与参考实现对照。

    再看另一条路。测试要探索输入空间，能否写程序自动探索？这就是搜索问题。假设 a.out 接收四个参数 S1、S2、S3、S4，还读取文件 a.txt，其中内容是 S5。若文件限制为 100 字节，四个参数各限制为 10 字节，就能把这次执行的输入编码成一个 140 字节序列。

    在这个受限模型里，若遍历所有 140 字节序列，就能把对应输入都运行一遍。是否正确仍需要另行判断，但至少执行过了。问题在于，穷举极其低效。

    图 49：01:30:40，从 NEMU 到香山与一生一芯的 DiffTest。

    图 50：01:32:00，Fuzz Testing：探索输入空间。

    怎样更高效地搜索？可以维护一组输入，反复变异。它有些像遗传算法，也可以先理解为 iterative search：把一个字节从 A 改成 B，替换成程序中出现的常量，或者做 crossover，把一个输入前半段与另一个后半段拼起来。

    再用反馈判断哪些输入值得保留，例如是否覆盖了此前没走到的代码。这样的反馈制导测试，可以放到大量服务器上持续运行，不断寻找安全漏洞或功能问题。Linux 内核的 syzkaller 已找到很多 bug，其中一些还难以复现和修复。

    开源生态还有 OSS-Fuzz 等持续测试服务。软件发布后，除了开发者自己的检查，第三方也会持续扫描、fuzz，帮助使用者判断版本质量。这类检查同样会增加供应链投毒被发现的机会，试图削弱检查本身就需要警惕。

    图 51：01:33:20，输入编码、变异与搜索的板书。

    让真实硬件进入测试循环

    原片 01:34:00–01:37:05

    持续 fuzz 一段时间、运行大量用例而未发现问题，可以作为发布时的一项信心来源，但覆盖范围仍然有限，检查也必须真实有效。

    在生成式软件工程时代，大家需要的是架构知识、测试的基本原理，以及从多年软件实践中积累的经验，再把它们迁移到自己的项目。你的系统未必需要 Differential Testing 或 fuzzing，但这些例子可能启发你写一个更好的定制输入生成器，覆盖更大的测试空间。

    想清楚以后，才知道该向 AI 提什么要求。至少当前的 agent 未必能替领域专家完成认知之外的设计，需要人提供方向。我很喜欢 Android 团队的一个例子：Sam Mehat 发现 G1 的 SD 卡插槽所用 Linux 驱动不稳定，后来甚至重写了驱动，但验证它还需要反复拔插 SD 卡。

    仅靠模拟还不够，即使 QEMU 中通过，也未必反映真机问题；当时的模拟能力也有限。于是他们做了一个物理装置，其中一部分由 3D 打印完成。软件给舵机发信号，就能反复拔插 SD 卡，让真实硬件进入自动化测试循环。

    今天我们也能把想法做成实物。我家小朋友设计了一个光栅动画小物件，拉动时能看到动画。只要提供四帧动图，就能自动拼成对应图样；卡扣可以扣在钥匙扣上，拉开后还能换一张 5 厘米 × 5 厘米的照片。

    现在很多事情都可以“许愿”，前提是先有正确的概念。今天就到这里。
