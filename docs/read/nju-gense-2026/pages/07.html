    选数据库的那一刻，债就背上了

    原片 00:00:00–00:04:03

    今天继续讲需求与架构。这两件事常常分不开：产品足够复杂时，intent、specification 和 implementation 之间就会出现 gap。瀑布模型提供了一种理解它的方式；沿着数据依赖构造 minimum viable product，则是在控制复杂性。

    上一节提到，代码之外有客户的规律，客户之外有社会的规律，社会之外有宇宙的规律。观察需求的位置不同，看到的内容也不同。我通过浏览器逆向了教务系统中与教师有关的需求，形成一份符合产品文档习惯的需求规格说明书。它只覆盖教师这一部分，还没有覆盖整套教务系统。

    架构师拿到这份需求，可能会决定选一个数据库，把全部功能实现出来。这样的产品可以完全满足客户眼前的要求，却可能在长期维护中陷入泥潭。任何设计从作出决定的那一刻起，就背上了一定的技术债。

    架构从十行代码时就存在，到了五十万、一百万、一千万行也一样。即使还没有代码，也必须作出决定；这些决定会影响后续方向，而最初的架构通常还有很大的改进空间。

    下一个实验这两天会放出来。做第一个实验时，可以把需求交给 AI，再通过对话不断修改。但如果第一反应就是设计数据库，值得先退一步想想：有没有更合适的方案？

    图 1：00:07，《Intent → Spec → Impl》。看似明确的需求，其实都有很多开放的空间。公平分配稀缺名额，可以落到同优先级抽签，也可以按紧要程度排序。让空余名额被利用，可以退课后候补递补，也可以到期释放预留。页底写着：未确认的假设可能使目标漂移，需要回溯原意。

    图 2：00:37，《架构无处不在》。从 10 行到 500,000 行：Tower of Hanoi、QRGen、教务系统（今天继续）。“脑子一热”的可行架构往往还有改进的空间。

    选课这件事，复杂是消不掉的

    原片 00:04:03–00:14:17

    Brooks 说，软件工程要驾驭复杂性。需求规格说明书展开后，现实软件会显得十分复杂，其中一些复杂性无法消除。这就是问题领域中的 essential complexity：选课涉及容量、先修、时间冲突、排课、教室，系统还要支持师生借教室。物理世界的复杂性投影到信息世界后依然存在，只能用架构去管理。

    技术债涉及另一类复杂性。选择数据库或文件系统，都要作取舍。文件系统便于直接修改，也方便组合 Unix 工具，但性能和并发处理可能不如数据库。它通常不提供跨多次读写的原子事务，无法保证这些操作 all or nothing，像加了一把锁一样整体完成。也有人尝试在操作系统中实现文件系统级事务。数据库能提供事务，调试时却多了一层间接访问，无法像文件一样直接接上各种 Unix 工具。查询理论上也能与工具组合，但交给 agent 后又多一层转换。技术选型带来的这些负担，就是 accidental complexity。

    长期观察不同架构，才能逐渐理解怎样减少 accidental complexity，以及怎样应对 essential complexity。需求工程直接面对后者：承认系统复杂，持续与客户沟通，把“到底要什么”弄清楚。可以让 GPT 写需求规格说明书，也可以使用追问需求细节的 skill。比如做购物车，它会问认证接微信公众号等第三方，还是自己做登录页。这类工具值得试试。

    每个选择都会带来后续问题。只告诉 GPT“我要登录”，它就会猜：先注册用户，再有用户名和密码，首次输入密码要确认，接着还要考虑忘记密码。用户忘记密码后，数据留在系统里却无法访问，于是需要短信或邮件找回，又要选择发送服务。看似理所当然的用户名密码登录，做下去会遇到大量细节。微信、支付宝登录更方便，却可能收费，并要求公司主体；个人与公司承担责任的能力不同，对个人开发者也就不够友好。仅登录就有这么多问题，进入系统后还有其他问题。

    探索需求可以深度优先，也可以广度优先。深度优先是尽快做一个 MVP，验证最重要的功能满足到什么程度、是否需要重做。广度优先是同时考虑登录方式、首页布局等不同需求点。两者可以结合，最终都要用某种形式把需求写清楚。

    代码本身也承载着需求。删掉项目文档，让大语言模型读代码、运行代码，也能还原出一份很长的需求清单。系统还可能有一套自上而下的设计哲学，例如尽量保持简单，把实现麻烦的功能交给第三方。也有人坚持自己管理用户名和密码，甚至想收集密码建立密码库；这不合规，但体量小的产品仍可能有人这样做。如何平衡深度与广度，需要动手比较不同设计。看完教务系统，可以想想自己会怎样实现。需求工程要靠多看、多做，今天还会继续看具体系统。

    需求之外，架构首先可以分解 essential complexity。无法消除的复杂性可以隔离到不同模块，通过接口划清边界。数据库就是一个例子：把数据交给它后，使用者依赖它提供的 contract，无须自己处理存储细节。云数据库通常还有备份承诺；故障期间可用性可能下降，备份接替后访问继续。可靠性和原子性由它负责，应用可以集中处理业务，也可以把部分逻辑下放到数据库中。

    自己的系统也需要模块划分。学校希望信息系统全部打通，让同一份信息只填一次。统一身份认证花了很长时间才打通，财务等系统仍未完全接入。没有领工资、管理项目或帮老师报销经历的同学，可能还没接触过这些系统。财务包含大量领域知识，也需要接受审计，整合确实困难；共享数据和推送通知仍有改进空间。需求与架构需要应对这些问题。架构可以收窄 specification 和 implementation 的选择范围。

    需求收窄 intent 空间中的不确定性。一个 intent 可以对应多种 specification，每种 specification 又有多种 implementation。需求约束意图，架构约束规格与实现；一旦作出选择，也就开始承担相应的技术债。

    这些概念可能仍然抽象。我最近重读了一些老论文，发现软件工程诞生初期乃至更早，人们就已经思考程序应该怎样构造。接下来打开《结构化程序设计》的 PDF 看原文。

    图 3：14:00，《需求工程：直面 Essential Complexity》。需求越完备，歧义越小。例子是“课程容量 100 人”：候补算不算，跨院预留名额能否借用。每个需求点都带来审计的代价。换到今天，是 token 开销，以及模型潜在的错误发挥。每补上一条约束，也多一条需要持续核对的承诺。

    人的脑袋很小

    原片 00:14:17–00:25:59

    书里讨论的程序规模与今天的软件工程不同。Dijkstra 还在画流程图，讨论顺序、选择、循环，以及是否需要 goto。当时关于“goto is harmful”的争论，有些只涉及一个小函数。他认为顺序、选择和循环足以表达程序逻辑。这些示例今天看起来简单，却已经体现出结构。书写得很好，今天也可以换一种方式来读。

    读书仍然必要，有了合适的 AI 工具，读书比以前容易了。前两天我给每位博士生的建议都是读经典。我研究操作系统、编程语言和软件工程；在我看来，1980—2010 年是这三个领域的黄金时期，后来研究逐渐变窄。当时许多系统尚不存在，人们提出大量设想，讨论怎样把它们建出来。

    最近 Cursor 提供了一些 Grok 额度，后面还有云电脑。我让它收集 1980—2010 年值得读的 systems 文献，它找出约一千篇，每个领域两三百篇。我读过其中大部分，核对后发现很多也在我的推荐范围内。现在开车时，我会打开 GPT 或 Claude 聊一篇论文。论文被索引后，AI 能看到全文；也可以直接把论文交给它。我教过一种读法：从已知知识向外扩展，弄清论文解决什么问题、使用什么未知手段、得到什么结论，再把它接入已有知识网络。这样的阅读能带来启发。

    Dijkstra 开篇谈的是“our inability to do much”。需求复杂，需要架构，也因为人的能力有限；可以把自己看作参数有限的大模型。他写道：“I have a very small head, and I had better learn to live with it, and to respect my limitations and give them full credit, rather than try to ignore them.”

    应对方式是抽象与层次分解。Structured programming 今天看似过时，后来有面向对象，前端又有 React 和 Vue，双方的争论像过去的 Vim 与 Emacs，尽管它们越来越相似。许多今天的问题，前人已经思考过。层次分解让人可以逐层理解那些无法一次理解的系统。

    书中讨论了三种 mental aids：枚举、归纳和抽象。示例虽然只是今天眼中的小程序，却体现了人脑处理复杂性的方式。他把构造程序比作串项链，将珍珠逐颗串起来，也就是把无法整体理解的东西变成可以逐个理解的部分。

    编程语言和软件设计的经典著作经常引用这本书。过去遇到这样的脚注，通常有两种选择：只记住 Dijkstra 写过它，或者花时间找原书来读。我读书时也面对过这种取舍。今天可以更方便地获取第一手材料，并按自己的方式阅读。

    1972 年的书里已经讨论 class、object，以及用于构造概念层次的协程。协程与线程相似。我上课常把线程比作一个人，把 shared memory 比作共同活动的物理空间：每个人有自己的记忆，知道工作进度和下一步安排，同时与其他人在共享空间里协作。通信需要协议，一个工作可以由三个协作过程完成，通过数据结构共享信息。书里用下棋和编译举例，构造出概念层次的金字塔。今天许多优秀系统所做的事，在这本书中已经有所讨论。

    操作系统课会介绍 coroutine。今天它更多被当作轻量级线程来提高性能，例如 Go 的协程使用方式接近线程，切换和 bookkeeping 开销较小。在当时，线程模型还不成熟。这些机制最初的设计，也是在应对软件世界的复杂性。

    图 4：16:00，他打开 Dahl、Dijkstra、Hoare 1972 年的 Structured Programming，停在流程图那一页。上面是顺序、选择、循环，下面是 Note on Structured Programming 第 19 页。

    图 5：19:31，《On Our Inability to Do Much》。引用 Structured Programming，1972。Dijkstra 说自己脑袋很小，得学会跟它相处，尊重自己的限度。图把注意力收成输入、处理、输出，细节仍在，只是暂时封装。

    图 6：21:01，《Our Mental Aids》。Dijkstra 的 Part I 讨论枚举、归纳、抽象。案例在今天看来都是小程序，necklace（pearls）的比喻是在分解复杂性。每一颗 pearl 承载一项独立的设计决策。决定的先后，会改变其他层必须知道多少细节。过早把 image 解释成 lines，中间各层就都要理解 lines。原文指向 On What We Have Achieved。

    模拟并行也一样。可以直接写状态机，也可以先建立 coroutine 抽象，把 wait、activate、simulate 分开。通过抽象表达模拟时间，与直接编写模拟程序，会得到不同的结构。对这些概念不熟悉，可以继续向模型追问。

    这个开场引出了编程语言的困境。相对于英语和用户需求，编程语言都很小，因为它必须具有可以在计算机上执行的形式语义。像 woman 这样的自然语言概念，很难直接赋予形式语义。但语言太小又难以使用，例如 Brainfuck 基本上只表达纸带上的左右移动、加法和判断，写一个 Hello World 都很费力。实用语言没有这么极端，C 却也因精简而有表达上的局限。它没有运算符重载，操作队列等结构不够方便；qsort 的比较函数接受 const void *，调用时还要提供 nmemb 和 size。C 缺少进一步构造语言抽象的能力，表达复杂概念时容易遇到困难。

    这与用单音节词定义多音节词的困难相呼应。小语言易移植，却可能无法满足增长的需求；一次设计庞大的语言，交付又太慢，成功前就可能被一个小而粗糙的语言取代。C 的成功与它贴近机器、额外抽象少、几乎能移植到任何平台有关。在主要靠人编写代码的年代，编译器本身就很复杂。语言提供哪些概念，也是一种架构选择。前面二维码例子里创建的小语言同样如此。架构既包括数据库选型、用什么 class 表示 student 和 course，也包括语言里有哪些概念。

    Unix Philosophy 有三条：每个工具 do one thing and do it well；write programs to work together；write programs to handle text streams。第三条用文本统一了人与程序、程序与程序的接口。二进制字节流对人不够友好；数据库虽然好用，每次查询都要经过 SQL，也会增加一层间接访问。人常常只想立即得到结果，对持续遵守额外规则并不擅长。模型则能接受类似“每句话后面加一个喵”的要求。McIlroy 在 1964 年就提出像连接花园水管一样连接程序。我记得管道到 1983 年前后才进入 Unix；动态链接等机制也深刻影响了今天的系统设计。

    Unix 建立了统一约定。The UNIX-HATERS Handbook 批评过它的许多设计，但命令行参数、输出格式和退出状态仍然构成了共同规则。sed、awk 奠定基础后，其他程序的输出逐渐兼顾这些工具与人的阅读。出错时，退出状态能把情况告诉下一个程序。这些约定加上管道，就形成了有效的组合机制。

    以打开文件的菜单为例，可以自己实现，也可以调用操作系统提供的窗口，但两者都可能不符合使用习惯。学校购买的办公软件自带打开菜单，能做预览，却也有难用的时候；系统菜单虽然集成了大多数常见功能，也未必合适。Unix 可以把编辑器与自己喜欢的文件选择工具组合。Vim、Emacs、nano 都可以，我这里用 nano，再接上自己的菜单。设计者未必预想到这种用途。我随便找第一课的 index，用 nano 打开。

    Shell 的文本接口、编程能力与 Unix 管道一脉相承，组合后就提供了大量复用空间。操作系统课上我常说，使用 Unix 时，每个人都是程序员：每条命令都是一个小程序，可以把各自做好一件事的工具组合起来。GUI 至今仍很难提供同样的可组合性。类似的开创性设计，也许今天仍能做出来。

    表、包，和一座一直在改的城市

    原片 00:57:38–01:03:40

    第二个例子是关系数据库。文件系统提供原始接口，能复用 Unix 工具，却缺少统一管理。关系代数为数据建立了一个模型。我曾研究程序合成，发现只要涉及人类世界的数据，就很难绕开 E. F. Codd 1970 年的论文：用二维表以及表之间的操作描述世界，join 等操作能够完成大量数据管理任务。存储方式和可靠性则交给数据库实现。

    关系代数之上有了 SQL。Unix shell、Bash 和 SQL 都是语言；一个系统具备生长能力时，往往也会出现某种语言形式。SQL、查询优化器和事务让二维表表示当前世界的状态，一次 transaction 把它推进到下一状态。还可以用查询构造视图，表达对世界的某一种理解。实现层继续扩展规模，图书、学籍、财务、商城订单都可以用实体及其逻辑关系来表示。数据库规定表与操作，具体 schema 由应用决定，这种抽象隔离了复杂性，也保留了扩展空间。

    第三个案例是 Internet。今天我一边上课一边推流，手机还能监看直播和弹幕。网络把世界连接起来，也给上层应用留下成长空间。TCP 解决可靠传输问题，让数据流从一个点送到另一个点；上层运行什么应用，可以继续扩展，无须提前规定。

    可以读 1996 年 6 月的 RFC 1958，Architectural Principles of the Internet。它强调变化本身是持续存在的原则。网络的目标是 connectivity，承载什么应用留给上层决定。一些数据中心仍用 TCP/IP，GPU 间通信则可能需要更合适的协议。网络要高效传输 datagram，同时处理拥塞控制、判断连接何时断开等必要细节，其他工作尽量交给上层。

    连接能力稳定之后，上层世界变化了许多。我读书时没有今天普遍的 HTTPS，网页使用 HTTP，还会通过 Telnet 登录南京大学小百合 BBS。后来安全需求提高，远程登录改用 SSH。当年校内用 FTP 下载电影，它支持断点续传，网络不稳定或中途暂停后还能接着下载。今天这些功能也能通过 HTTPS 接口实现。HTTPS 逐渐成为互联网服务之间的常用通信基础，再配合 REST API 等建议性规范。共同规则之上，局部实现不断更新，像城市交通网络保留下来，建筑持续改造。

    大学学习这些课程，一方面要掌握具体技术，例如离线时仍能自己写 SQL；另一方面也要理解经典设计为什么能支持长期发展。这里关注的是软件架构：它怎样应对变化，又怎样支撑一个生态。

    由此可以讨论 MVC，即 Model-View-Controller。我先说了 1972 年，更正一下，是 1979 年。这篇文章很短，大约两页。Models represent knowledge：谁选了什么课、有哪些订单，都是对当前世界的描述。View 是 model 的视觉表示，可以看作 state 的函数，而且希望它是纯函数。视图只负责展示，改变世界交给 controller。修改需求对应事务，展示需求对应状态的投影，各自职责清楚。

    MVC 很自然地成为信息系统的常见架构。教务系统中的 model 包括课程和选课记录，view 是页面，controller 接收按钮、输入框等产生的操作，再调用数据库事务。

    当界面只有 HTML 页面、每次操作都整页刷新时，这种划分比较直接。但今天界面还有大量不应进入业务数据库的状态，例如展开的菜单、搜索词和 hover 状态。教务系统的搜索通常要求输入后点击按钮，再发起一次数据库查询；如果学生列表已经在浏览器里，只需按姓名或学号过滤，就无须重新查询 model。此时业务数据没变，视图状态却变了。把 view state 也建模，就引出了 MVVM 等设计。

    与此相关的前端框架中，我更偏向 React。写过一些前端的人很容易理解它的 view。它希望把界面看作状态的投影：除了业务数据，还有 query string、hover 等页面状态。文本框绑定搜索词，视图也可以依赖它。接着定义一个没有副作用的纯函数，由全部界面状态计算 DOM tree。困难在性能：页面可能有几万个元素，搜索词每变一个字符就全部重算，代价很高。React 通过 virtual DOM 等机制处理更新，把这些复杂性藏起来，让开发者声明状态及其变化。

    Vue 更像构建依赖图，记录输入与输出的依赖并保持同步。新版本中两者似乎越来越接近，但我使用 Vue 较少，了解有限。它们都要求隔离复杂性，分别管理数据来源与展示逻辑。人的注意力有限，考虑状态时最好不必同时考虑怎样生成 DOM；状态确定后，再研究界面映射。两者都围绕状态驱动界面，更新方式有所不同。

    MVC、MVVM 仍然无法消除业务中的 essential complexity，长流程任务尤其明显。

    图 23：72:22，《MVC：让不同的变化各有归属》。Separation of concerns。最初面向交互式界面：同一个业务对象，可以有不同的展示和操作方式。教务系统里，Model 封装数据、状态和业务逻辑，不只是数据库里的几张表。View 是展示界面。Controller 接收用户输入，协调两边。课表从列表换成周历，主要改 View；选课限制变化，主要改 Model。

    图 24：72:50，《MVC：一次选课请求》。浏览器提交 POST /enroll。Controller 解析参数、确认身份、调用选课、选择模板。Model 检查先修、时间冲突和余量，在事务中验证并写回成功或失败。View 用模板把结果渲染成 HTML。选之前余量是 1，选之后余量是 0，按钮变成已选。

    图 25：73:18，《把 ViewState 也当成 Model》。View 等于 render(Model, ViewState)。展开的菜单、hover 的元素，通常不进业务数据库。课程数据没变，只改筛选词，显示的列表就变了。页上引用 Fowler 2004 年的 Presentation Model：是否持久化，和是否值得建模，是两件事。

    一条长流程，一个 status 列装不下

    原片 01:19:04–01:24:32

    假设设计一个淘宝式系统，下单后要锁库存、算优惠、等待支付确认，再经过风控、发货、退款、售后和对账。二维表可以表示当前状态，但订单走到哪一步，需要进一步建模。最直接的方式是在 order 表里加 status，用 1 表示下单、2 表示库存环节、3 表示下一环节，或分别记录是否下单、锁库存、支付。流程一长，状态机就会复杂，风控失败还需要回退路径。这是业务的 essential complexity。教务系统也可能出现类似问题：某个学生在一些条件下能毕业，在另一些条件下又不能毕业。特批可能覆盖正常规则，让流程在“风控失败”之类的状态下继续前进，留下难以解释的不一致。我相信教务系统中也有许多手工修改造成的数据不一致，只要没有影响毕业，就暂时搁置了。

    长业务流程同时涉及过去、现在和未来。当前状态只是快照，它由过去的操作推演而来。如果丢掉形成过程，出现不一致时就很难追查。

    记账提供了一个例子。支付宝能记录收支，严肃的会计则使用复式记账法：一笔交易同时涉及两个或以上账户，借贷金额相等、方向相反。只记一条流水虽然简单，却无法完整反映业务结构，也缺少自平衡校验。试算平衡能帮助发现不一致。除了流水，还需要资产负债表，列出现金、存货、固定资产、应付账款、短期借款和所有者权益等项目。如果要按会计法规记账，就必须生成这样的报表。我没有会计知识，怎样设计架构，才能把这些记账需求实现出来？

    图 26：83:06，《应对复杂性》。MVC 和 CRUD 解决了博客、社交网络、课程信息系统这类问题：业务对象比较稳定，一次请求完成一小段局部操作。长流程是下单、锁库存、优惠计算、支付、风控、发货、退款、售后、对账。强规则是修满学分、毕业设计、归还资产、特殊政策、毕业。会计账本写的是复式记账法。

    图 27：84:24，《复式记账：同一笔业务，保持会计等式》。公司向银行借入 10,000 元，记在同一张凭证上：借银行存款 10,000，资产增加；贷短期借款 10,000，负债增加。合计借方等于合计贷方。资产等于负债加所有者权益，所有者权益保持不变。借和贷是记账方向，不等于收入和支出。

    不记现在，记发生过的事

    原片 01:24:32–01:35:47

    我采用了 event sourcing，记录状态如何迁移。像一棵树，既可以记录现在的样子，也可以记录生长过程。账本中保存今天收入 1000、明天支出 1000，以及各自原因。我没有先设计数据库，而是让 AI 做一个类似编译器的小系统，从最终报表的条目中提炼记账动作。例如支付营业成本时，货币资金、所有者权益、应付账款和现金流量表怎样变化。这张规则表由 AI 生成，我选择相信它，并依靠后续校验发现问题。

    总体架构是用 LLM 做编译器，把持久化、不可篡改的历史记录编译成小操作。发生什么就记录什么，连“特批某位不满足条件的学生毕业”也要留下事实。每个操作规定资产负债表、利润表和现金流量表怎样变化，再按顺序 reduce、replay，得到当前报表。实现中还有小规模的架构选择：原来的代码很长，我用 currying 合并重复部分。给 payroll 固定一部分参数后，剩下的就是可调用函数。这是函数式编程中常用的技巧。每笔银行收支对报表的影响都定义好后，按时间顺序执行即可生成当前报表。

    用数据库维护当前状态时，一条逻辑出错或规则改变，都可能把正确状态推成错误状态。可生长的架构还要容纳对旧规则的修改，而直接迁移当前数据容易遗漏关联后果。比如更正成绩：学生要求查卷，老师发现一道空题当时多给了二十分，扣掉后由及格变成不及格。成绩修改会影响学分、毕业、准出以及后续课程的选课资格。原来通过计算机系统基础，才能选操作系统；现在先修课变成不及格，已经选上的操作系统该怎样处理？这些依赖本身就属于 essential complexity，简单修改一项数据无法自动保证其他数据一致。

    如果只维护当前状态，把成绩或是否通过从 1 改成 0 后，很难评估其他地方应做哪些修改。Event sourcing 要求把原始事实之间的依赖理清，再通过 replay 计算当前状态。记账条目编译成操作也会出错，但账目有人审核；发现翻译错误，可以修正规则并重新计算。选课同样如此：把“通过计算机系统基础”记为事实，简称 ICS，其他结果由它推导。事实变化后重新执行相关计算，即使采用自动数据流分析，也能看出哪些结论受到影响，因为依赖已经显式表达出来。

    Event sourcing 基于 replay，还可以用来推演未来。当前状态由过去决定，也就能从当前位置假设后续事件。例如订单走到支付环节，可以分别推演风控成功和失败的结果。记账系统也可以根据模型评估破产风险：假设多少应收账款无法收回，就可能破产。这些预测能力来自可重放的计算结构。

    它仍然无法消除 essential complexity：先修课和毕业条件的依赖已经存在。Event sourcing 把事实、视图与预期分开，世界没有按预期发展，就追加新的事实。例如领导特批某位同学毕业，也可以记录为一次明确的 override，无须让工程师直接修改数据库中的当前结果。

    图 28：84:36，《记账架构：Event Sourcing & LLM as a Compiler》。原始凭证走到分录，再走到状态变化。借贷平衡是可检查的约束，不代表业务真实，分录仍要核对凭证。下面是 curry 过的 pay_payroll：按类别从 PAYROLL_FLOWS 取出流水，个人劳务单独记一笔，再支付净额。

    现在是过去算出来的

    原片 01:35:47–01:39:41

    现在由过去推演而来。可查证、可追溯的计算过程，把 data dependency 显式建模了。普通数据库也可能存在表间依赖，但这些关系未必构成明确的计算图。例如通过 ICS 时，程序取出当时的课程学分加到总分里；课程学分后来可能变化。Event sourcing 保留事件发生时的事实及计算依据，能追查当时按几学分计算，减少各处派生结果不一致的问题。

    从这个角度看，我觉得 SQL 或关系代数也有一个“billion-dollar mistake”。这个说法来自 Tony Hoare 对自己引入空指针的调侃：空指针可能使程序崩溃，严重时甚至影响火箭。关系代数在当时提供了很好的可扩展架构，但没有把图灵可计算的依赖关系作为一等公民来管理。我也不能直接把它说成设计缺陷。比如学生表中为了快速查询而保存“能否毕业”的 0 或 1，其背后可能是复杂计算；关系代数很难把任意复杂计算表达成视图，这个派生字段就可能与其他数据不一致。

    MVVM、React、data flow、event sourcing 等设计，都在用不同方式显式表达 derived state 和 dependency。回头理解这些经典设计，再看新框架为什么采用相应机制，就能更清楚地看出它们解决的问题。

    图 30：95:47，《记账为什么麻烦？》“当前状态”同时编码了过去、现在、未来。过去是合同签订，现在是等待打款，未来是货物交接和潜在坏账。
