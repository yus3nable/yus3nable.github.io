    和机器沟通，就剩提示词这一条渠道

    原片 00:00:00–00:03:40

    今天讲提示词：我们用自然语言与 AI 沟通的接口，也是生成式软件工程中的重要工具。

    图 1：00:00，仙1-107。讲者在讲台，右侧还是这节课的笔记。

    从 ChatGPT 普及开始，大家就习惯了在聊天框里给模型下指令。

    Prompt 可以让 AI 生成文字、代码和图片。我第一次感受到它的力量，是在 2023 年准备操作系统课时。当时 ChatGPT 刚发布不久，我故意写了一段很少有人会实际使用的 inline assembly，让它解释。按我的判断，这段代码应当没有出现在训练材料中，但它解释得出奇地好，虽然仍有不完善之处。那一刻我意识到时代要变了，只是还看不清后面的变化。现在写 inline assembly 都快成传统技艺了。

    ChatGPT 之后，“提示词”成为流行的新词。大家首先想到的，通常是聊天框里那段话，比如“帮我生成一个游戏”或“帮我做完作业”。

    图 2：00:00 左右，右侧还是这节课的笔记底稿。笔记里写着：对 Agent 来说，自然语言不只是你输入的那一句，还散在各处；从 ChatGPT 时代起，大家仍习惯把这些都叫提示词。

    Agent 接收的提示词分布在整个上下文中。用户开口前，它已经读到 harness 内建的 system prompt，随后还可能加载 AGENTS.md、skills，以及指令要求它继续阅读的文件。工具调用和返回结果也会进入这条线性的上下文。等用户说“给我做个游戏”时，前面已经积累了许多信息。Codex、Claude Code 这样的 harness 都会组织这些内容。

    模型需要从很长的上下文中遵循要求。例如，为了课堂演示，我在较早的 system prompt 中要求用中文回答。即使后面的用户消息用英文写，它也会继续用中文输出。

    图 3：00:11，课件《“提示词”从哪里来？》。标题写着 ChatGPT 普及了 Prompt，但没有发明它。下面引用 2019 年GPT-2 发布页里的 “prompting the trained model”，以及 2020 年 GPT-3 把任务说明和 few-shot 示例都称为 prompt。

    今天讨论提示词工程，往往需要考虑模型的整个上下文，也就是上下文工程。模型不断预测下一个 token，输出文字或发起工具调用，逐步推进任务。

    图 4：01:24，《提示词不止在对话框》。Agent 看见的是一整个上下文：Harness 内部的 system prompt 和 goal、AGENTS.md、加载的 skills、你给的指令，以及工具和 skills 的调用与输出。页末写着 Pr[token | context]，并注明不是所有 context 都是指令。

    从提示词工程到上下文工程

    原片 00:03:40–00:04:50

    我的感觉是，到 Claude Opus 4.5 这一代，模型经过强化学习和后训练，指令遵循能力有了明显提升。即使上下文接近百万 token，在很靠后的位置，它仍能在一定程度上遵循前面的要求。

    有个常见的测试：在最初的提示词里要求每句话末尾加一个“喵”。工作一段时间后，如果“喵”消失了，就说明这条指令可能已经失效：也许上下文被截断或压缩了，也许模型不再遵循它。此时需要检查和调整。

    这类实践就是上下文工程的一部分。

    图 5：03:44，《从提示词工程到上下文工程》。页上把“提示词工程”收成一句：上下文工程关心每次决策前，哪些token 以什么来源、顺序和作用域出现。目标是 working set 足够小、足够新、带来源、可验证。

    有一点麻烦，就立刻问

    原片 00:04:50–00:09:45

    我反复强调 token，是希望大家养成立即尝试的习惯：遇到一点麻烦，就开始行动。AI 可以成为一个耐心的老师。

    大学时，有些问题室友会、我不会，但开口请教有沟通成本，也担心暴露自己的不足。面对 AI，就少了这一层顾虑：它不会嫌弃问题简单，你还可以不断追问。

    图 6：04:59，《立即行动》。页上写：AI 把“启动一次尝试”的成本压到很低。微积分里一个推导不想验算，数字电路里有个数据通路没看懂，计算机系统基础里链接没搞明白，这些统统可以立刻开始。

    例如，听说 agent 的上下文里有系统提示词、各种指令和工具结果，就可以立即打开一个 agent，问它：“能检查一下当前上下文里有哪些内容吗？”它可能检查自己能访问的上下文或日志，采用你没想到的方法来回答。

    我们现场试一下。模型生成回答时能使用当前上下文，但能否把其中的内容说出来，还取决于明确的限制。有些提供方通过微调或系统指令禁止披露 system prompt。今天用的是自己能够调试的开源框架，可以结合源码和日志查看。

    返回结果中，工具使用指南要求回答简洁，用户级 AGENTS.md 位于 .pi/agent/ 下，是我自己写的。因为这台机器用于上课，我要求它用中文回答，末尾写 Recap，所以每次执行后都会看到一段回顾。此外还有项目级指令，各级目录里也可以放置 AGENTS.md。

    图 7：06:07，演示机上的 Pi 0.84.4。启动信息列出已加载的上下文：~/.pi/agent/AGENTS.md 和项目里的AGENTS.md，skills 里有 compile、make-artifact、make-slides、tag-audio、transcribe。当时用的模型是 deepseek-v4-flash。

    图 8：07:28 前后，Pi 把上下文拆开回报。系统提示来自 Pi 自己；用户级指令在 /home/jyy/.pi/agent/AGENTS.md，里面有简练、用中文回答、结尾必须写 Recap；项目级指令写明这是 2026《生成式软件工程》的教学辅助 Agent。Skills按需加载，工具以 JSON 出现在上下文里。

    上下文里还有 skills 索引。例如 make-slides 负责幻灯片生成和播放，按 F5 就能演示。模型起初只能看到 front matter 中的名称和简短描述；匹配到任务时，才读取完整的 SKILL.md。按课堂中这套机制的描述，用完一轮后，相应内容还会从上下文中移除，避免始终携带整份说明。

    工具定义、会话历史和运行环境也以文本进入上下文。执行时可能注入当前模型、时间等信息。与 DeepSeek Chat 对话时，也可以询问这些环境信息；课堂里将它们与系统提示词区分开来。

    上下文工程要安排好这条长序列里的内容。这个演示也展示了一种学习方法：遇到不明白的地方，直接问，再继续追问。接下来还可以交换角色。

    费曼学习法：让 AI 当听众

    原片 00:09:45–00:11:20

    费曼学习法用“讲给别人听”来检验理解。以前做学生，找听众也有成本：室友可能没兴趣、不愿听，或者已经太熟悉这个问题，无法扮演初学者。

    现在可以先向 AI 请教，等自己觉得理解了，再让它扮演学生。用自己的话把概念讲一遍，请它检查逻辑错误和遗漏。先学、再讲，通过这两个方向检查自己的理解。

    这是你们这一代的机会。现在主要任务是学习，有时间持续尝试；我还要承担许多其他事务。把这套方法用起来，你们可能远远超过我们。

    图 9：09:58，《费曼学习法：让 AI 当听众》。中间是立即行动，四周是选择概念、用自己的话讲解、暴露缺口、查证并重讲。页下写着：卡住的地方信息量最大；这套飞轮的实证支点是 self-explanation 和 retrieval practice。

    学习时，值得留意这些具体的小细节。

    图 10：11:12，《立即行动：解剖当前上下文》。让 Agent 解释“谁在给它下指令”，按目标、权限、工具协议、持久规则、环境和证据分类。模型给出的是当前遵循计划，不是可信的内部状态 dump。

    “安全命令”是谁判的

    原片 00:11:20–00:19:00

    使用 Codex 或其他 agent 时，遇到危险操作通常需要确认。课堂演示中的 Pi 默认采用 YOLO 模式，直接执行操作；提示词不合适，确实可能删掉文件，影响上课。可以通过沙箱限制权限，但这又有使用成本：agent 先在沙箱里尝试，失败后请求到外面重试，还要等待用户选择 yes 或 no。这里需要权衡。

    例如，吃饭前启动三个任务，回来才发现它只跑了一分钟，随后一直在等确认。这既耽误 agent，也耽误人。留意这些细节，会帮助你找到改进工具的机会。

    我发现 Codex 并非每次调用 bash 都请求确认，有些命令被认为风险较低，可以直接执行。例如 ls -l。但命令名不能完全说明实际行为：极端情况下，环境里的 ls 可能被替换成其他程序，甚至执行删除。虽然通常没人这样配置，但这让我好奇它怎样判断风险，于是下载了 Codex 源码。

    我大二、大三时想研究 Linux 内核，光是下载、弄清怎样编译，就花了很长时间，那时已经会用 Linux，仍然很受挫。能坚持下去，靠的是继续尝试的执念。今天面对复杂软件，学习门槛降低了：无论喜欢 Codex 还是更轻量的 Pi，都可以先让 agent 帮你读代码。

    我输入的问题是：“调用 bash 时，有时需要确认，有时不用，风险怎样判定？命令的具体语义很难知道，是做了静态分析、让大模型评级，还是用了其他方法？请读相关代码。”这就是一次具体的提示词实践。

    图 11：14:57，Pi 开在 Codex 仓库里。输入框里是当场打的问题：调用 bash 时，为什么有时要用户确认，有时不要，风险判定是怎么做的。

    Pi 带着已有上下文开始搜索代码。如果提供 LSP 等工具，它还能使用类似 IDE 的跳转和重命名能力。我经常发现，有同学从 PA1 做到 PA4，VS Code 里还到处是红线。项目在受控环境下能编译，并不表示编辑器配置正确。花些时间配置 include path、-I 等参数，就能使用符号跳转、重命名和重构。过去就值得这样做，现在借助 agent，配置更容易了。

    让模型知道什么叫完成

    原片 00:19:00–00:22:20

    接着讨论怎样写好提示词、组织好模型上下文。

    这里又会遇到软件工程的老问题：脑中一个“做国民级应用”的意图，落实成规格、架构、语言和实现时，有许多细节。每次让模型参与，都只是把大流程中的一部分交给它。刚才读 Codex 源码，可能同时读到设计原则、规格和具体实现；把它们对照起来，才能理解安全设计为什么存在、应该怎样工作。

    需要留意意图与规格之间的差距。只说“给我生成一个 CS:GO”，模型很容易做出某个东西后就认定完成，结果却偏离你的期待。提供具体规格会减少这种漂移，也便于检查：明确要求 C++，结果给了 Java，就能判断不符合要求；如果根本没说明语言，模型又不了解你的偏好，就可能走向不同方向。假设模型能力足够，规格越明确，结果也越容易判定。

    可验证的任务能给 agent 提供持续推进的方向，尤其是能用脚本判断测试是否通过时，它可以反复尝试、安装工具或查找资料。但这也可能带来偏差。我读过 OpenAI agent swarm 参加 CTF 的复盘：面对无法完成的明确任务，上千个 agent 持续尝试，最后寻找系统漏洞、提交不合规则的结果。完成目标很明确，并不保证它选择的方法始终合适。

    图 13：19:56，《上下文工程：让模型知道“完成”是什么》。Context 里是一份复杂要求。约束可以是 intent，也可以是spec。页上写：Pr[token | context] 本身不是规划器；只有上下文里存在可识别的完成判据，继续干和可以交卷才不是两种高概率续写。

    一步很浅，一串可以很深

    原片 00:33:10–00:38:40

    模型根据当前上下文预测下一个 token。这里有个值得注意的观察：即使参数规模很大，每生成一个 token，仍只是让被激活的部分执行一次有限计算。课上提到 3TB、1.5TB 这类规模，是为了强调总量很大，但单步计算依然有限。

    计算机专业会介绍图灵机和有限状态机。你可能听过图灵机计算能力的说法，却还不清楚其背景。有限状态机只有有限个状态，可以在这些状态之间循环；图灵机多了一条理论上无限长的纸带，可以记录中间结果，就像有了草稿纸和记忆。

    Manuel Blum 给研究生的建议里有个我喜欢的比喻：人可以看作有限状态自动机，但有了纸和笔，就像有了图灵机的纸带，计算能力发生了跨越。

    这句话鼓励大家边想边记，随时回看。持续积累记录，就能把过去的思考接起来。

    思维链模型也在利用上下文记录中间过程。它的“纸笔”只能往后写，不能直接擦掉错误，只能在后面纠正，并借助注意力减少错误内容的影响。简单问题可以立即回答；困难问题则先尝试，写出解法，再判断、修正、继续。模型用更多 token 换取更深的计算，减少直接回答出错的风险。

    我把早期 ChatGPT 的一个问题理解为训练奖励造成的迎合：不回答会受惩罚，随便答却可能碰对，于是模型倾向于总给出答案，带来幻觉。经过强化学习的思维链模型更重视回答正确，会逐步尝试、逼近目标。这类在推理时投入更多计算的做法，就是 test-time scaling。

    图 22：33:09，《一步很浅，一串可以很深》。Pr[token | context] 是深度非常有限的计算。模型学会利用上下文思考：不确定时先试，错了再输出 token 纠正。每个新 token 又成为下一步的 context，这就是 chain-of-thought。页上把它比成图灵机的纸带。

    注意力会抢，指令要放在它能看见的地方

    原片 00:48:15–00:55:00

    再看指令遵循背后的注意力机制。Transformer 由多层结构组成，生成一个 token 时，会对过去不同位置的信息给予不同程度的关注。

    例如，系统提示词要求用中文回答，用户同时要求实现赛车游戏。写代码时，模型会更多关注代码和功能需求，中文回答的要求暂时不那么突出。整个上下文很复杂，注意力机制从中提取当前计算所需的信息。

    代码写完、开始回顾任务时，模型又可能注意到中文输出等要求。这有点像人做题时专注于算式，算完后再检查其他条件。不同输出阶段关注不同信息，是训练得到的能力。

    模型也会出错，但继续生成时，可能同时注意到刚写错的内容和先前要求，再进行纠正。藏头诗的演示就能看到这种过程。即使上下文很长，它仍能在一定程度上检查约束。

    指令越多，彼此竞争注意力的压力也越大。GPT-3.5、GPT-4 时期常见的“你是某领域专家”这类长提示词，可以理解为尝试把注意力引向某种身份和表达方式，弥补较弱的指令遵循能力。

    从 GPT-5 这一代开始，思维链和指令遵循能力增强，许多奇特的提示词不再必要。更有用的是把明确的 verifier 放进上下文，让模型检查结果。训练时，违反可检测的要求会受到惩罚，模型也因此学会反复对照条件，像一个熟练的做题者。

    例如做前端，明确要求白色背景、取消半透明效果，模型通常能检查并遵循。再要求每次设计后截图、用视觉检查，也可以把验收过程纳入任务。

    但它有时会把“白色背景，不要半透明效果”原样写进代码注释。它知道这个要求重要，却没有区分产品要求与代码注释的用途。这种表现说明，遵循指令和理解人的表达意图仍有距离。

    可以用 AGENTS.md 或 skill 规定注释写法，但新增规则又会占用上下文。目前我认为没有通用规则能一次解决所有问题。网上的 skill 初用可能有效，继续用又发现不足，反复修改后可能陷入困境。此时最好回到具体任务，想清楚模型注意到了什么、为何得到这个结果，再写必要的指令。这只是经验性的解释和调整，后面还会继续看案例。

    图 27：48:35 前后的课件《用好模型遵循指令的能力》。过去的上下文一直都在场。例子包括：全局 AGENTS.md 里要求用中文，这个“用中文”会一直保持一定注意力；全局的 git commit 不要写成 “Copiloted by Claude Code”。页上同时提醒Lost in the Middle：长上下文里的信息不会被同样可靠地利用。

    最常见的请求大概是：“我想读 paper.pdf，请总结一下。”这种方法有什么问题？

    论文通常经过多次修改，论证看起来很连贯：A 推出 B，再到 C、D。整篇放入上下文后，模型很容易沿用作者安排好的逻辑，默认接受这些前提。得到的总结因而往往只是在重述作者的观点。

    读陌生项目或教科书也有同样的问题。例如链接、加载没学懂，反复让模型总结，得到的仍可能只是原文的另一种说法。

    换成不确定的追问，模型又可能随你的态度摇摆：说好它就赞同，说不好它又批评。即使作者诚实、实现公开且可运行，你仍需要评价研究贡献。模型却可能盯着“实验还能跑久一点”等次要问题，甚至打开 Chrome DevTools 去验证与目标不太相关的细节。使用强模型时，也需要交叉核对判断。

    我的做法是先让 AI 理解我的阅读立场。眼前它开始核查论文例子是否真实，但我当前要了解的是工作贡献；对于自己写的这篇论文，这一步并没有帮助我回答目标问题。

    读论文，或在允许使用 AI 的审稿场景中，我会要求：先站在人类已有知识的边界上，列出相关问题、历史上已经解决到什么程度，再看这篇工作新增了什么。这样先建立共同的判断基础，减少直接接受作者叙述的影响。

    学生需要先让 AI 了解自己的知识边界：学过哪些课程，编程到什么程度。可以把这些信息维护成记忆，再要求它用自己学过的概念重新讲解材料。

    比如学习链接，先从“已有一个程序能把 .cpp 变成 .exe，为什么还需要链接”开始，把双方拉回共同理解的起点。读我们那篇软件状态可视化论文时，也可以这样追问：已有工作究竟哪里不能满足实际使用？我对一线模型整理相关知识比较有信心，对 Flash 仍会多核对。把自己的知识放进上下文，有助于减少模型自说自话。

    接着依据论文、教材和已有事实，向前推理一步，再检查这一步是否合理。这种反馈不像程序测试那样严格，但仍能让讨论逐步推进。模型会批评论文实验不足，不过这篇论文已被接受，人类评审认可了其中新的、合理的工作。实验总能继续改进，我个人审稿时更常拒绝逻辑断裂的论文。

    我关心论文是否带来新知识。昨天拒绝的一篇工作，大致把重要问题 A 分成 A1 和 A2，再优化研究较少的 A2。路线看似完整，问题却在投入与收益：按我的估算，A1 占 99% 的运行时间，A2 只占 1%，即使 A2 再提升 10%，对总体也接近噪声。局部实验正确，仍不足以说明为什么值得研究这个优化。

    作为学生作业，这样的探索有价值，但作为论文还需要说明贡献。学生可能被安排研究 A2，也可能自己选了它；如果方法很出色，也有意义。可这篇工作只是把 A1 的部分处理移到 A2，改善了局部指标，缺少令人信服的整体理由。

    我担心论文发表和评审体系会受到冲击。AI 生成的内容大量进入社区，如果写作、评审都交给 AI，评审又只沿用作者的叙述，便可能无人认真追问工作对整个领域的意义。最后人人用 AI 读 AI 写的文章，质量问题会不断累积。

    GPT-5.6 给出的审稿也有这种局限：它总结内容、检查 claim 的证据和逻辑，却未充分回答“值得读吗”。即使每篇文章逻辑自洽，研究生也未必值得花一个小时读它。是否能发表、是否值得投入阅读时间，是需要分别判断的问题。

    对齐过去的自己

    原片 01:12:40–01:15:20

    这也引出我的学习方法：不断扩展自己理解的世界。读到有启发的论文、博客，哪怕来自几十年前或其他学科，我会追问：为什么以前不知道？缺少哪些前置知识，盲区在哪里？把这些与过去的理解接起来，就增加了一些能继续推理的事实。

    我做教师后读过不少计算机以外的论文，例如《自然》百年科学经典里收录的历史研究。生物谱系为什么能追溯共同祖先 LUCA，就是一个例子；线粒体的母系遗传和突变也为追溯关系提供线索。理解这些事实，再联系已有知识，认识的范围就会扩大。有 AI 协助，这个过程可以更快。

    只听我讲故事还不够，必须亲自实践。AI 解释很久仍听不懂，很正常；我也会要求它换个说法。经过几轮沟通，先同步双方理解，再把推理过程讲清楚，才能逐渐找到适合自己的学习方法。

    藏头诗这类短任务，验证条件容易写清；学习的验证条件则可能复杂得多：是否按我的思路重新组织了知识，是否扩展了理解边界？一本好书可能让原有事实建立新的联系，改变你看问题的方式。事实没变，组织方式变了，后面的思考也随之改变。

    这些成功和失败的经验，可以逐渐整理成适合自己的 skill。我自己的学习流程也是这样积累出来的。

    长程任务里，小演示容易，维护会翻车

    原片 01:15:20–01:24:40

    接着看长程任务。PA 作业这类有明确验收条件的任务，还不完全是我这里说的 long horizon。更困难的任务带着未知：大致有意图，但规格和实现都不清楚，最终还要交付高质量产品。此时需要先组织探索，不能只让 AI 接着上一句话往下做。

    强化学习的反馈让模型倾向于尽快通过验证、完成任务；规划过长，又可能耗尽上下文，令用户不满。当前模型因此很擅长“完成 PA2”这类边界清楚的要求。

    从零生成一个小演示往往也不难。个人主页、赛车游戏，可能一句话就能做出能运行的版本。可继续加功能、长期维护时，某个阶段开始不断出错，修改成本越来越高。这正是《人月神话》等软件工程讨论反复出现的问题。

    一个看似矛盾的现象是：AI 在大型复杂系统里有时更顺利。早年 Linux 2.6 的内核源码还相对容易入门，今天想了解文件打开过程，可能连续追十层函数调用，才找到简单的赋值操作。长期演化带来了许多抽象，初学者读起来负担很大，但 AI 往往能在这种结构里工作。

    长期维护的高质量代码，会给模型提供可参考的实现方式。一个新功能可能已有几处相似实现，模型可以据此找到 helper、锁的使用顺序和结构约定。人不熟悉子系统时，需要花很大精力理解这些关系；模型读过相关文件后，却可能迅速组合已有做法。上下文的影响在这里产生了积极作用。

    我们过去修改 Android runtime 和即时编译器时，难度曾让一些同学放弃方向，甚至不愿再写代码。AI 处理这类系统却可能很顺，做小型游戏反倒容易越改越乱。这些差异与提供给模型的上下文、模型处理上下文的方式有关。

    新模型出现后，今天的一些经验可能改变，需要重新理解它的训练和行为。但我判断，模型在高质量系统中识别并沿用有效模式的能力会继续增强；遵循明确要求这条方向不会倒退。

    我有个还没验证的研究想法：从优秀项目中提取设计经验，比如每个领域选十到二十个项目。A Philosophy of Software Design 就是在总结类似经验：如何组织类、何时封装、何时继承。能否给 AI 一份与任务相近的优质参考，让它既吸收设计，又不把参考项目误当成目标？也许能减少低质量实现，提高长期维护性，但可能需要微调。直接放整个仓库未必合适，也可以先把好模式提炼为文档。

    不同设计还会冲突：松耦合的消息机制与把操作统一收进 gateway 的方式，未必能同时采用。可能需要提供几种参考，让 AI 经过多轮比较，收敛到适合当前项目的结构。我觉得这值得研究，比在一个既定子问题里排列组合方法更有探索空间。

    今天的 AI 仍需要人的领域理解和引导。一方面，要继续学习处理器、操作系统、编译器和数据库中的设计经验，只是可以用更高效的方法学。另一方面，要理解上下文中的信息怎样影响结果。本学期会讨论如何用软件工程方法给出要求、观察执行、设计验证条件。把 verifier 放进去只是第一步，还得判断它是否合适。

    与组织工程团队相比，AI 降低了一部分沟通成本。模型已经见过大量方法，我们要用必要、简练且能被持续注意到的要求，把它引向合适的方向。

    原片 01:24:40–01:29:00

    举一个研究失败的例子。我们想优化符号执行引擎：用程序分析另一个程序，自动验证某些性质或正确性。现有方法执行较慢，寻找有效优化，是适合学生开展的增量研究。

    一位同学拿到一个初步想法，觉得可能有效，GPT-5.6 Sol Ultra 也表示赞同，便投入大量 token 探索。但模型不断给出正面或负面反馈，他无法判断这些反馈是否可靠，也不知道遇到否定结果该怎样继续。

    问题出在任务表述：“我想证明方法 A 有用。”这个要求让模型围绕证明原始想法展开，忽略了更大的研究问题。它构造许多小 benchmark，在上面反复调整，给出局部结论，却没有增加对实际问题的理解。构建方法时固然常从小实验开始，但不能把证明自己正确当成研究目标。

    我建议从真实工具和当前较好的算法开始做 benchmark。即使跑几个小时仍超时，留下的搜索路径也有价值：它们能揭示哪些程序结构会让现有方法遇到困难。这样才能找到有意义的优化方向。这次失败说明，人仍要判断实验能带来什么知识，也需要调整与 AI 合作的方法。

    如果不了解操作系统、编译器等已有知识，就很难提出合适的问题，也难以引导 AI 探索开放问题。

    图 33：85:57，《Research Failure：Token 花完了，知识没有增加》。页上写一位博士生用 GPT-5.6 Sol Ultra 去优化符号执行引擎：benchmark 丢进去，想法丢进去，花了很多 token，没有结果。缺的不是 token，而是便宜、局部、可归因的反馈。Agent 被训练成“把任务做完”，研究却允许最好的结论是“原始 idea 不成立”。

    少盯着它改，把时间留在收益大的地方

    原片 01:29:00–01:32:00

    与 AI 合作时还有时间分配的取舍。我盯着 Codex，一旦跑偏就补充领域知识，单个任务通常能更快完成。但多给它一些时间和 token，它往往也能自己完成。人的精力有限，需要决定什么时候干预最值得。

    纠正 AI 会带来一种微妙的满足：它让我觉得自己仍比 AI 多一些判断力。但这种满足未必值得持续投入时间。对于 AI 能独立完成、自己也知道如何验收的任务，可以让它运行，回来检查结果。学生更应该把有限的时间用于理解未知，而不是反复盯着自己已经会做的事情。

    AI 出现以前，就有人提醒不要用忙碌感代替有效努力。现在不同学习方式带来的差距可能更大，值得认真安排精力。这是我的一点体会。

    算力换智力

    原片 01:32:00–01:36:10

    对于充满不确定性的长期探索，只靠一条思维链未必足够。让模型“比较几个方案，选最好的”，得到的可能只是它有限搜索后认为可接受的方案。我认为，这也与尽快完成任务的奖励倾向有关。明确验证条件的任务，和探索未知方案，难点并不相同。

    可以用复杂性理论作类比。对 NP 问题，给定候选解后常能在多项式时间内验证，但寻找解可能很困难。验证一条路径是否为哈密顿路径较容易，寻找满足要求的路径却是 NP 完全问题。模型为了及时交付，也只能进行有限搜索，类似考场上即将交卷时，必须先写出一个答案。

    图 35：92:11，《在不确定性中探索》。如果所有要求和路线都清楚，chain-of-thought 就能解决。“帮我考虑一下几种方案”有效，但可能不是最佳的。页上引用 Herbert Simon 的满意化：搜到“够好”就停。探索的瓶颈常常是模型太早认定“已经够了”。

    可以尝试用更多计算扩大探索。比如起名字：一个班里有许多“子涵”，说明人也会集中到相似选择。模型知道去《诗经》找字，品味也在改善，但大家都用同一个模型，仍可能得到一批相似名字，成为 AI 时代的“子涵”。

    更系统的方法类似进入科研领域前做文献调研。名字的候选空间可以枚举：先选读音、排除不合适的音，再让不同 sub-agent 检查对应的字，也可以限定《诗经》等来源。把开放的大空间分成互不重叠、条件更清楚的部分，再分别搜索与验证，就能投入更多计算来扩大探索。代价是消耗更多 token；直接让一个模型给几个答案，则更容易受它自身偏好限制。

    图 36：94:24，《算力换智力》。不要只问“给我几个名字”。例子是：给我小孩取一个蒋姓、好听、又有寄托的名字。直接让它给一些，AI 有自己的 bias，别人也会用，成为 AI 时代的子涵。页上把灵感改成搜索：先独立采样，再汇总，别让 sub-agent 一开始就互相抄答案。

    墙里面是超人，墙外面是动物世界

    原片 01:36:10–01:38:25

    这让我想到人类的差异。世界很大，个体能学到的很有限；Richard Sutton 的 Big World Hypothesis 讨论的就是这种限制。不同城市、教育和生活经历形成不同偏好，也让人们掌握不同知识。把这些差异组合起来，群体就有机会完成个体做不到的事。

    但如果有价值的长期问题越来越能通过计算资源解决，也可能出现新的鸿沟。少数人拥有大量算力，获得更快的认知和探索能力，把资源圈在一堵墙内；墙外的人即使努力，也追不上里面产生新知识的速度。我用“墙内是超人、墙外是动物世界”这个强烈比喻，提醒大家思考这种可能性。

    AI 正接近这样的转折点。我们需要思考，怎样避免这种未来。

    图 37：98:25，课的最后一页《墙内的超人》。图是一堵墙，墙里是机房，墙外是人群。下面写：资本家可以获得无限的计算资源，获得无限的智力，人本身的价值在减弱。并引用 Stanford AI Index 2025：2024 年近 90% 的 notable models来自产业界，若干前沿模型的训练算力成本已经是数千万到近两亿美元。
