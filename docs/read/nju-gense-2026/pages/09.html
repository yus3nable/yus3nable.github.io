    你就是那个 CTO

    原片 00:00:00 – 00:03:08

    软件工程和项目管理的概念，正在 Agent-native 时代重新定义。上周 Anthropic 提到 Git 已经不够用，这在版本管理课里也讨论过。独自写 C++、Python、JavaScript 时，开发者相当于一条单线程；有了 agent，组织方式就像一家公司：自己担任 CTO，下面有架构、产品、UI、前后端，各个 agent 还可以继续管理 subagent。

    这种组织用于管理复杂需求，最终产品仍要进入仓库，经 CI/CD 上线。每个任务对应仓库中的部分区域，重构子系统与修复小功能的影响范围不同。Anthropic 的方案还没采用我想加的锁：除读锁、写锁外，还应区分重构和小修。互相独立、不会破坏架构的小修可以并行。操作系统和数据库已有悲观锁与乐观锁：前者先锁定再操作，后者先执行再检查冲突。新的版本控制方式，可能从这种协作组织中逐渐形成。

    图 1：3:09 左右，《Review & Comments》。Brooks（1986）那条写着：花在 accidental complexity 上的工作不到九成，即使全部消除，也换不来十倍提升。下面是开发状态管理和 CI/CD。

    从零做一个 harness

    原片 00:03:08 – 00:06:15

    接下来回到一个具体产品：DeepSeek Harness。前天我参加了它在北京的线下聚会，许多同学没有传统编程经历，主要通过对话提出需求，但愿意交流实践，几年后可能成为主要开发者。今天讨论从零构建 Agent Harness 会遇到哪些需求、架构与系统设计问题。下一课再讲二次开发，以及其中更细的 Agent-native 开发机制和 CI/CD。

    有同学觉得前几课说了很多，却似乎没有具体收获。许多原则听起来简单，实际应用才会暴露问题。网上有 grill-me、superpowers 等 skill，使用后可能把任务引向自己不想处理的方向，或反复启动 subagent 做当前无须进行的测试。这些流程在企业产品开发中可能合适，面对未知任务时却需要判断。最好亲自体验一次。

    这台机器已经装好编译后的 DeepSeek Harness，可以正常对话。过去部署复杂开源软件常常很困难；这两天我主要通过描述目标，让 agent 完成部署和修改。只要知道项目大致可以编译，就能开始让它执行。

    一百五十行在高铁上断了

    原片 00:06:15 – 00:10:32

    可以从上一课约一百五十行的 mini agent 出发理解 DeepSeek Harness。几乎所有 Agent Harness 都有相似循环：模型发出一轮回复，接下来可以由人响应，也可以由工具返回结果。这个最小实现已经能完成实际任务。

    周日在高铁上，我让它做了一个复杂任务。新模型刚发布，只输入一句话：生成一个比例基本真实的南京大学仙林校区三维图。结果比预期好，虽然计算机楼十层的高度明显不对，杜厦图书馆的几何形状却保留得不错。

    它利用了网上的数据。OpenStreetMap 的地图很细，连篮球场上的线都有。模型抓取数据后自行补充建模，却没有充分核对：空白区域直接铺成绿地，大门处被画成建筑，还种满了树。可以进一步要求逐块分析区域用途、精确建模，可能多消耗约十倍 token，再修一版。网上展示 GPT、Opus 或 DeepSeek Flash 图形能力的许多案例，也依赖 skill 不断推动验证，用更多计算改进初版。

    这可以作为南大版 GTA 的起点：有了三维场景，再定义哪些地方能走、能蹲，就能逐步加入游戏逻辑。

    但这个原型还不能成为产品，因为它假设网络始终连通。一两轮对话不容易暴露问题，在高铁上跑长任务时，已有中间结果却突然断网，进程直接结束。它没有会话保存、恢复或断线重试，只能重新开始。真实使用产生了无法回避的 essential complexity：API 中断后该怎么办？

    图 4：6:16 左右，《Agent Harness：需求》。上节课的 150 行 mini agent 完全可以工作。one-shot 的那句话是：生成一个相对真实的南大仙林校区 3D 图。下一句是：不，它不能。

    图 5：高铁上那句话跑出来的仙林校区。杜厦图书馆、公共教学楼、学生宿舍都在图上，楼的层数和绿地是它自己补的。

    重试不是再做一遍

    原片 00:10:32 – 00:14:26

    Coding agent 的重试策略必须适应环境。在美国数据中心访问 OpenAI，与在国内经过多层代理访问，网络条件差别很大，timeout 不能始终写死。失败后可以等间隔重试，也可以延长间隔。网络课程中的 exponential backoff 就是后者：一秒后仍失败，立即再试大概率也无效，于是改为两秒、四秒、八秒。高铁上那次物理网络故障，恢复可能需要两三分钟。

    让 AI 继续分析，还会发现客户端与服务端状态可能不同。例如手机发起支付，服务端已把订单交给银行或航空公司，事务不能一直等待手机确认。手机中途断网，界面可能还在转圈；应用需要提示网络故障和结果尚不确定，而不能直接崩溃。这些情况都属于必须处理的需求。

    图 6：13:00，《API 中断，应该怎么办？》。暂时断网要保留进度、有限重试；输入损坏或权限不足，需要先改变条件。未收到结果时，执行可能已经发生，恢复后应先核对实际状态，避免重复执行带副作用的操作。

    需求的根基会塌

    原片 00:14:26 – 00:19:43

    一百五十行远不足以覆盖产品需求。Agent 可能同时处理多个工作目录，需要 dashboard 切换项目；还需要项目相关的工具和 skill，以及工具调用的沙箱、权限和 approve 流程。需求规格会迅速增长。

    我让 AI 模拟老板的要求：比较当前面向人交互的 agent 产品，看看 DeepSeek Harness、WorkBuddy 等谁卖得好，再做一个类似产品。它意识到 DeepSeek Harness 的设计方向有所不同，先列出典型场景，例如从本周项目文件生成周报、列出延期项，再扩展到历史检索、任务复用、模板、偏好、预算、用量、账号、数据、外部内容与指令隔离、用户反馈，以及更多非功能需求。

    直接让 agent 实现这份清单，容易得到难维护的代码。模型倾向于完成当前任务，未必主动考虑未来变化。MVP 用来验证真实需求，产品还需长期演化。小 agent 对网络和 API 稳定性的假设一旦失效，就会增加许多需求；Agent Harness 面临的挑战还包括需求本身不断变化。

    假设按照办公场景写完详细需求，开发了五十万行并上线，随后 Grok Bot 流行起来：用户把 agent 当作有记忆的人，可以拉群、安排每日任务。原先左侧项目栏、右侧不同 view 的交互基础就受到了冲击。程序员常调侃“改三次需求就够了”。大厂为保证交付质量，架构通常比较保守，遇到这种变化，需要重新协调方案和复用边界，再进入下一版。

    架构没有免费的午餐

    原片 00:23:27 – 00:27:33

    把需求文档交给 agent 设计架构，它通常围绕已有需求组织模块。需求中有工作区，就建立工作区 class，再连接模型、agent、session。Session 发起 chat，agent 运行 loop 和工具，结果回到 session，再把会话存进数据库。这很自然，也是大厂常见的架构画法。

    模块边界一旦确定，开发某部分时就可以少了解其他部分，多个 subagent 也能尽快并行实现。但约束同时减少了自由度。Grok Bot 式的新需求出现时，如果原有架构无法承接，抽象就会泄漏，维护难度随之上升。

    另一种做法是让工作区、session、agent、UI 各自成为进程，相互发消息，类似 actor model。但只说“发消息”还没有规定协作方式。如果工作区与 agent 只能通过一条 session 消息队列交互，接口明确，开发就较容易；若何时发送什么都未约定，自由虽大，也几乎没有架构约束。两种选择各有代价。

    图 10：23:33，《架构：没有免费的午餐》。架构是受限和自由之间的平衡。进程、高级语言、LAMP、event sourcing 各牺牲了一项，换来边界、分工或可重建的状态。

    自由和受限

    原片 00:27:33 – 00:32:54

    每层架构都在取舍。进程抽象允许构建浏览器、coding agent、虚拟机等大量应用，却也有边界。人们争论用什么语言写操作系统已经几十年；我上学时还流行“PHP 是最好的语言”这个梗。C 提供较大的机器控制能力，也带来内存泄漏等问题。很难同时获得完全的自由与牢固的约束。

    LAMP 由 Linux、Apache、MySQL、PHP 组成，支撑过十几年互联网应用，WordPress 是典型例子。面向一亿、十亿用户时，单机与数据库都会遇到瓶颈，需要分库分表、扩展服务器，原来的抽象开始暴露底层问题，推动下一代架构。

    Event sourcing 把事实作为只追加的记录，当前状态由事件推导，结构清楚，性能却更难处理。现实需求有时只是直接改当前状态，例如教务员希望悄悄让不满足条件的学生毕业。在 event sourcing 中，需要添加“特批毕业”的事件及规则，进入持久历史后就能被审计，提交者也留下记录，无法再以不知道经过为由解释。这换来了更清楚、可回溯历史版本的系统。

    LAMP 与单机时代的需求匹配时，PHP 就是合适的选择；假设改变后，原有架构可能成为阻力。社会中的产业变化也有相似过程：国企改革、房地产、互联网、云计算、AI，每次变化都伴随人才流动与淘汰。AI 还会加快这种演变。后面几页是 AI 协助补充的案例，可以继续看 slides。

    图 11：33:13，《操作系统：进程的自由有边界》。进程在自己的地址空间里跑，不能改谁的内存就改谁的。内存够用这个假设一破，交换、OOM 和地址映射就露出来。

    接受一种计算形式

    原片 00:32:54 – 00:38:21

    看一个具体案例。我先说成 2010 年，更正一下，是 2004 年。Jeff Dean 和 Sanjay 的论文 MapReduce: Simplified Data Processing on Large Clusters，改变了以中心化服务器为主的一些做法。它容易读，看示例即可：接受 map 与 reduce 的受限计算形式，就可以编写大规模分布式任务。Python 也有类似操作，map 把函数应用到 list 元素，reduce 逐步合并元素；满足结合律时，可以分别合并两部分，再合并结果。

    MapReduce 要求先 map，再按 key 分组、排序和 shuffle，最后 reduce，隐藏了系统实现。早期 Google 内部用 C++，包含 mapreduce.h，写 class 定义 map 与 reduce。操作对象由系统封装，可能分布在多台机器上。示例指定最多 2000 台机器、每个任务 100 兆内存，再启动执行。机器规模一大，故障就必然需要考虑，例如为整个互联网建索引时，总会有机器掉线。LAMP 或自己的课程作业常默认机器稳定；Google 必须通过系统抽象处理故障，无法靠人工解释把问题搁置。

    这种约束适合离线任务，却难以覆盖实时需求。银行订单等数据走向分布式后，单纯 MapReduce 就不够用了，后来有 Spark 计算引擎和 Flink 流式处理。Flink 又与 event sourcing、函数式编程有关。架构持续在自由与受限之间寻找平衡。

    图 12：36:30 左右，《MapReduce：接受计算形式，换取集群能力》。接受 map、按 key 分组、reduce，就得到自动并行、任务调度、负载均衡和失败重试。热门 key、重复发送，原文要求应用自己保证额外的幂等。

    图 13：38:00，《当计算不再是一轮批处理》。Spark 用 DAG 组织多阶段计算，并缓存可复用数据；Flink 持续处理到达的数据，以事件时间、水位线与迟到处理策略决定何时生成或修正结果。

    所有东西都是插件

    原片 00:38:21 – 00:45:00

    设计 Agent Harness 的基本原则是什么？最初提纲提到微内核和操作系统。操作系统无须预先知道进程的用途；Unix 诞生时还没有桌面浏览器，却能支持后来的进程组合。这里采用 Everything is a Plugin：每个插件保留私有状态，通过消息与其他模块交互。这与 actor model 不完全相同。理论上，把函数调用换成远程过程调用，也能得到类似组织；仅有这一点还不足以形成有用的架构。

    Cordis 是其中一部分，包含形式化讨论，今天暂不展开。它负责服务解析、依赖激活、插件加载与卸载。类比操作系统，进程退出后资源应被回收，写 OJ 时常不手动释放内存，也是依赖系统最终清理。Cordis 让插件声明所需资源和副作用，自动激活依赖，并在卸载时回收相应资源。

    Harness 的难点在协同：插件不交流就无法工作，随意发消息又会混乱。因此需要为 agent 建立共享的世界模型，把重要数据结构和协作规则定义清楚。系统没有特权内核，所有东西都是 Cordis 插件；core 中的 Session 是只追加事件日志，作为事实依据。模型看到的消息由 deriveMessages 派生，这就是 event sourcing。Event bus 让插件监听变化，服务则有 definition、provider、consumer 和权限，事件按领域分类并提供扩展点。其他能力围绕这份历史记录生长。

    图 14：38:31，《设计 Agent Harness》。每个插件有私有状态。Cordis 管服务解析、依赖激活、作用域和卸载，今天不展开。不协同就没用，随便协同就没法用。

    世界模型在总线上

    原片 00:45:00 – 00:52:02

    插件把事件送到 bus，消息格式、发送权限和类型关系由共同规则约束，TypeScript 能在编译时检查类型。其他插件可以监听 body，某些钩子还允许修改事件。这些原子能力构成一个小型操作系统，例如插件可以观察本轮模型推理输出了多少 token。

    一轮推理结束前可以保持未 commit，history 中保留 open 条目，持续接收 token。这个进行中的状态尚未持久化，却能被界面观察，实时显示思维链。监听推理事件的插件还可以统计 token 成本、cache hit，再通过 slot 显示。内测刚开始时这些功能还没有，开发者很快提出 token 和上下文统计需求。实现时只需观察 bus，维护插件自己的状态，无须修改其他系统部分。状态尽量留在本地，需要共享时再发事件。Session 保存事件列表，Agent 接收输入、推进执行，UI slots 装配界面，组合起来就能实现许多办公 agent 功能。

    如果不喜欢聊天框，可以把 Session 流渲染成另一种界面，隐藏原有窗口即可。Trajectory 就是同一份 Session History 面向开发者的展示，包含工具调用、payload 和结果。这样的扩展依赖第一方把 Event 与 Session 定义好：基础概念若失效，后续维护都会困难。定义合适时，大多数插件只消费少量事件，保持较低侵入性；系统也保留更深入干预的能力。

    这些接口包括向 Session append、在 EventBus 注册 handler、从事实生成投影，以及用 Session.deriveMessages 得到轨迹或聊天消息。还可以向 Agent 提交输入，通过 followup、inject、steer 控制后续执行。模型输出时追加的信息，是等工具全部结束、下一模型回合，还是先停止再处理，由这些操作定义。动态上下文也可以持续提供。某些事件在进入系统、尚未持久化时可以修改，例如 agent pre-step。小 agent 的 Build Context 会写入时区、机器信息，也可以改为在 pre-step 中调整本轮上下文。

    整体结构是插件接入总线，使用少量协作接口，大部分状态仍由自己维护。插件能够观察 Agent Loop、Session 和各类投影，了解模型进度及其他插件行为。这些设计为插件生态服务，Trajectory 则是其中一个朴素而有用的调试功能。

    图 16：47:22，《构建 Agent Harness 的世界模型》。Session 等于事件列表。模型上下文和业务状态都是这份状态的投影。旁边类比 Pacioli 1494 年的日记账。Agent 接收输入、推动执行，界面用 slots 装配。

    图 17：50:27，《Agent：接收输入与动态上下文》。followup 是新的一轮用户输入，唤醒执行。inject 补上下文，等后续步骤，不唤醒。steer 尽快进入后续步骤，可以唤醒。动态上下文走 ctx.systemPrompt。

    图 18：53:16，《插件挂在“总线”上》。Session 只追加事件。模型看见的消息由 deriveMessages 投影出来。业务插件和 UI 插件各自守着自己的状态。底下一行写着 Cordis：服务解析、依赖激活、作用域、卸载 effects。

    图 19：53:32，同一套界面切到 Trajectory。系统提示、用户的 Hi、注入的运行时上下文、助手的回答按回合铺开。模型是 DeepSeek-V4.1-Flash，effort 调在 Low。

    许愿的是插件

    原片 00:52:02 – 01:00:00

    基础抽象具备后，就能生成不同界面。原生 Web UI 使用 slots；Text UI 可以只保留 Session 与 Agent，监听包括流式 token 在内的事件，再呈现到命令行，无须修改 Web UI。两者还能共享状态：网页中输入 Hi，终端同时看到输出。早期内测官方仓库曾有 TUI，后来移出，现在使用的是第三方实现。PDF reader 也可以通过工具加载生命周期注入自己的工具。

    插件还可以提供完整工作环境。例如参考 VS Code，把目录作为工作区，组合侧栏、编辑器、浏览器、终端、Git 和 side chat，再接上主聊天窗，形成类似 Cursor agent 模式的体验。插件维护自己的 UI 状态，持续观察主 session，与其他功能可以共存。一个开发者就能通过描述目标，逐步实现自己想要的工作环境。

    DeepSeek Harness 的 creator mode 给了 agent Cordis 相关权限。普通 session 通常只有工作区读写、Bash 等能力，外面还可能有沙箱；creator mode 则可以安装、卸载插件，让正在运行的系统接入新能力。Cordis 支持动态生命周期，类似操作系统随时启动或结束进程。这样一块看似空白的界面，就允许用户直接要求生成插件，形成 creator mode。

    插件之间会打架

    原片 01:00:00 – 01:05:56

    插件架构也有代价。类型统一只能保证大家使用同一组事件，无法消除语义冲突。Better sidebar 的窗口与终端状态由自身管理，也可以向总线发事件。如果安装十个上下文压缩插件，每个都压成一半，最终只剩 1/1024，几乎无法使用。先检查输入还是先改写输入，也会影响结果。两个 hook 分别要求停止和继续时，遇到停止后，后续流程就无法执行。这些属于应用语义中的 essential complexity，需要自行协调。再增加共享状态也可能让抽象边界泄漏。插件减少了一些实现负担，却无法解决所有协作问题。

    驾驶舱插件还在生成。相比固定需求、发布产品再盈利的模式，DeepSeek Harness 提供了少量基础抽象和第一方能力，把更多空间交给开源社区。上周北京 OMDSH 聚会由开发者自行组织，官方没有到场，我只是顺道参加。接口简单、实现复杂性低、容易试验，才有机会形成完整生态。

    图 21：62:55，《那么，代价呢？》。A 改写输入，B 检查输入，先后顺序会改变结果。两个 hook 都合法，一个要继续，一个要停止。十个自动压缩插件，每个压成一半，最后是 1/1024。每个插件单独合理，合在一起不保证合理。

    我觉得社区目前有些方向偏向界面装饰。若由我来推广 Harness，会更关注通过 event bus 接入现有工具、让工具互相组合，充分利用生态能力。高达驾驶舱展示了扩展能力，但可探索的范围还大得多。
