# 前言 {#preface}

<!-- SOURCE pdf-009-b001 -->
<div id="pdf-009-b001" hidden></div>
人们为电子计算机编写程序，已经有八十多年了。然而，对于这些程序该怎样设计、好的程序应当是什么样子，讨论却少得令人意外。敏捷开发等软件开发流程，以及调试器、版本控制系统、测试覆盖率工具等开发工具，都得到了广泛讨论。面向对象编程、函数式编程等编程技术，以及设计模式和算法，也有大量分析。这些讨论都很有价值，但软件设计的根本问题仍少有人触及。David Parnas 的经典论文《论将系统分解为模块的准则》（On the Criteria to be used in Decomposing Systems into Modules）发表于 1971 年；在此后的四十五年里，软件设计的方法并没有在这篇论文的基础上向前走出多远。

<!-- SOURCE pdf-009-b002 -->
<div id="pdf-009-b002" hidden></div>
计算机科学最根本的问题，是问题分解：怎样将一个复杂问题分成若干可以独立解决的部分。程序员每天面对的主要设计任务就是问题分解。然而，除了本书所介绍的工作，我还没有找到任何一所大学开设了以问题分解为中心议题的课程。我们教授 for 循环和面向对象编程，却不教授软件设计。

<!-- SOURCE pdf-009-b003 -->
<div id="pdf-009-b003" hidden></div>
此外，程序员之间的工作质量和生产效率差异很大，我们却很少尝试了解，优秀程序员究竟凭什么远胜他人，也很少在课堂上传授这些能力。我和几位自己认为出色的程序员交谈过，但他们大多难以明确说出，哪些具体方法让自己具备优势。许多人认为，软件设计能力是一种无法教授的天赋。不过，大量科学证据表明，在许多领域，出色表现与高质量练习的关系比与先天能力的关系更密切。例如，可以参阅 Geoff Colvin 的《Talent is Overrated》。

<!-- SOURCE pdf-009-b004 -->
<div id="pdf-009-b004" hidden></div>
<!-- SOURCE pdf-010-b000 -->
<div id="pdf-010-b000" hidden></div>
这些问题多年来一直让我困惑、沮丧。我想知道软件设计究竟能不能教，也一直猜想，设计能力正是优秀程序员与普通程序员之间的差别。最终，我决定开一门软件设计课，亲自尝试回答这些问题。于是，斯坦福大学有了 CS 190。在这门课上，我提出一组软件设计原则，让学生通过一系列项目理解和实践。课程的教法与传统英语写作课类似：写作课上的学生先写初稿，得到反馈，再修改完善。在 CS 190 中，学生从零开始开发一个有一定规模的软件，然后我们进行深入的代码审查，找出设计问题，再由学生修改项目。这样，学生就能看到，应用设计原则究竟怎样改善自己的代码。

<!-- SOURCE pdf-010-b001 -->
<div id="pdf-010-b001" hidden></div>
截至写作本书时，我已经教过三轮软件设计课。本书以课堂中逐渐形成的设计原则为基础。这些原则相当抽象，有些近乎哲学，比如“通过设计消除错误”，学生很难只凭抽象表述就理解它们。效果最好的学习方式，是亲自写代码、犯错误，然后看到错误及其修正与这些原则之间的联系。

<!-- SOURCE pdf-010-b002 -->
<div id="pdf-010-b002" hidden></div>
读到这里，你可能会问：我凭什么认为自己知道软件设计的所有答案？坦率地说，我并不知道。我学编程时，没有软件设计课程，也没有导师教我设计原则；当时几乎不存在代码审查。我对软件设计的认识，来自亲自编写和阅读代码的经历。在职业生涯中，我用多种语言写过大约二十五万行代码，参与的团队从零开发过三个操作系统、多个文件系统和存储系统、调试器和构建系统及 GUI 工具包等基础工具、一门脚本语言，以及用于文本、绘图、演示文稿和集成电路的交互式编辑器。在此过程中，我亲身经历了大型系统的问题，也尝试过各种设计方法。此外，我阅读了大量他人编写的代码，接触了形形色色的做法，其中有好的，也有不好的。

<!-- SOURCE pdf-010-b003 -->
<div id="pdf-010-b003" hidden></div>
<!-- SOURCE pdf-011-b000 -->
<div id="pdf-011-b000" hidden></div>
我一直尝试从这些经历中找出共性，包括应当避免的错误和可以采用的方法。本书反映了这些经验：书中描述的每个问题，我都亲身遇到过；提出的每种方法，我都在自己的编程工作中成功使用过。

<!-- SOURCE pdf-011-b001 -->
<div id="pdf-011-b001" hidden></div>
我不指望本书成为软件设计的定论。我肯定遗漏了有价值的方法，也有些建议可能在长期实践中被证明并不好。不过，我希望本书能引发更多关于软件设计的讨论。请将书中的观点与自己的经验比较，独立判断这些方法是否确实减少了软件复杂性。本书表达的是个人见解，有些读者会不同意其中的建议。遇到这种情况，请试着弄清楚不同意的原因。我很想听到哪些方法对你有效、哪些无效，以及你对软件设计的其他想法。我希望由此展开的交流，能增进大家对软件设计的共同认识。我也会把学到的东西写进未来的版本。

对书中的建议，我希望你保留自己的判断。总的目标是减少复杂性，这比任何一条具体原则或观点都重要。尝试某个方法后，如果发现它并没有减少复杂性，就不必勉强继续使用。不过，请把经历告诉我，我想了解哪些方法有效，哪些无效。
