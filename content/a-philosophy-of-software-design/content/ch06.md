# 第6章 通用模块更深 {#chapter-06}

<!-- SOURCE pdf-050-b002 -->
<div id="pdf-050-b002" hidden></div>
设计新模块时，最常面对的决定之一，是采用通用实现还是专用实现。有人可能主张通用方法：实现一种能解决广泛问题的机制，同时照顾眼下重要的问题和其他问题。这样，新机制将来可能用于未曾预料的场景，节省时间。通用方法似乎符合第 3 章介绍的投资心态：前期多花一点时间，今后省下时间。

<!-- SOURCE pdf-050-b003 -->
<div id="pdf-050-b003" hidden></div>
另一方面，我们知道很难预测软件系统未来的需求，通用方案可能包含永远用不到的功能。而且做得过于通用，可能无法很好地解决眼前的具体问题。因此，也有人主张聚焦当前需求，只构建已知需要的东西，针对当前计划的用法专门设计。采用专用方法后，若发现其他用途，随时可以重构，使它更通用。专用方法似乎符合软件的增量开发方式。

<!-- SOURCE pdf-050-b004 -->
<div id="pdf-050-b004" hidden></div>
## 6.1 让类适度通用 {#ch06-section-01}

<!-- SOURCE pdf-050-b005 -->
<div id="pdf-050-b005" hidden></div>
<!-- SOURCE pdf-051-b000 -->
<div id="pdf-051-b000" hidden></div>
根据我的经验，最合适的做法是把新模块设计得“适度通用”。这意味着，模块功能应体现当前需求，接口则应足够通用，能够支持多种用途。接口既要方便解决今天的问题，也要避免与这些具体需求绑定。“适度”很重要：不要一味追求通用，以至于当前需求都难以实现。

<!-- SOURCE pdf-051-b001 -->
<div id="pdf-051-b001" hidden></div>
通用方法最重要、也可能出人意料的好处，是它比专用方法产生的接口更简单、更深。将来若把类用于其他用途，还能节省时间。但即使模块始终只用于最初的用途，通用方法仍因其简洁而更好。

<!-- SOURCE pdf-051-b002 -->
<div id="pdf-051-b002" hidden></div>
## 6.2 示例：为编辑器存储文本 {#ch06-section-02}

<!-- SOURCE pdf-051-b003 -->
<div id="pdf-051-b003" hidden></div>
来看软件设计课的一个例子。学生需要构建简单的 GUI 文本编辑器，显示文件，并允许用户通过移动指针定位、点击和键入来编辑。编辑器需要支持在不同窗口中同时显示同一文件的多个视图，还要支持对文件修改进行多级撤销和重做。

<!-- SOURCE pdf-051-b004 -->
<div id="pdf-051-b004" hidden></div>
每个项目都有一个类，管理文件底层的文本。文本类通常提供方法，把文件加载到内存、读取和修改文件文本，再把修改后的文本写回文件。

<!-- SOURCE pdf-051-b005 -->
<div id="pdf-051-b005" hidden></div>
许多小组为文本类实现了专用 API。他们知道这个类会用于交互式编辑器，于是按照编辑器必须提供的具体功能定制 API。例如，用户按退格键，编辑器删除光标左边紧邻的字符；按 Delete 键，则删除右边紧邻的字符。有些小组据此在文本类中为每种功能创建一个方法：

```java
void backspace(Cursor cursor);
void delete(Cursor cursor);
```

<!-- SOURCE pdf-051-b006 -->
<div id="pdf-051-b006" hidden></div>
这些方法以光标位置为参数，用专门的 Cursor 类型表示。编辑器还需要支持选区，允许复制或删除。学生于是定义 Selection 类，删除时把这个类的对象传给文本类：

```java
void deleteSelection(Selection selection);
```

<!-- SOURCE pdf-051-b007 -->
<div id="pdf-051-b007" hidden></div>
<!-- SOURCE pdf-052-b000 -->
<div id="pdf-052-b000" hidden></div>
学生大概认为，文本类方法与用户可见功能对应，界面就更容易实现。实际却是，这种专门化对界面代码帮助很小，还增加了界面和文本类开发者的认知负担。文本类最终有大量浅方法，每个只适用于一种界面操作。许多方法，例如 delete，只有一个调用位置。界面开发者不得不学习文本类的大量方法。

<!-- SOURCE pdf-052-b001 -->
<div id="pdf-052-b001" hidden></div>
这种做法让界面与文本类之间出现信息泄漏。选区、退格键等界面抽象体现在文本类中，增加了文本类开发者的认知负担。每增加一种界面操作，就要在文本类中定义新方法，界面开发者很可能最终也得修改文本类。类设计的目标之一，是让每个类能独立开发，但专用做法把两者绑在了一起。

<!-- SOURCE pdf-052-b002 -->
<div id="pdf-052-b002" hidden></div>
## 6.3 更通用的 API {#ch06-section-03}

<!-- SOURCE pdf-052-b003 -->
<div id="pdf-052-b003" hidden></div>
<!-- SOURCE pdf-052-b004 -->
<div id="pdf-052-b004" hidden></div>
更好的方式是让文本类更通用。API 应仅根据文本的基本能力定义，不体现建立在它之上的高层操作。例如，修改文本只需要两个方法：

```java
void insert(Position position, String newText);
void delete(Position start, Position end);
```

<!-- SOURCE pdf-052-b005 -->
<div id="pdf-052-b005" hidden></div>
<!-- SOURCE pdf-052-b006 -->
<div id="pdf-052-b006" hidden></div>
<!-- SOURCE pdf-052-b007 -->
<div id="pdf-052-b007" hidden></div>
<!-- SOURCE pdf-053-b000 -->
<div id="pdf-053-b000" hidden></div>
第一个在任意位置插入任意字符串，第二个删除位置大于等于 start、小于 end 的全部字符。API 使用更通用的 Position 类型，替换体现具体界面的 Cursor。文本类还应提供操作文本位置的通用能力，例如：

```java
Position changePosition(Position position, int numChars);
```

这个方法返回距离给定位置指定字符数的新位置。numChars 为正，新位置在文件中更靠后；为负则更靠前。必要时，方法会自动跳到下一行或上一行。有了这些方法，Delete 键就可以这样实现，假设 cursor 保存当前光标位置：

<!-- SOURCE pdf-053-b001 -->
<div id="pdf-053-b001" hidden></div>
```java
text.delete(cursor, text.changePosition(cursor, 1));
```

<!-- SOURCE pdf-053-b002 -->
<div id="pdf-053-b002" hidden></div>
退格键同样可以这样实现：

```java
text.delete(text.changePosition(cursor, -1), cursor);
```

<!-- SOURCE pdf-053-b003 -->
<div id="pdf-053-b003" hidden></div>
通用文本 API 下，删除、退格等界面功能的代码，比原先使用专用 API 时稍长。但新代码更清楚。界面开发者很可能关心退格键具体删除哪些字符，新代码一看就知道。旧代码则需要到文本类中阅读 backspace 的文档、代码，或两者都看，才能确认行为。而且通用方案的总体代码更少，因为少量通用方法取代了大量专用方法。

<!-- SOURCE pdf-053-b004 -->
<div id="pdf-053-b004" hidden></div>
采用通用接口的文本类，还可能用于交互式编辑器之外的场景。例如，构建一个应用，把指定文件中某个字符串的所有出现位置，都替换成另一个字符串。专用文本类中的 backspace、delete 等方法对它没有多少价值，但通用文本类已经具备新应用所需的大部分能力，只缺少查找给定字符串下一次出现位置的方法，例如：

```java
Position findNext(Position start, String string);
```

<!-- SOURCE pdf-053-b005 -->
<div id="pdf-053-b005" hidden></div>
当然，交互式文本编辑器很可能本来就有查找替换机制，此时文本类已经包含这个方法。

<!-- SOURCE pdf-053-b006 -->
<div id="pdf-053-b006" hidden></div>
## 6.4 通用性改善信息隐藏 {#ch06-section-04}

<!-- SOURCE pdf-053-b007 -->
<div id="pdf-053-b007" hidden></div>
通用方法使文本类与界面类的边界更清晰，信息隐藏也更好。文本类无须了解退格键如何处理等界面细节；这些信息现在封装在界面类中。新增界面功能时，无须在文本类中创建配套函数。通用接口也降低了认知负担：界面开发者只需学习几个简单方法，就能复用于多种用途。

<!-- SOURCE pdf-054-b000 -->
<div id="pdf-054-b000" hidden></div>
原版文本类中的 backspace 是一种虚假抽象。它试图隐藏删除哪些字符的信息，但界面模块确实需要知道这些。界面开发者很可能阅读 backspace 代码，确认其准确行为。把方法放在文本类里，只会让他们更难获取所需信息。软件设计最重要的工作之一，是确定谁在什么时候需要知道什么。当细节重要时，应明确呈现，让它尽可能清楚，就像修改后的退格操作。把这类信息藏到接口背后，只会造成晦涩性。

## 6.5 可以问自己的问题 {#ch06-section-05}

<!-- SOURCE pdf-054-b002 -->
<div id="pdf-054-b002" hidden></div>
识别清晰的通用类设计，比创造它容易。以下问题有助于为接口找到通用与专用之间的恰当平衡。

<!-- SOURCE pdf-054-b003 -->
<div id="pdf-054-b003" hidden></div>
**满足当前全部需求的最简单接口是什么？**如果减少 API 方法数量而不削弱整体能力，很可能是在创造更通用的方法。专用文本 API 至少有 backspace、delete、deleteSelection 三种删除方法，通用 API 只用一种方法就覆盖三种用途。但减少方法数的前提，是每个方法的 API 仍然简单；如果为此增加大量参数，就未必是在简化。

<!-- SOURCE pdf-054-b004 -->
<div id="pdf-054-b004" hidden></div>
**这个方法会用于多少种情况？**方法若像 backspace 一样只为某种具体用途设计，就可能过于专用，这是一个危险信号。看看能否用一个通用方法替换几个专用方法。

<!-- SOURCE pdf-054-b005 -->
<div id="pdf-054-b005" hidden></div>
<!-- SOURCE pdf-055-b000 -->
<div id="pdf-055-b000" hidden></div>
**用这个 API 解决当前需求是否容易？**这个问题有助于判断，是否过度追求简单、通用。为当前目的使用一个类，却必须编写大量额外代码，是接口没有提供恰当功能的危险信号。例如，文本类可以围绕单字符操作设计：insert 插入单个字符，delete 删除单个字符。API 简单又通用，但用于文本编辑器并不方便：高层代码会充满循环，用来插入或删除一段字符。大规模操作时，逐字符处理也低效。因此，文本类最好内置对字符范围操作的支持。

## 6.6 小结 {#ch06-section-06}

<!-- SOURCE pdf-055-b002 -->
<div id="pdf-055-b002" hidden></div>
通用接口相对专用接口有许多优势：通常更简单，方法更少，每个方法更深；类之间的边界也更清晰，而专用接口往往造成类间信息泄漏。让模块适度通用，是降低系统整体复杂性最有效的方法之一。
